# 06 · 签名校验与防篡改：自校验 vs 系统校验

> 一句话点题：安卓有**两层完全独立**的签名校验——系统装包时的"格式+一致性"检查,和 App 自己代码里加的"这真的是官方发布的我吗"检查;**改包重签后 App 会自己崩,崩的从来不是第一层,而是第二层**,搞懂这个区别,你就看懂了报告里"过签名校验"整章在打什么。

上一篇 [05-APK签名体系-v1v2v3v4.md](05-APK签名体系-v1v2v3v4.md) 讲了签名"是什么"(证书、v1/v2/v3/v4 格式、Janus 漏洞)。这一篇讲签名"被谁校验、怎么校验、校验失败会发生什么"——这是报告里"签名校验绕过"整条攻防链的靶子。

---

## 0. 先建立直觉：两层校验是谁在查、查什么

你在 C/C++/后端世界里,最接近的类比是**代码签名(code signing)在两个不同环节各查一次**:

```
                     ┌─────────────────────────────────┐
                     │   第一层:系统级安装校验         │
                     │   (谁来查:PackageManager,       │
                     │    装包这一刻查一次,            │
                     │    开发者不用写一行代码)        │
                     └─────────────────────────────────┘
类比:                 apt/dpkg 装 .deb 前验证 GPG 签名格式合法、
                     Windows 装驱动前验证 Authenticode 证书链完整
                     ——只管"这个包的签名结构没坏、装的时候前后一致",
                     **不管这个证书到底是不是"官方"的**。

                     ┌─────────────────────────────────┐
                     │   第二层:应用自校验/防篡改      │
                     │   (谁来查:App 自己的代码,       │
                     │    运行时随时查,                │
                     │    开发者得自己写)              │
                     └─────────────────────────────────┘
类比:                 你的程序在 main() 里自己读自己的 Authenticode 证书,
                     跟硬编码在代码里的"官方证书指纹"比对,
                     不一致就 exit(1) —— 这是"自己给自己加的保险",
                     **系统不会替你做**,做不做、做多严全看开发者。
```

两层的关系：**第一层允许"任何自签名证书",只要求"内部一致";第二层才是真正区分"你是不是官方"的那道关卡**。报告里"MT 一键过签名校验"打的几乎全是第二层。

---

## 1. 第一层：系统级安装校验(PackageManager 装包干了什么)

### 1.1 谁是 PackageManager?

`PackageManager` 是安卓系统里一个**常驻系统服务**(跑在 `system_server` 进程里),职责类似 Linux 发行版的 `dpkg`/`rpm` 数据库 + 一部分 `apt` 的安装逻辑：记录"手机上装了哪些包、每个包的签名是什么、权限是什么"。你的 App 想问"我自己的签名是什么",不是自己去读文件,而是**发一次 IPC(跨进程调用,类似给一个常驻 daemon 发 D-Bus/gRPC 请求)问系统服务**——这是保姆级要点之一：**App 读到的"我的签名"默认不是自己现读的,而是系统服务缓存好告诉它的**,这个"中间人"角色后面会成为攻防焦点。

### 1.2 装包这一刻,系统查了什么

当你 `adb install xxx.apk` 或者点"安装"时,`PackageManager`(具体走 `PackageInstaller` → `ApkSignatureVerifier` 等内部组件)会做：

1. **签名格式合法性**:APK 里的 v1(JAR 签名)/v2/v3 签名块结构必须能被正确解析、证书链能验签(证书本身的数字签名是自洽的——即"证书没有被搬运时改坏字节"),否则**直接装不上**,报 `INSTALL_PARSE_FAILED_NO_CERTIFICATES` 之类的错误。
2. **签名与内容一致性**:v2/v3 校验的是"整个 APK 的字节(除签名块自身)都被这份签名覆盖",任何人改一个字节(哪怕只改一个资源文件)而不重新签名,这一步就会失败——这也是为什么"改包"必然要"重签",前一篇讲的核心逻辑。
3. **同包名一致性(签名锁定)**：如果手机上**已经装了**一个包名叫 `com.mt.mtadmin` 的 App,现在你要装另一个也叫这个包名、但证书不同的 APK,系统会**拒绝安装**(报 `INSTALL_FAILED_UPDATE_INCOMPATIBLE`),必须先卸载旧的才能装新的。这条规则的本意是防止"李鬼冒充李逵覆盖升级、窃取原 App 的数据和权限"——类比 SSH 的 `known_hosts` "这个 IP 之前的公钥变了,拒绝连接"提示,只不过安卓这里是**装包时强制拒绝**,不是提示后自己选。

### 1.3 关键认知：这一层从来不检查"是不是官方"

**这是最容易被误解的一点**：系统安装校验**只保证自洽性和一致性,完全不关心证书是谁签的**。你用 `keytool`/`apksigner` 生成一个全新的自签名证书(哪怕证书主题写"Mickey Mouse"),用它给任意 APK 签名,系统照样能装——因为安卓的信任模型不是"CA 体系"(不像 HTTPS 证书需要被根 CA 链认可),而是**"自签名 + 首次见面即信任(TOFU, Trust On First Use)+ 之后必须保持一致"**。

所以：**改包重签后,系统安装校验这一层永远能通过**(只要重新签好、卸载旧包再装新包)。真正会拦下"这不是原厂 App"的,是第二层——App 自己写的代码。这也是为什么报告和后续教程通篇讲的都是第二层的攻防,第一层几乎不构成防线。

## 2. 第二层：应用自校验 / 防篡改(代码层)

这一层的本质：**App 启动后,自己去问系统"我当前的签名证书是什么",跟写死在代码里的"官方证书指纹"做比较,不一致就认为"我被改过了"**,然后可以选择：退出、报错、悄悄阉割功能、上报服务器。这是开发者**主动加的自保护**,系统不会替你写。

### 2.1 老 API:`getPackageInfo(GET_SIGNATURES)`

最经典、最古老的写法(API 28 之前,现已标记 deprecated 但仍能用):

```java
// 问 PackageManager:"把我自己包的签名信息给我"
PackageInfo info = getPackageManager()
        .getPackageInfo(getPackageName(), PackageManager.GET_SIGNATURES);
Signature[] sigs = info.signatures;   // 通常只有 1 个元素:当前签名证书
```

- `GET_SIGNATURES`：一个查询标志位(flag),告诉 `PackageManager` "把签名字段也一起填进返回结构体",类比 SQL 里 `SELECT *` 还是只 `SELECT cert_field`——不传这个 flag,返回的 `PackageInfo.signatures` 默认是空的,省一次不必要的数据搬运。
- `Signature`：一个包装类,内部就是**证书的 DER 编码原始字节**(`byte[]`)。它重写了 `equals()`/`hashCode()`,语义上就是"按字节比较两份证书是否完全相同"。
- 拿到 `Signature` 之后,开发者一般不会存整个证书字节(太大、比较慢),而是算一次 **SHA-256 摘要(digest/指纹)**,跟硬编码在代码里的官方指纹字符串比对：

```java
String officialFingerprint = "3A:F4:...(官方证书的 SHA-256 指纹,写死在代码里)";
String actualFingerprint = sha256Hex(sigs[0].toByteArray());
if (!officialFingerprint.equalsIgnoreCase(actualFingerprint)) {
    // 签名不符 —— 可能是被改包、被重签、被二次打包
    System.exit(0);   // 或者:上报服务器 / 悄悄跳过高级功能 / 弹窗
}
```

> **为什么改包重签之后一定会跑到这个 `if` 分支?**
> 因为改包者**拿不到官方的私钥**(私钥从来不在 APK 里,是开发者电脑上/CI 密钥库里的秘密),只能用自己生成的证书重签。重签之后 `actualFingerprint` 必然是"改包者自己的指纹",跟硬编码的官方指纹对不上,`if` 恒真,程序退出——**这就是"改包必崩"的根本原因,也是整个第 11 篇"签名校验绕过"要解决的唯一问题**。

### 2.2 `checkSignatures`：比较"两个包"是不是同一伙的

```java
int result = getPackageManager().checkSignatures(pkgA, pkgB);
// 或按 uid 比较:checkSignatures(uidA, uidB)
```

这个 API 常见场景不是"防篡改"本身,而是**判断两个不同包名的 App 是不是同一个开发者发的**(用于共享 `UID`、共享数据、互相授权组件访问)——类比后端里"两个微服务是不是持有同一张受信的 mTLS 证书,可以互相调用内部 API"。返回值 `SIGNATURE_MATCH_EXACT`(完全一致)/`SIGNATURE_MATCH_COMPATIBLE`(经过合法轮换后仍兼容,见下)/`SIGNATURE_NO_MATCH` 等。防篡改场景里,它常被用来做"我 vs 官方包名"的比较变体,原理跟 §2.1 一致。

### 2.3 新 API(Android 9 / API 28 起):`signingInfo` + `SigningInfo`

`GET_SIGNATURES` 从 API 28 起标记为 deprecated,原因是它**只能表达"单证书"这一种简单情况**,没法表达 v3 引入的"**证书轮换(key rotation)**"——即一个 App 生命周期里,官方可能因为老密钥泄露/丢失,用新证书重签并保留"我曾经用过旧证书"的**血统链(lineage)**(详见上一篇 05 的 v3 部分)。新 API 用一个专门的 `SigningInfo` 对象表达这种复杂情况：

```java
PackageInfo info = getPackageManager()
        .getPackageInfo(getPackageName(), PackageManager.GET_SIGNING_CERTIFICATES);
SigningInfo signingInfo = info.signingInfo;

if (signingInfo.hasMultipleSigners()) {
    // 场景一:APK 由多个"互相独立、同时生效"的证书联合签名(不常见,罕见的多签名场景)
    Signature[] currentSigners = signingInfo.getApkContentsSigners();
    // 直接比对"当前生效的全部签名者"
} else {
    // 场景二(绝大多数 App 走这条路):单一签名者,但可能经历过 v3 证书轮换
    Signature[] history = signingInfo.getSigningCertificateHistory();
    // history[0] = 最初始的证书,history[history.length-1] = 当前正在用的证书
    Signature current = history[history.length - 1];
    // 拿 current 去跟硬编码指纹比对
}
```

- `GET_SIGNING_CERTIFICATES`：新 flag,取代旧的 `GET_SIGNATURES`。
- `hasMultipleSigners()`：区分"多签名者"(罕见)和"单签名者+可能轮换过"(常见)两条分支——这是官方文档明确要求的用法,选错分支会导致判断逻辑出错。
- `getApkContentsSigners()`：只在多签名者场景下用,返回"当前签这份 APK 内容的证书"(不含历史)。
- `getSigningCertificateHistory()`：返回"从最初到现在的整条证书链",专门为兼容 v3 轮换设计——类比 Git 的 `git log --follow` 能追踪一个文件改名前的历史,只不过这里追踪的是"这个包换过几次签名证书"。

**保姆级小结**：不管用老 API 还是新 API,防篡改的核心动作永远是同一件事——**拿到"我当前实际的签名证书指纹" vs "写死在代码里的官方指纹",不一致就报警**。新 API 只是把"证书可能会轮换"这件事考虑得更周全,并没有改变攻防的本质。

### 2.4 这一层的"命门"：它依赖 PackageManager 这个"中间人"

回到 §1.1 提到的关键点：`getPackageInfo`/`signingInfo` 都是**问系统服务要答案**,而不是 App 自己去读 APK 文件字节算出来的。这就意味着——**只要能让这次 IPC 调用返回一份"伪造的、内容是官方指纹"的假数据,App 自己完全没办法分辨真假**,因为它压根没有另一条独立的验证路径。

这正是报告里 `KillerApplication`(源自开源 `ApkSignatureKillerEx`)的原理：用 Java 反射(§见 [03-ART运行时](03-ART运行时-类加载与反射与JNI.md))把 `PackageInfo.CREATOR`(一个负责"从 IPC 传回的 Parcel 里反序列化出 `PackageInfo` 对象"的工厂对象,类比 protobuf 的反序列化回调)偷偷替换成一个假的 `CREATOR`,让每一次反序列化都"顺手"把 `signatures`/`signingInfo` 字段改写成官方指纹——这样不管 App 代码里怎么调用 `getPackageInfo`,拿到的永远是"看起来没问题"的假答案。这部分绕过手法的完整拆解见 [11-签名校验绕过全景.md](11-签名校验绕过全景.md) 和深度专文 [../安全审计-MT一键过签名校验-机制逆向与正向实现路径.md](../安全审计-MT一键过签名校验-机制逆向与正向实现路径.md)。

## 3. 更强的自校验：native 层自己读 APK 字节解析签名块

聪明的开发者会意识到 §2.4 的命门,于是升级思路：**别再问 PackageManager 这个"可能被污染的中间人",我自己直接打开自己的 APK 文件,按字节手工解析 v2/v3 签名块,自己验证签名**。

### 3.1 怎么做到

- v2/v3 签名块(APK Signing Block)是插在 ZIP 的 Central Directory 之前的一段特殊区域,有固定的**魔数(magic)**字符串 `"APK Sig Block 42"` 作为结尾标识,格式在 AOSP 里是公开文档化的(上一篇 05 已详细讲过结构)。
- native 代码(C/C++,跑在 `.so` 里,类比你熟悉的直接读 ELF 文件字节做自定义校验)自己 `open()`/`mmap()` 这个 APK 文件,定位到签名块,按格式手动解析出证书,再用密码学库(如 BoringSSL/OpenSSL)验证签名和证书指纹。
- 这样一来,**校验完全不经过 PackageManager 这一层**,`KillerApplication` 那种"污染 IPC 返回值"的反射手法**对它完全无效**——因为 native 代码根本没调用那个被污染的 Java API。

### 3.2 类比

这就像你不再相信 `whoami`/`id` 命令的输出(可能被 `LD_PRELOAD` 劫持了 libc 的 `getpwuid`),而是自己写代码直接去读 `/etc/passwd` 原始字节解析——绕开了所有"中间层可能被污染"的风险,**但代价是"读文件"这个动作本身还是可能被拦截**(见下)。

### 3.3 这一层怎么被绕：`killOpen`(hook `open`/`openat`)

道高一尺魔高一丈——既然 native 层也是"打开文件读字节",那就在**更底层的系统调用入口**动手脚：用 inline hook 或 PLT/GOT hook(类比你熟悉的"改写 PLT 表项做函数劫持"、`LD_PRELOAD` 覆盖 libc 符号、Linux 下的 detour 技术)劫持 `open`/`openat`/`openat64` 这几个 libc 函数,**当检测到有人在读"当前正在运行的这个 APK 自身"时,悄悄把文件句柄重定向到一份内嵌在改包体积里的"干净原版 APK"**——native 层代码以为自己读的是"当前正在跑的(已被改过的)APK",实际上读到的字节全部来自另一份干净的原版文件,算出来的签名自然是"正确"的。报告里管这个手法叫 `killOpen`,通常和 `killPM`(即 §2.4 的反射污染)配套使用,一静一动、覆盖 Java 层和 native 层两条校验路径。完整攻防细节见 [11-签名校验绕过全景.md](11-签名校验绕过全景.md)。

**注意边界**:`killOpen` 挡的是"native 层自己重新读文件字节"这一种校验方式;它**不能**让"Play Integrity 硬件背书"(见下一节)也被绕过——因为下一层根本不依赖读本地文件。

## 4. 更强的远程认证：Play Integrity(前身 SafetyNet)

前面两层的共同弱点是：**判断逻辑始终跑在用户手机上、在攻击者完全可控的环境里**——无论 Java 层还是 native 层,理论上攻击者拥有 root/hook 能力时总能干预。要彻底摆脱"本地判断不可信"这个死结,只能**把"背书"这件事交给硬件 + 服务器**。

### 4.1 SafetyNet Attestation API：已经退役

历史上安卓提供过 `SafetyNet Attestation API`,让 App 发起一次"设备完整性认证"请求,Google 服务端结合设备的软硬件状态返回一个签名过的"判定书(verdict)"。**这个 API 已经完全下线**:Google 于 2023-01-31 停止接受新接入,2024 年逐步限流,**2025-01-31 正式全面关停**,现在调用会直接收到错误响应。旧文档/旧代码里看到 `SafetyNet` 字样,一律理解为"历史遗留,现在已被 Play Integrity API 取代"。

### 4.2 Play Integrity API：现役的远程认证方案

Google 在 2021 年发布 `Play Integrity API`,把 SafetyNet 的"设备完整性判定"能力整合并强化,现在是安卓生态**官方推荐**的远程认证手段。核心流程：

```
  App                    Google Play 服务(设备本地组件)         App 自己的后端服务器
   │                              │                                    │
   │ 1. 生成一次性 nonce          │                                    │
   │    (防重放,类似挑战-应答)    │                                    │
   │─ 请求完整性判定 (带 nonce) ─▶│                                    │
   │                              │  2. 结合硬件安全模块(TEE/StrongBox,│
   │                              │     类比 TPM 远程证明)、Play Store │
   │                              │     发行记录、APK 证书等,生成      │
   │                              │     一份 JWS(带数字签名的 JSON)    │
   │                              │     "判定书 verdict"               │
   │◀──────── 3. 返回签过名的 verdict token ───────────────────────────│
   │                                                                   │
   │───────── 4. 把 token 原样转发给自己的后端服务器 ─────────────────▶│
   │                                                                   │  5. 后端用 Google
   │                                                                   │  公钥验证 token 签名,
   │                                                                   │  读出其中的判定结果
```

judgment(判定)内容大致包含三类维度(具体字段以 Google 官方文档为准,这里只讲原理不逐字段展开):
- **App 完整性**：当前这份 APK 的签名证书 / 包名 / 是否来自 Play Store 正规发行渠道,是否与开发者在 Play Console 登记的一致。
- **设备完整性**：这台设备是否是"未 root、Bootloader 锁定、通过 Google 官方兼容性认证(CTS)"的正规设备。
- **账号相关**：发起请求的 Google 账号是否被 Play 判定为可信(反刷量/反女号)。

### 4.3 为什么这一层"硬"很多

关键差异在于：**判定逻辑根本不在"可被攻击者完全掌控的手机本地代码"里跑**,而是：
1. 依赖**硬件级安全模块**(如 ARM TrustZone 提供的 TEE、部分设备的 StrongBox 安全芯片)做**密钥证明(key attestation)**——密钥在硬件里生成、不可导出,硬件本身能证明"这把密钥没有被软件层篡改过",这是纯软件 hook 很难伪造的信任根;
2. 返回的 verdict token 是**用 Google 私钥签名**的 JWS,`App 自己的后端服务器`验证签名要用 Google 的公钥——攻击者要伪造一份"通过认证"的 token,等于要伪造 Google 私钥签的名,这在密码学意义上不可行;
3. 真正的决策点被推到了**开发者自己的后端服务器**上(第 4 步、第 5 步),而不是本地某个 `if` 分支——这跟《加固实施清单》里反复强调的"权益裁决上移服务端 + 结果参与解密"是同一个思路(详见 [../安全审计-加固实施清单-把App推进C档.md](../安全审计-加固实施清单-把App推进C档.md))。

### 4.4 局限性(保姆级也得讲清楚"不是银弹")

- **依赖 Google 移动服务(GMS)**：国内大量安卓设备(华为/小米/OPPO/vivo 等本地渠道机型)**没有装 GMS**,压根调不通 Play Integrity;国内场景通常要换成"厂商自己的完整性服务"(如华为 Safety Detect)或自建的"设备指纹 + 行为异常检测"。**拿不到 Play Integrity 结果 ≠ 完整性一定失败**,盲目 fail-closed 会误伤正常用户。
2. **服务端如果偷懒不验证 token 签名、只看 App 本地传来的一个 boolean**,那这层"硬件背书"就形同虚设——本系列反复强调的一条铁律：**"挪到服务端"如果最后仍收敛成一个可被绕过的本地布尔判断,那这道防线就没意义**。真正有效的是"后端拿到 token → 验证签名 → 判定结果参与解密/下发内容"这条完整链路。
3. root 隐藏工具(如 Magisk 的部分模块)长期在打"如何让 Play Integrity 判定通不出问题"这场攻防拉锯战,目前对普通用户设备的 CTS/硬件证明这一路,攻击面明显比前两层小很多,但**"很难"不等于"绝对不可能"**——安全永远是概率/成本博弈,不是非黑即白的开关。

## 5. 汇总：哪层防哪层、什么手段绕得动 / 绕不动

| 层级 | 校验发生在哪 | 判断依据 | 能被什么绕过 | 绕不动什么 |
|---|---|---|---|---|
| ① 系统安装校验(PackageManager 装包时) | 系统服务,装包那一刻 | 签名格式自洽 + 内容完整 + 同包名证书一致 | 天然不设防"是不是官方",改包重签+先卸载旧包即可通过 | 单纯改字节不重签(格式会直接坏掉,装不上) |
| ② Java 层自校验(`getPackageInfo`/`checkSignatures`/`signingInfo`) | App 代码,运行时随时查 | 问 PackageManager 要"我的签名",跟硬编码指纹比对 | 反射污染 `PackageInfo.CREATOR`(`killPM`)、Xposed/LSPosed/Frida 直接 hook 该 API 返回值、静态 patch 把比较逻辑改恒真 | 不依赖 PackageManager 的独立校验路径(见③) |
| ③ native 自读 APK 字节解析签名块 | App 的 `.so`,运行时自己读文件 | 自己 `open`/`mmap` APK 文件,手工解析 v2/v3 签名块验证 | inline/PLT hook `open`/`openat`(`killOpen`)把读取重定向到内嵌的干净原版 | 单纯的 Java 反射污染(它压根没经过 Java API) |
| ④ Play Integrity 远程认证 | Google 服务端 + 硬件安全模块 + App 自己后端 | 硬件 key attestation + Google 私钥签名的 verdict token,后端验签 | root 隐藏 + 高阶反检测(门槛高、拉锯战持续)、**开发者自己没做好服务端验证这一步**(实现缺陷,非机制被破) | 纯软件层的 hook/反射/静态 patch(判断根不在本地) |

**给 C++ 工程师的一句话总结**：①-④ 是一条**信任根不断上移**的链条——从"系统只管格式一致"→"App 自己代码里问一个可能被污染的中间人"→"App 自己直接读文件但读文件动作可能被系统调用层拦截"→"把信任根交给你完全不可控的硬件+服务端"。**越往上越难绕,但代价是接入成本和平台依赖也越高**,这也是为什么现实中的强力商用 App 通常是①②③④叠加使用,而不是只依赖一层。

## 一页速记

- **两层校验、职责完全不同**：系统安装校验管"格式对不对、前后一不一致",从不管"是不是官方"——改包重签永远能骗过这一层。真正的关卡是应用自校验。
- **应用自校验的本质**：拿"当前实际签名指纹"跟"硬编码的官方指纹"比对,`getPackageInfo(GET_SIGNATURES)`(老,API28 前)/`signingInfo`(新,`SigningInfo` 类,`hasMultipleSigners()`/`getApkContentsSigners()`/`getSigningCertificateHistory()`)殊途同归。
- **改包为什么必崩**：改包者没有官方私钥,重签后指纹必然对不上,`if` 分支恒真触发退出——这是第 11 篇整章绕过手法要解决的唯一问题。
- **Java 层的命门**：它靠问 `PackageManager` 这个中间人,`killPM`(反射污染 `PackageInfo.CREATOR`)能让它拿到假答案而不自知。
- **native 层更硬但也有软肋**：自己读 APK 字节解析 v2/v3 签名块能绕开"污染 Java API"这招,但读文件这个动作本身能被 `killOpen`(hook `open`/`openat`)重定向到内嵌的干净原版。
- **Play Integrity(SafetyNet 已于 2025-01-31 全面退役)是当前最硬的一层**：判断根在硬件安全模块 + Google 服务端签名的 verdict token,纯本地 hook 难以撼动,但依赖 GMS(国内大量设备没有)、且如果开发者自己的后端偷懒不验证 token 签名,这层照样形同虚设。
- **防御的正确姿势不是"选一层",而是叠加 + 结果参与解密 + 绑定服务端新鲜值**——单点校验(不管哪一层)都只是"拖延战术"。
