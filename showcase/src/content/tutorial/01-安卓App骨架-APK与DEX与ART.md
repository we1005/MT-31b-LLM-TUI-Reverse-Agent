# 安卓 App 的骨架:APK、DEX、ART

> 一句话点题:一个安卓 App 从"源码"到"跑起来",要经过「Java/Kotlin → DEX 字节码 → ART 虚拟机执行(或 AOT 编译成机器码)」这条链路——**这条链路比 C++ 的"源码→机器码"多留了一层"还原度极高的中间表示"**,这正是安卓比 native 二进制"好逆"的根本原因,也是本教程接下来一切攻防话题的地基。

读者背景假设:你懂 C/C++、链接器、ELF、汇编、指针、系统调用,但没碰过安卓开发,没听过 Dalvik/ART/DEX 这些词。这篇就是把这些词一次性钉死。

---

## 0. 先建立坐标系:你熟悉的链路 vs 安卓的链路

你熟悉的 C++ 世界:

```
foo.cpp  --(gcc/clang 编译)-->  foo.o (目标文件,机器码)
                                    |
                              (ld 链接器)
                                    v
                              a.out / foo.so   ← ELF 格式,CPU 直接执行
```

一旦编译完成,**类型名、变量名、大部分控制结构信息都被扔掉了**——你反汇编 `a.out` 看到的是裸的 `mov/call/jmp`,IDA/Ghidra 得靠模式识别、符号表(如果没被 strip)去猜"这堆汇编原来是个什么函数"。这就是为什么 native 逆向门槛高。

安卓世界(以 Java/Kotlin 写的 App 为例):

```
Foo.java / Foo.kt --(javac / kotlinc 编译)--> Foo.class   ← JVM 字节码,不是机器码!
                                                   |
                                            (d8/r8 编译器)
                                                   v
                                            classes.dex    ← Dalvik 字节码,还不是机器码!
                                                   |
                              ┌────────────────────┴────────────────────┐
                              v                                          v
                     手机上跑的时候:                              安装/首次运行时:
                  ART 虚拟机边解释边 JIT              dex2oat 提前编译成 .oat(内含机器码)
```

**关键区别**:C++ 编译产物 `a.out` 直接就是机器码;安卓的 `classes.dex` **不是机器码**,它是一种给"虚拟机"读的中间表示,类似 JVM 字节码、.NET 的 IL(Intermediate Language,中间语言)。机器码要等到 ART 虚拟机运行时(解释/JIT)或者安装时(AOT,后面细讲)才生成,而且**即使生成了机器码,逆向工具通常还是选择直接分析 DEX**,因为 DEX 里保留的信息量比机器码大得多——这是本篇要讲透的核心因果链。

## 1. APK 是什么:说白了就是个 ZIP

**APK**(Android Package,安卓应用包)本质上就是一个 **ZIP 压缩包**,只是后缀名改成了 `.apk`。不信你可以直接把一个 `xxx.apk` 复制一份改名成 `xxx.zip`,双击就能用普通解压软件打开——这跟 Java 的 `.jar`(也是 ZIP)、Office 的 `.docx`(也是 ZIP)是一个套路,都是"用 ZIP 当容器格式,里面塞一堆结构化文件"。

解压一个典型 APK,你会看到:

```
MyApp.apk  (本质是个 ZIP)
├── AndroidManifest.xml     ← 二进制格式的"清单文件"(应用元数据,见下方解释)
├── classes.dex             ← 第 1 个 DEX 文件(编译后的代码,本文重点)
├── classes2.dex            ← 如果方法数超过 6.4 万,会拆成多个 dex(见 §3.4)
├── classes3.dex
├── resources.arsc          ← 二进制"资源表"(字符串/图片/布局等资源的索引,04篇细讲)
├── res/                    ← 具体的资源文件(图标 png、布局 xml 编译后的二进制等)
│   ├── drawable-xxhdpi/icon.png
│   └── layout/activity_main.xml   ← 已被编译成二进制 XML(AXML,04篇细讲)
├── assets/                 ← 原样打包、不经过编译的自由格式文件(你想塞什么塞什么,常见:
│                              配置 json、字体、小的数据库文件、有时候是加密后的"第二个 dex")
├── lib/                    ← native 动态库,按 CPU 架构分文件夹
│   ├── arm64-v8a/libfoo.so     ← 真正的机器码!就是你熟悉的 ELF 共享库
│   ├── armeabi-v7a/libfoo.so
│   └── x86_64/libfoo.so
└── META-INF/                ← 签名相关文件(05篇细讲 v1/v2/v3/v4 签名方案)
    ├── MANIFEST.MF          ← 每个文件的摘要清单(类似 sha256sum 的列表)
    ├── CERT.SF              ← 对 MANIFEST.MF 的签名描述文件
    └── CERT.RSA / CERT.DSA  ← 实际的签名值 + 证书(公钥)
```

逐项对应你熟悉的概念:

| APK 里的东西 | 是什么 | 你熟悉的类比 |
|---|---|---|
| `AndroidManifest.xml` | 声明这个 App 叫什么名字、需要哪些权限、有哪些界面(Activity)/后台服务(Service)、入口点是谁 | 有点像 ELF 的 `.dynamic` 段 + `/etc/systemd/xxx.service` 单元文件的合体——"这个程序是谁、怎么启动、需要什么权限" |
| `classes*.dex` | 编译后的**应用代码**,本文主角 | 对标你的 `.o`/`a.out`,但它是"字节码"不是机器码 |
| `resources.arsc` | 资源名字(比如 `R.string.app_name`)到实际内容的索引表 | 有点像一个专用的"资源打包 + 符号表"系统 |
| `lib/*.so` | native 代码,**真正的机器码**,ARM/x86 的 ELF 文件 | 就是你天天打交道的 `.so`,一模一样的格式 |
| `META-INF/` | App 完整性签名信息 | 类似给整个压缩包做了个"代码签名"(Authenticode/GPG 签发布物的思路) |
| `assets/` `res/` | 图片、布局、字符串等资源 | 前端打包里的 "public/ 静态资源" |

**为什么这个"ZIP 里装什么"很重要?** 因为逆向分析安卓 App 的第一步永远是"解压这个 ZIP,分门别类地看每一块"——`classes.dex` 归静态分析工具管(07篇),`lib/*.so` 归 IDA/Ghidra 管,`AndroidManifest.xml`/`resources.arsc` 得先解出人类可读格式才能看(04篇),`META-INF/` 归签名分析管(05/06篇)。后面报告里提到的"这个 APK 有没有加壳""签名对不对""有没有 native 化",本质都是在问"这个 ZIP 里的某一块文件长什么样"。

## 2. 代码怎么变成 DEX:编译链全貌

先看整条编译链,再逐段拆解:

```
   Foo.java              Foo.kt
      |                    |
   javac 编译           kotlinc 编译
      |                    |
      v                    v
   Foo.class            Foo.class      ← 都是 JVM 字节码格式(.class),Kotlin 编译器直接产出跟
      \                    /              Java 编译器一样格式的 .class,这是 Kotlin 能无缝
       \                  /               和 Java 互操作的关键
        \                /
         v              v
      ┌──────────────────────┐
      │   d8 / r8 编译器      │  ← Google 官方工具:把一堆 .class 文件"翻译+合并"成 dex
      │ (老工具链叫 dx,已弃用) │     字节码,同时做混淆/压缩(R8 = d8 + ProGuard 规则的合体,09篇细讲)
      └──────────────────────┘
                 |
                 v
          classes.dex (们)
```

**术语打卡**(第一次出现,当场解释完):

- **javac**:JDK 自带的 Java 源码编译器,`.java` → `.class`。类比你的 `g++ -c foo.cpp -o foo.o`,只不过产物不是机器码而是 JVM 字节码。
- **kotlinc**:Kotlin 语言的编译器。Kotlin 是安卓官方现在更推荐的语言(语法更现代,类似 Rust/Swift 那味儿,但设计上刻意贴近 Java 好互操作),编译产物同样是 `.class`,所以 Kotlin 代码和 Java 代码在字节码层面是"平等公民",逆向的时候你会同时见到反编译出的"类 Java 风格代码"和"类 Kotlin 风格代码",工具链不区分对待。
- **`.class` 文件 / JVM 字节码**:Java 虚拟机(JVM,Java Virtual Machine)执行的中间格式,是一种**栈式**(stack-based)虚拟机指令集——每条指令从一个操作数栈上 push/pop 数据,类似"逆波兰计算器"的执行模型。
- **d8 / r8**:Google 官方提供的"DEX 编译器"。它读入一堆 `.class` 文件(可能来自你的代码,也可能来自你依赖的第三方库),把里面的**栈式**字节码转换、合并成 DEX 用的**寄存器式**字节码(下一节细讲这个区别),同时可选地做压缩混淆。历史上先有 `dx`(老工具),后来 Google 用 `d8`(编译)+ `r8`(编译+混淆压缩合体)取代了它,现在 Android Studio 默认走 r8。
- **dex**:Dalvik Executable 的缩写,即"Dalvik 可执行文件"——这就是本文接下来的主角。

对比一下 C++ 的编译链你会发现:C++ 是"源码 → 直接到机器码",安卓是"源码 → 先到一种字节码(.class)→ 再转换合并成另一种字节码(dex)"。**中间多转了一道**,但两道都还是字节码,都不是机器码——这是理解安卓逆向"为什么好还原"的第一把钥匙。

## 3. DEX 到底是什么

### 3.1 DEX = Dalvik 可执行文件,寄存器式字节码

DEX 是 **Dalvik**(安卓最早的虚拟机名字,§4 细讲)专用的可执行格式。它和 JVM 字节码(`.class`)的核心区别:

| | JVM 字节码(.class) | Dalvik 字节码(dex) |
|---|---|---|
| 执行模型 | **栈式**(stack-based):指令操作一个虚拟操作数栈 | **寄存器式**(register-based):指令直接操作一组"虚拟寄存器"(不是真 CPU 寄存器,是虚拟机模拟出来的一堆槽位) |
| 一个简单加法 `a+b` 大概长这样 | `iload a; iload b; iadd; istore c`(先压栈两次,再加,再弹出存) | `add-int c, a, b`(一条指令直接说清楚"结果放哪、两个操作数是谁") |
| 指令数量/体积 | 指令更"碎",但单条更短 | 指令更"粗",单条信息量更大,总指令数更少,体积通常更小、执行更快 |

为什么安卓选寄存器式?因为手机是资源受限设备(尤其是早期功能机时代),Google 想要更少的指令数、更少的内存搬运。你可以把这类比成"CISC vs RISC"的取舍,但注意这里两边都是**虚拟机指令**,不是真实 CPU 指令集——不要和 x86(CISC)/ARM(RISC)的真实硬件区别搞混。

多个 `.class` 文件会被合并进**一个** DEX 文件(这也是为什么叫"dex"而不是"多个 class 打包"——d8/r8 做的是真正的格式转换+合并,不是简单拼接)。

### 3.2 DEX 文件内部长什么样(简化版)

一个 DEX 文件大致分这几块:

```
classes.dex
├── header                     ← 魔数 "dex\n035\0" 之类、文件大小、各表偏移量
├── string_ids[]               ← 全局字符串常量池(类名、方法名、字面量字符串全在这)
├── type_ids[]                 ← 类型(类/接口/基本类型)表,指向 string_ids
├── proto_ids[]                ← 方法"原型"(参数类型+返回类型的组合)
├── field_ids[]                ← 字段引用表(哪个类的哪个字段,什么类型)
├── method_ids[]                ← 方法引用表(哪个类的哪个方法,什么签名)——64K 限制打的就是这张表
├── class_defs[]                ← 每个类的定义:父类是谁、实现了哪些接口、有哪些方法/字段
└── data                         ← 实际的方法字节码(code_item,含每条 opcode)、注解、调试信息等
```

**这张表结构本身就在替你做逆向工程的一半工作**——`string_ids` 里明晃晃地写着每一个类名、方法名、字符串字面量(除非被混淆);`method_ids`/`field_ids` 精确记录了"谁调用了谁的哪个方法、传了什么类型的参数"。这些信息在 C++ 编译成机器码之后基本**全部丢失**(除非你没 strip 符号表),但 DEX 格式里天然、完整地保留着——这不是逆向工具"猜"出来的,是**编译器为了让虚拟机能正确执行,不得不老老实实写进文件里的**。这正是"DEX 还原度极高"的技术根因,02篇会继续深入到具体的 opcode 和 smali(DEX 的"汇编语言")。

### 3.3 一个直观例子

假设你写了这么一段 Java:

```java
public int add(int a, int b) {
    return a + b;
}
```

反编译工具(比如 jadx,07篇细讲)读取 DEX 之后,基本能**逐字还原**成:

```java
public int add(int a, int b) {
    return a + b;
}
```

——方法名 `add`、参数名(如果保留了调试信息)、参数类型 `int`、返回类型 `int`、逻辑 `a+b` 几乎原样重现。而如果你把同样逻辑的 C++ 函数编译成 ARM64 机器码丢给 IDA,你得到的是一串 `add w0, w0, w1; ret` 这样的汇编,函数名可能已经变成 `_Z3addii` 或者干脆被 strip 掉,IDA 需要你自己重新起名、猜类型。

**这就是本教程反复强调的核心事实**:安卓 App 之所以"比 native 程序好逆",根本不是因为工具多厉害,而是因为 **DEX 这种格式本身就是为"给虚拟机解释执行"设计的,天然携带大量高层语义**(类名、方法签名、字符串常量、控制流结构)。后面报告里讲的"加固""Dex2C""VMP"这些攻击者的对抗手段,本质上都是在**想办法把这些语义信息从 DEX 里挖掉、藏起来**——理解了这一节,后面每一种"防逆向手段"你都能一眼看穿它的动机。

### 3.4 64K 方法数限制与 multidex

DEX 格式里 `method_ids` 这张表用 **16 位**(2 字节)整数做索引——16 位能表示的最大数量就是 2^16 = 65536,这就是业界常说的"**64K 方法数限制**"(64K 里的 "K" 指 1024,65536 = 64×1024)。一个 App 一旦所有方法引用(包括你自己写的 + 所有依赖库的)总数超过 65536 个,单个 DEX 文件就装不下了。

解决办法是 **multidex**(多 dex):把代码拆成 `classes.dex`、`classes2.dex`、`classes3.dex`……多个文件,每个文件各自不超过 64K 方法引用。这也是为什么你解压大型 App 的 APK 经常能看到好几个 `classes*.dex`。类比一下:有点像大型 C++ 项目拆分成多个 `.so` 是为了控制单个二进制体积/编译时间,但 multidex 纯粹是**格式的数值限制**逼出来的,不是设计选择。

## 4. 虚拟机是谁在跑:Dalvik 与 ART

DEX 字节码不能被 CPU 直接执行,必须有一个"虚拟机"来解释/编译执行它——这就是 **Dalvik** 和 **ART** 干的事。

- **Dalvik**:安卓最早(2008 年发布,到 Android 4.4 KitKat 为止是默认运行时)的虚拟机,以**解释执行**为主(边读字节码边翻译成动作执行,类似 Python 解释器跑 `.pyc`),后期加入了有限的 JIT(见下节)。
- **ART**(Android RunTime):从 Android 5.0(Lollipop, 2014 年)开始成为默认运行时,取代了 Dalvik。ART 一开始主打纯 **AOT**(Ahead-Of-Time,提前编译,见下节),后来在 Android 7.0(Nougat)又演化成"AOT + JIT + 解释器"混合模式(见下节),这个混合模型延续至今(包括你手上的 Android 14/15 设备)。

**类比你熟悉的东西**:Dalvik/ART 之于 DEX,就像 **JVM 之于 `.class`**——都是"托管运行时"(managed runtime):

- **托管**(managed)的意思是:内存分配/回收不用你手动 `malloc`/`free`,由虚拟机自带的 **GC(Garbage Collector,垃圾回收器)** 自动管理。你写 Java/Kotlin 代码时基本不用管内存释放,ART 的 GC 会在后台扫描"还有没有人引用这块内存",没人引用就自动收走。
- 与之相对,你的 C++/.so 代码是"非托管"的——`new`/`delete`、`malloc`/`free` 全靠你自己,ART 的 GC 完全不管这部分。这也是为什么"把逻辑塞进 .so"之后,内存管理复杂度会转嫁回开发者自己身上(§7 还会再提这一点)。

一句话记忆:**ART/Dalvik 相当于安卓世界的 JVM**——都是"读字节码、管内存、提供反射/异常处理等运行时服务"的托管虚拟机,只是 JVM 读 `.class`(栈式字节码),ART/Dalvik 读 `dex`(寄存器式字节码)。ART 运行时更深的机制(类加载、反射、JNI 边界)留到 03 篇细讲。

## 5. AOT 与 JIT:字节码到底何时变成机器码

DEX 字节码最终还是要在真实 CPU 上跑,所以必然存在"字节码 → 机器码"的转换,只是**时机**不同。安卓这些年的做法演变、也是现在的实际状态(2026年主流机型):

- **AOT(Ahead-Of-Time,提前编译)**:在 App **安装时或空闲时**,由系统工具 **`dex2oat`** 把 DEX 编译成机器码,产物是 **`.oat`** 文件(内嵌了机器码 + 一些元数据),运行时可以直接跑 `.oat` 里的机器码,不用每次都重新解释。这就像你在部署 C++ 服务前先 `g++` 编译好,而不是每次请求来了才现场解释源码——**换取的是启动更快、执行更快,代价是安装/更新时要多花时间编译、多占一些磁盘空间**。
- **JIT(Just-In-Time,即时编译)**:程序**运行过程中**,虚拟机一边解释执行字节码,一边监控"哪些方法被频繁调用"("热点方法"),对这些热点方法现场编译成机器码、换上去跑,下次调用直接执行编译好的机器码,不用再解释了。这就像 Python 里的 PyPy、JVM 里大家更熟悉的 HotSpot JIT。
- **解释执行(Interpreter)**:最朴素的方式,虚拟机逐条读字节码、逐条翻译成动作执行,不生成机器码,启动最快但单条指令执行开销最大。

现代 ART(Android 7.0 之后,包括现在)是**三者混合**:
1. App 装上,系统用**云端 profile**(如果 App 商店提供,通常打包在一个 `.dm` 文件里,内含"哪些方法在典型使用场景下是热点")指导 `dex2oat` 提前编译一部分方法,其余方法先不编译。
2. App 前几次运行,没被 AOT 编译的方法先由**解释器**执行;解释器同时统计哪些方法被频繁调用。
3. 被判定为"热"的方法交给 **JIT** 现场编译成机器码。
4. 手机**空闲、充电**时,系统后台把本机积累的执行画像(profile)和云端 profile 合并,再次触发 `dex2oat`,把这次判定为热点的方法**提前编译**好,供下次启动直接用——这一步生成/更新的产物包括 `.odex`/`.vdex`/`.art` 等文件,统称广义的 "AOT 缓存"。

**为什么这事对逆向分析者重要**:

- 你在手机 `/data/app/.../oat/` 目录下翻到的 `.odex`/`.oat` 文件,**是从 DEX 编译出来的机器码**,理论上可以像分析 `.so` 一样丢进 IDA/Ghidra 看汇编——但实际逆向分析者**几乎从不这么干**,因为原始 `classes.dex` 才是"语义完整"的那份原料(§3.3 讲的道理),分析 AOT 产物纯属舍近求远。
- 反过来,这也解释了为什么攻击者(以及本系列后面要讲的 Dex2C、加固方案)如果想让分析变难,思路必须是"**想办法让分析者拿不到、或者拿到了也看不懂 classes.dex**",而不是在 AOT/JIT 这层做手脚——因为 AOT/JIT 只是"运行加速优化",不是"代码分发格式",分析者一开始拿到手的永远是 DEX。

Sources: [Boosting Android Performance with Baseline Profiles](https://www.strv.com/blog/boosting-android-performance-with-baseline-profiles) · [Configure ART | Android Open Source Project](https://source.android.com/docs/core/runtime/configure) · [Android Runtime - Wikipedia](https://en.wikipedia.org/wiki/Android's_ART)

## 6. .so 原生库:这块才是你的主场

APK 里 `lib/<arch>/*.so` 这些文件,和 DEX 完全是两个世界:

- 它们是用 C/C++(有时候 Rust/Go 也能编译到这里)写的代码,经过普通的 `clang`/`gcc` 交叉编译工具链,产物是**标准的 ELF 共享库**——文件格式、节区(`.text`/`.data`/`.rodata`/`.dynsym`……)、动态符号表、重定位表,跟你在 Linux 服务器上见到的 `.so` **一模一样**,只是目标架构通常是 `arm64-v8a`(ARM64)、`armeabi-v7a`(ARM32),有时也有 `x86_64`(模拟器/部分平板)。
- 这些库是**真机器码**,天然不带 DEX 那种"类名/方法名/字符串常量全裸奔"的语义信息(除非编译时没 strip 符号、或者用了 C++ RTTI 导出了类型信息)。逆向它的难度,就是你熟悉的**标准 native 逆向**——上 IDA/Ghidra 反汇编、猜函数边界、抠数据结构、跟指针,跟你分析任何一个 Linux/嵌入式 `.so` 完全同一套方法论。

Java/Kotlin 代码要调用 `.so` 里的函数,得经过 **JNI**(Java Native Interface,03 篇细讲),你可以先按 "**类似 FFI(Foreign Function Interface)或者 C++ 的 `extern "C"` 跨语言调用边界**" 来理解——DEX 那边声明一个 `native` 方法(只有签名没有实现),.so 那边提供真正的函数实现,ART 负责在调用发生时把两边接起来、做参数类型的转换封送(marshalling)。

## 7. 为什么"把逻辑从 DEX 搬进 .so"能抬高逆向门槛

现在你已经有了理解这件事的全部拼图,拼起来看:

| | DEX(Java/Kotlin 代码) | .so(native 代码) |
|---|---|---|
| 产物形态 | 字节码,给虚拟机解释/JIT/AOT 执行 | 真机器码,CPU 直接执行 |
| 语义信息保留度 | **极高**——类名/方法名/参数类型/字符串常量/控制流结构原样在文件里(§3.2/3.3) | **低**——编译优化会重排/内联/消除大量高层结构,除非没 strip 符号否则连函数名都没有 |
| 反编译效果 | jadx 等工具能**逆向出接近源码的 Java 代码**,直接读就懂(07篇) | 只能拿到汇编/伪代码(Ghidra 反编译器已经很强,但仍是"猜出来的近似源码",不是精确还原) |
| 分析者需要的技能 | 会读 Java/Kotlin 即可,几乎零门槛 | 需要扎实的汇编/调用约定/数据结构逆向功底——门槛陡增 |
| 动态调试 | Smali/Java 层断点、Frida hook Java 方法都很成熟顺手(08篇) | 需要 native 调试(gdb/lldb 远程调试、Frida hook native 符号),更繁琐 |

结论显而易见:**同一段业务逻辑,写在 DEX 里几乎"裸奔"给分析者看;写(或者编译)成 .so 里的机器码,分析成本会指数级上升。** 这正是本系列后面 `10-方法原生化-Dex2C与VMP.md` 要专门讲的攻击手段的**动机来源**——业内把"把某个 Java/Kotlin 方法编译成 .so 里的机器码,原来的方法体只剩一个空壳去调用 native 实现"这种手法叫 **Dex2C**("方法原生化"是常见中文叫法)。

给你一个类比帮你直接建立直觉:Dex2C 干的事,很像后端工程师用 **Cython** 把 Python 里的热点函数改写成 C 扩展——表面上调用方式(在 Python/这里是 Java 层)没变,但函数体从"解释执行、逻辑透明的高层语言"变成了"编译后的机器码,想看懂得反汇编"。区别在于 Cython 的目的通常是**性能**,而安卓场景下 Dex2C 的目的往往主要是**逆向对抗**(当然,原生代码执行速度通常也确实更快,这是个双重收益,攻击者两头都占了)。

这个机制的**完整原理**(dcc/amimo 工具怎么把 DEX 方法转换、桩函数长什么样、静态分析怎么识别、防御方怎么应对)本教程第 10 篇会专门讲,更深的技术细节可以直接看进阶专文《[方法原生化 Dex2C 原理保姆级详解](../安全审计-方法原生化Dex2C-原理保姆级详解-给后端工程师.md)》和《[方法原生化 Dex2C 开源工具全景](../安全审计-方法原生化Dex2C-开源工具全景与NP云端一键真相.md)》。本篇你只需要记住**因果链**:DEX 语义信息高 → 好逆 → 攻击者想变难逆 → 把代码搬去语义信息低的 .so → 逆向门槛陡增。这条因果链也解释了报告里几乎所有"加固""混淆""VMP"手段的底层动机——它们本质上都是同一个游戏的不同打法:**想办法让分析者拿到的东西语义信息更少**。

## 一页速记

- **APK = 一个 ZIP**,解压就能看到 `classes*.dex`(代码)、`resources.arsc`(资源索引)、`AndroidManifest.xml`(应用清单)、`lib/*.so`(native 库,真 ELF)、`META-INF/`(签名信息)、`assets/`/`res/`(资源文件)。
- 编译链:`Java/Kotlin` → `javac`/`kotlinc` → `.class`(JVM 字节码,**栈式**)→ `d8`/`r8` → `classes.dex`(Dalvik 字节码,**寄存器式**)。全程没有直接产出机器码。
- **DEX 还原度极高**的根本原因:格式本身就要求把类名/方法名/字符串常量/方法签名/控制流结构完整写进文件(`string_ids`/`method_ids`/`class_defs` 等表),这是虚拟机正确执行的刚需,不是逆向工具"猜"出来的。
- 单个 DEX 的 `method_ids` 用 16 位索引,上限 **65536(64K)个方法引用**,超了就拆成 `classes2.dex`……即 **multidex**。
- **Dalvik**(4.4 及以前)/**ART**(5.0 起,当前主力)是执行 DEX 的**托管虚拟机**,类比 JVM——自带 GC,不用手动管内存。
- 字节码变机器码有三条路,现代 ART **三者混合**:**AOT**(`dex2oat` 提前编译,产物 `.oat`/`.odex`/`.vdex`)、**JIT**(运行时对热点方法现场编译)、**解释执行**(逐条翻译执行,不产出机器码)。
- `.so` = **标准 ELF 共享库**,真机器码,逆向方法论和你熟悉的 native 逆向完全一致(IDA/Ghidra 走起)。JNI 是 Java↔native 的调用桥,类比 FFI / `extern "C"`。
- **DEX 语义信息高→好逆;.so 语义信息低→难逆**,这条因果链驱动了"把 Java 方法编译成 .so"的 **Dex2C**(方法原生化)手法——类比 Cython 把 Python 热点函数改写成 C 扩展,但安卓场景下主要动机是逆向对抗而非单纯性能。
