# 安全审计：攻击者(模组作者/分发渠道)画像 + 工具链指纹

> **一句话定位**：基于 99 份 mod APK 只读取证审计报告,提炼"看到什么证书/类名/水印字符串 → 大概率是谁 → 惯用什么手法"的可 grep 速查表,供审计员快速定位与归因,**不是**司法级身份认证。

> [!IMPORTANT]
> **合规声明**：本文档纯防御/取证视角。只讲"如何识别被攻破的手法 + 如何加固防御",**绝不提供**可直接照做的再破解步骤、patch 脚本、签名绕过配方或任何"改这行就解锁"的操作序列。文中出现的类名/证书指纹/字符串仅用于**审计识别与溯源**,不构成可执行的破解指南。

## 0. 怎么用这份文档(给审计执行者)

1. 先读 §2「证书 DN → 作者速查表」,用 `apksigner verify --print-certs` 或 `keytool -printcert` 拿到证书 DN/SHA-256,对表查作者/渠道。
2. **警惕陷阱证书**(§2 底部标红条目):AOSP testkey、`CN=editor`、裸 `C=IN`/`C=US` 等是**多个不相干作者共用的工具默认证书**,命中它们**不能**直接下结论"是谁",必须再核对 §1 的工具指纹/类名/字符串水印做二次确认。
3. 再读 §1 头部作者档案表,按证书锁定的作者查其惯用手法,决定下一步该 grep 哪些类名/字符串/so。
4. 遇到"标签作者"和"证书作者"对不上号(如文件名 `_@PJAPK` 但证书是别人的),按 §3 的判定法拆解"谁是真正的破解者、谁只是分发渠道"。
5. 遇到 Dex2C/VMP/加固壳,§4 的"作者×加固程度"相关性能帮你预判"这个作者的样本大概率能不能读到具体字节码,还是只能定位机制入口"——据此提前调整审计预算,不要在天花板上硬耗。

## 3. "分发渠道水印" vs "个人作者" 的区分方法

### 3.1 判定信号清单(按可信度从高到低)

1. **包内水印字符串是否与文件名标签一致** —— 最强信号。若文件名写 `_@PJAPK`,但反编译后在类名/字符串常量/关于页里搜到的是另一个名字(如 `Modded By Logan & Published by RBMods`),则文件名标签**必为**分发渠道,真实作者是水印里那个名字。
2. **同一标签下证书 DN 是否跨样本一致** —— 一致(如 zhou45 的 12+ 样本、鹿蜀的 `lushu` 7 样本、youarefinished 的 4+ 样本)强烈支持"同一个人/团体在用固定密钥反复签名";不一致(如本批 PJAPK 标签下已验证出至少 **5 种**互不相同的证书,见下表)则该标签更像是转发多个不同来源产物的搬运渠道。
3. **证书 DN 风格"机器生成" vs "人工填写"** —— 随机 Base64、全字段空、仅一个国家字段等"懒得填"风格,通常是自动化脚本或转发渠道随手生成;拼音/英文昵称/品牌名(`lushu`、`zhou`、`笙`、`Cxapk`、`youarefinished`)是个人/团体的自我署名,更可信。
4. **破解手法风格是否跨样本一致** —— 同一真实作者的多个样本通常共享同一套自定义类前缀、同一 so 命名习惯、同一加固搭配(如鹿蜀去广告线总用 `com.bytedance.shadowhook.<App>.Hook` 马甲 + 云镜;zhou45 总用 NP 管理器 Apk-Dex2C)。风格突变但标签不变,要怀疑是否被别的团队冒用/转发。

- **PJAPK / APKDADDY / Tinkler** 三个标签在本批语料中均已被**直接证据**证实主要是**分发/搬运渠道水印**,而非稳定的单一制作团体——审计时见到这三个标签,应默认"作者身份未知,以证书 DN + 包内水印字符串为准",不要写"该样本由 XXX 破解"。

## 6. 局限声明(诚实标注静态上限)

1. **自签名证书的 DN 可以填任意文本**,`CN=lushu`/`CN=zhou`/`CN=笙` 这类"人类可读别名"只是攻击者的自我署名,不是密码学身份证明——本文档的归因建立在"跨样本证书完全一致 + 手法风格自洽 + (若有)包内水印字符串"三者交叉印证之上,单独一个证书 DN 相同**只是强线索,不是确凿结论**。
2. 本文档的"数量"统计(如"鹿蜀 20 个")来自本批 99 份报告的标签聚合,**不代表**该作者在互联网上的真实产量或活跃度,仅反映本次审计样本池的构成。
3. 遇到 Dex2C/VMP/加固壳/商业 ART Hook 引擎包裹的判定逻辑,本文档和被引用的各报告都只能确证"机制入口"(壳标记文件、Hook 引擎 so、马甲类/ContentProvider),**无法**确证被隐藏的具体字节码改动——这是只读静态审计的硬上限,不是分析不够仔细。凡遇到这种情况,应如实标注"推断/静态无法坐实",禁止臆造具体的方法名、寄存器操作或恒真化位置去填补空白。
4. 部分"陷阱证书"(§2 表 B)的哈希比对基于报告原文摘录,个别数值存在**转录误差**(如 derrin 的 `Video-Downloader` 报告哈希缺失末位一位数字,经核对后与 NURIK 版本一致)——本文档已在能力范围内做了字符级核对,但读者复核时仍应以 `apksigner verify --print-certs` 现场取值为准,不要直接信任任何二手转述的指纹字符串。
