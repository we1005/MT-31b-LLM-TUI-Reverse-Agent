## 二、框架完整性审查 — 诚实结论

用 4 个独立 agent 并行读了全部源码（带 file:line）+ 一个首席审查员综合。结论诚实、不替框架护短：

### 一句话：能独立做静态，不能独立做逆向全程

> **rev-agent 是「离线静态逆向的定位加速器」，不是能端到端独立完成逆向的自主 agent。**

- ✅ **能无人值守独立跑完**：反编译 → grep → 读片段 → 出静态结论（对得上 benchmark 静态 11/12）
- ❌ **必须人接管**：一旦进入"连真机 → 触发 APP → 读实时输出"或"native 深挖 / 算法执行验证"

### 7 大工作流的真实覆盖

| 工作流 | 能否独立 |
|--------|---------|
| §3.A 拆包/指纹/manifest | ✅ 全自动 |
| §3.E 提取 native 签名 | ⚠️ 只能静态侦察(nm/strings)，Ghidra 深挖交人 |
| §3.G 破解 VIP | ⚠️ 只能静态定位破解点，不内置破解 |
| §3.B 抓 HTTPS | ❌ 起代理/装CA/人点APP产流量 |
| §3.C 绕 SSL Pinning | ❌ objection 交互 REPL 喂不了 stdin |
| §3.D Frida hook | ❌ 写不出 hook.js + 流式输出被掐 |
| §3.F 批量 | ❌ python3/docker 不在白名单 |

**"不懂逆向的人靠它端到端还原签名" = 不能。它只对"已会逆向、要加速静态定位"的人高价值。**

### 根因：一个架构撬点

`shell.ts:141-170` 的 shell 工具是一次性 fire-and-wait——spawn 只在 close 时返回、无 stdin、
60s 强杀、4KB 截断。所以持不住代理/frida 会话、喂不了 REPL、流式读不了 hook 输出。
**§3.B/C/D 全塌方都挂在这一个根因下。**

### 审查也揪出 4 个 blocker 级的健壮性真 bug（跟能力无关，是"敢不敢无人值守"）

1. **A1**: `generateText` 无 abort/timeout → 本地后端 stall 就永久 hang
2. **A2**: LLM 抛错零重试 + `run-interactive.onSubmit` 未 try/catch → 崩 TUI
3. **A5**: budget 用"累计吞吐"不是"上下文占用"，且后端不报 usage 时硬止损静默失效
4. **A6**: 交互模式 stepCount/nudge 跨轮不重置 → 跑满 30 步后会话卡死

这几个之前 benchmark 没测到（都是 `--once` 单轮跑，没暴露多轮/hang/崩溃）。

### 建议（分两档）

**第一档：立刻补循环韧性（A1+A2+A5+A6）** — 便宜、零边界冲突、不加能力但把"demo 能跑"变成"敢无人值守跑"。这几个是真 bug，不补的话"独立完成"在无人值守语义下是假命题。

**第二档：会话型工具 + 接入设备工具（A3+A4）** — 战略投入，解锁动态半场。但审查诚实地说：即便做了，native 签名还原仍卡 Ghidra GUI、执行验证受 python 约束，不建议把"全自主端到端"设为目标。

务实定位 = **静态强项可信无人值守 + 动态观察类自主，native 深挖与破解永远显式留给人** —— 与锁定的"只读分析/不内置破解/私用不分发"边界恰好自洽。

## 三、能否像 MT 管理器一样直接打包签名出新 APK？

### 答案：技术上能，但被审批闸控住 + 撞红线

#### 技术层面：能（工具都在）

MT 管理器那套"改完直接出新 APK"的三件套，rev-agent 白名单全有：

| 步骤 | 工具 | 白名单 | 审批分类 |
|------|------|--------|---------|
| 反编 → 改 smali | `apktool d` / `sed` / `smali` | ✅ | 改 smali(sed) = **auto** ⚠️ |
| 重打包 | `apktool b -o new.apk` | ✅ | **ask**（弹审批） |
| 对齐 | `zipalign` | ✅ | **ask** |
| 签名 | `apksigner sign` | ✅ | **ask** |

流程上完全跑得通：`apktool d` → 改 → `apktool b` → `zipalign` → `apksigner sign` → 出新 APK。

#### 但有三道关：

**1. 审批闸（设计使然，D6 那次没动它）**
`apktool b` / `zipalign` / `apksigner sign` 都是 **ask**——`--once` 默认拒、要 `--auto-approve` 才放行、交互模式弹窗。这是 D6 决策（write 类弹审批）故意的：**打包签名不会自动发生，必须人点头。**

**2. 撞锁定的红线 🔴**
compliance_redlines + user_preferences **红线 #6**：
> 不内置一键签名校验绕过 / VIP 破解 / killer_dex 注入

"改完直接出新 APK" 如果是为了破解/绕过 VIP/去签名校验，就踩这条。完整性审查（B1）也明确把 **§3.G 永久破解、smali 补丁、回签重打包 = 红线不做**。

**3. 刚发现的一个真洞 ⚠️**
`sed -i` 改 smali 被判 **auto**（不弹审批）——审查 A8/B1 已揪出：agent 能不经审批盲改 smali 文件。这是白名单漏配，违背"只读分析"定位。**这个该修（改成 ask）。**

### 结论按用途分两种

| 你的用途 | 能不能 |
|---------|--------|
| **合法重打包**（自有 App 加日志/改配置/patch 自己的代码，`--auto-approve` 或逐次审批） | ✅ 技术上能，工具齐全，走审批 |
| **破解别人的 App / 绕签名校验 / 做 MT 圈那种 MOD** | 🔴 撞红线 #6，且审查定为 out-of-scope |

**一句话**：rev-agent 具备打包签名的工具能力，但它被设计成"分析 + 定位"的 agent，打包签名是留给人审批的收尾动作，不是它自动帮你出破解包——这正是当初锁死红线 #6 的本意。
