# 安全审计：按破解类型的排查方向与决策树

> 一句话定位：拿到一个 mod APK,先看文件名标签定「类型」,按类型分流去查对应的判定方法名/SDK包名/注入痕迹,遇到 Dex2C/VMP/加固壳/ART Hook 立即止损标注「推断」,绝不因「没搜到」就断言「不存在」。

> **合规声明**：本文档纯防御/取证视角。只讲「如何识别被攻破的手法」与「审计员/防御方如何加固」,**不提供任何可直接复用的再破解步骤、patch 操作序列或绕过脚本**。文中出现的类名/方法名/工具指纹均为**已发生的取证事实**(用于训练识别能力的模式库),不构成可执行的破解教程。

**数据来源**:`/Volumes/zhitai-7100/reverse-agent/_scratch/apk-2-audit` 下 99 份只读静态审计报告(逐个反编译取证),经 `_index_rows99.json`(结构化聚合)+ `INDEX.md`(总索引)+ 对 99 份报告全文做关键词频次统计后蒸馏。类型分布：去广告 30、高级/Pro 29、会员/VIP 25、解锁完整 5、纯净版 5、注入模块 3、其它 2(共 99)。

## 一、总决策树

```
拿到一个 mod APK
  │
  ├─ Step 0. 文件名/标签速判类型 ────────────────────→ 见 §二 对照表
  │
  ├─ Step 1. 签名证据(通用,所有类型都先做)
  │     aapt dump badging(包名/入口Activity/权限/版本)
  │     apksigner verify --print-certs
  │     ├─ DOES NOT VERIFY → 正常(几乎必然反编译重打包过)
  │     ├─ 记下证书 CN / 签名方案(v1/v2/v3) → 查 §三 作者指纹表,常可秒定位手法族
  │     └─ 若原厂证书被原样保留但业务dex哈希与MANIFEST.MF不一致
  │           → 说明"重打包后未重签",可能是流水线中间产物,查改包时间戳链佐证改包窗口
  │
  ├─ Step 2. 反编译进场
  │     apktool d(资源+smali完整) / jadx(读 Java 语义辅助定位)
  │     ├─ 反编译后 classes.dex 只剩个位数类(如仅壳自身 stub)+ 高熵 assets/*.jar|*.dat
  │     │     → 判定"整体加壳,业务代码在加密载荷里",直接跳 Step 4
  │     └─ 正常反编译出完整业务类 → 继续 Step 3
  │
  ├─ Step 3. 按类型分流 grep(见 §四,6 个子决策树 4.1~4.6)
  │     命中具体 class.method 且字节码可读 → 输出确证破解点,标 [确证]
  │     未命中但有旁证(方法名残留/字段值反常/配置资产异常) → 标 [推断],写明依据
  │
  └─ Step 4. 原生化/加壳/运行时 Hook 止损判据(见 §五)
        看到 SecShell/爱加密/360/云镜/云镑/Apk-Dex2C/dpt-shell/Smob/LSPlant/Epic/Pine 等指纹
        → 明确写"机制已定位到入口,具体改动点因加壳/native化/运行时Hook无法静态还原"
        → 严禁因为"grep 不到"就写"不存在此类判定",也不得编造具体行号/字节码去凑"确证"
```

## 二、文件名标签 → 类型速判表

| 文件名/标签关键词 | 判定类型 | 备注 |
|---|---|---|
| 会员版 / VIP版 / SVip | 会员/VIP | |
| 高级版 / 专业版 / Pro | 高级/Pro | 与「会员/VIP」界限常模糊,以实际判定字段是 `isVip` 还是 `isPro`/`isPremium` 定归类,而非只看文件名 |
| 去广告版 / 无广告 / 净化广告 | 去广告 | |
| 解锁版 / 解锁完整版 | 解锁完整 | 样本证明这类多是 `licensing`/`checkLicense` **服务端授权网关方法**被恒真,而非改 `isVip` 字段 |
| 纯净版 / 绿化版 | 纯净版 | 常是「去广告 + 去推广弹窗 + 去更新检测」组合,比单纯去广告版改动面更杂 |
| 内置XX模块 / 集成XX模块 | 注入模块 | 通常是 LSPatch/Xposed 打包壳,判定改动在**独立注入的模块**里实现,不在主 App 业务 dex 里改 |

> 标签可复合(如"会员+去广告版"),此时按两个子目标分别查,见 §四 对应小节。

## 四、按破解类型的排查决策树(核心)

> 每类给：grep 锚点(按命中率降序)→ 典型落点模式 → 命中率排序 → 止损时机。命中率数字来自 99 份报告中该类型「静态确证到具体 class.method」vs「撞见壳/Dex2C/native化只能推断」的实际比例。

### 4.1 高级/Pro(n=29,静态命中率最高 ≈93%——29 例中仅 2 例撞壳/native)

**优先 grep 锚点**:
1. 方法名族：`isPro(` `isPremium(` `isPremiumUser(` `isProUnlocked(` `isProBlocking(` `hasPremiumAccess`
2. 恒真指纹：方法体内 `const/4 v0,0x1` 或 `const/16 v0,0x1` 紧邻 `return`/`return v0`,且方法名/字段名含 Pro/Premium
3. 默认分支篡改：数据结构/枚举遍历末尾的 `default` 返回值从 `NONE`/`FREE` 改为 `PRO`/最高档位
4. 计费回调伪造：`BillingClient` 购买回调方法未购买分支被覆盖为直接置真(常见于 `move-result` 后紧跟一条 `const/4 vX,0x1`)
5. LicensingService/LVL 回调：`dontAllow()`/`applicationError()` 被改写成与 `allow()` 同构

**典型落点模式**(真实出现过的命名规律,供比对认知):
- `<包>.billing.impl.XxxBillingImpl` / `XxxLicensingServiceCallback`
- Activity/Fragment **公共基类**里的全局门禁字段(如 `BaseActivityParent.isPremiumUser()`),改一处联动全 App 数十处调用点——**审计时优先查基类而非逐个业务类**,性价比最高
- `Globals.R()` / `Feature.c()` 这类全局单例的门禁 getter/setter,常有 30+ 调用点

**命中率排序**：中心判定方法直接恒真 > 计费回调短路 > 默认分支篡改 > 依赖 native/Dex2C 隐藏(少数)。

**止损时机**：若判定方法已被 R8 类合并/内联到无法定位具体行,或被 Dex2C 转 native(`.source "YJ-Dex2C"` 一类标记),只能确证"该方法整体native化,推断为判定点",不得编造具体字节码改法。

### 4.2 会员/VIP(n=25,命中率高 ≈80%——20% 遇到壳/native)

**优先 grep 锚点**:
1. 方法名族：`isVip(` `isVipUser(` `isMember(` `getMember(` `isPermanentVip(` `getVipType(` `getVipLevel(` `isVipVM(` `isSVip(` `isAiVip(`
2. **数据模型构造参数恒真化**(比恒真方法体更隐蔽,易漏判)：找承载会员态的 RPC/DTO 模型类构造函数,核对入参寄存器是否被覆盖为常量(尤其布尔字段)而非原样传递——真实案例中一个 8 参数构造函数,6 个被替换为硬编码常量,仅 2 个原样传递,而外层判定方法本身完全未改
3. SharedPreferences/本地缓存篡改：搜 `USER_IS_VIP` / `isPermanentVip` 一类 key 的 `getBoolean(key,false)` 默认值是否被改为 true
4. 签名相关旁路联动：`com.srpatchv3.Application` / `killPM` / `killOpen` 常与会员判定改动**同包出现**,见到即优先查其上下游是否也动了 VIP 字段

**典型落点模式**:`<包>.model.UserBean/UserInfo.isVip()`、`<包>.data.entity.User.isVip()`、SharedPreferences 里的 `USER_IS_VIP`/`vipType` 键

**命中率排序**：单方法直接恒真 > 数据模型构造参数恒真化(需寄存器级追踪,别只读方法名就下结论"未改") > SharedPreferences 篡改 > 依赖运行时 ART Hook(静态只能定位注入框架,挂钩具体目标判不出)。

**止损时机**：见到 `com.bytedance.shadowhook.<应用名>.Hook` 这类**伪装成 ByteDance 官方组件、实际是自定义 Hook 载荷**的类,且方法体已被 Dex2C 编译为 native(`.source "YJ-Dex2C"`)→ 只能确证"存在运行时 Hook 机制,目标疑似某某",不能倒推出具体 Hook 的字节码逻辑。

### 4.3 去广告(n=30,全批**静态定位最难**的一类,命中率 ≈40%——60% 撞见壳/Dex2C/ART Hook)

去广告类很多样本的广告 SDK 组件/manifest 完整保留未删,真正的中和点被壳或运行时 Hook 掩盖——这是**结构性**的困难,不是审计员技术不到位,如实标注即可。

**优先 grep 锚点**:
1. 先按附录 A 确认广告 SDK 身份,定位其 init/load/show 入口方法名：`init(` `loadSplashAd(` `showAd(` `TTAdManagerHolder.init/doInit/reset` `WBAdSdkInit()`
2. Flutter 混合应用：查 `xxx.flutter_advert_xxx.FlutterGgPlugin` 一类 MethodChannel 桥接类是否被**整体删除**(利用 `GeneratedPluginRegistrant` 自带 try/catch 容错,删除后不崩溃、只是广告请求静默失败——判据是"类消失但App仍稳定运行")
3. 广告位配置资产(壳保护下仍可能明文可读的旁证)：若能找到 `assets/SDK_Setting_*.json` 一类配置,比对同文件内不同广告场景(feed/splash/reward)的广告位 ID/status 字段是否被**选择性清空**(只清空一个场景,比全清空更隐蔽,是壳后手法的最佳静态旁证)
4. Application 继承链劫持：检查 Manifest `application` 与 `appComponentFactory` 是否指向陌生类,业务 Application 的 `.super` 是否被改指向注入的 Hook/签名绕过类
5. 高 `initOrder` ContentProvider：搜 `initOrder` 极大值(如 `2147483647`/`Integer.MAX_VALUE`)的自定义 ContentProvider,是运行时 Hook 引擎抢在业务代码前加载的常见挂载点

**典型落点模式**:`<包>.feature.advertisement.view.*AdSwitchView`、自建首方广告位组件(`XxxAdStartView`/`XxxAdPauseView`)、`com.anythink.flutter.*Helper`(banner/interstitial/reward/splash 全形态)

**命中率排序**:manifest/资源层配置清空(明文可见) > Application/appComponentFactory 劫持(能定位机制) > dex 内判断分支 no-op(常被壳挡) > 纯运行时 ART Hook 拦截(静态只能定位到 Hook 引擎本身,拦截目标不可还原)。

**止损时机(本类型最容易触发,务必留意)**：一旦确认 `classes.dex` 反编译后只剩个位数的壳自身类(如 `com.SecShell.SecShell.*`/`com.stub.StubApp`),真实业务在 `assets/classes0.jar`(高熵、非合法 zip/dex 结构)内 → **立即停止猜测具体广告判断分支**,报告应写"业务dex被X壳整体加密,广告SDK组件在manifest中完整保留未删除,支持'运行时/加密态代码内no-op'假设但无法静态坐实具体类.方法"。**绝不能因为"广告SDK还在、manifest没变"就断言"没有做去广告"——去广告完全可能发生在你读不到的加密dex或native层里。**

### 4.4 解锁完整(n=5,命中率最高 100%——0 例撞壳)

**优先 grep 锚点**:
1. `checkLicenseOnBackend(` `checkLicense(` `checkPluginLicense(` `checkUnlockerLicense(` `isValid(` `isPurchased(`——服务端授权网关类方法,常见于第三方 Licensing SDK(如 Google LVL 或自研 licensing 包)
2. 优先看类名含 `licensing`/`License` 的**独立授权包**,而不是 App 自己业务层的 `isPro`/`isVip`——**破解者倾向挑校验链路里最底层/最薄弱的网关方法下手**,上层业务判定往往完好无损、只是判定源头已经被喂了"已授权"
3. 恒真收敛出口：方法体唯一收敛出口(如某个 `:cond_xx`/`:goto_xx` 标签)被硬编码为 `const/4 p0,0x1; return p0`,函数内已无任何返回 false 的路径

**典型落点模式**:`pl.solidexplorer.licensing.SELicenseManager.checkLicenseOnBackend(String)`——本批中**同一开源库、两个不同作者的独立样本都命中了同一个方法**,说明攻击者之间会共享"这个类是命门"的经验,审计常见开源授权库时应优先假设其公开薄弱点已被广泛复用。

**命中率排序**：服务端网关方法恒真 > SharedPreferences 缺省值篡改 > 签名/证书伪造配合(少数需额外查)。

**止损时机**：本类型基本不会撞壳。若某案例迟迟找不到,先检查是否该按"高级/Pro"或"会员/VIP"的判定方法名重新分流查——标签词有时口语化,不代表真实判定机制的类别。

### 4.5 纯净版(n=5,命中率较高但改动面分散,需按子目标逐个查)

纯净版通常是「去广告 + 去推广弹窗 + 去更新检测」的**组合包**,不是单一判定点：

**优先 grep 锚点**:
1. 去广告部分：同 §4.3
2. 会员相关 getter 批量恒真：一个类里连续多个 getter(常见单字母混淆名如 `a()/b()/d()/f()/g()/k()/l()/j()`)被逐个改写,常见于把整个"用户/VIP信息类"批量清空
3. 推广/弹窗组件：搜索 `Dialog`/`Popup`/`Ad*View` 相关的 `init`/`doInit`/`reset` 方法体是否被阉割为 `return-void`
4. **反向指标**：若发现新增的、与原 App 包名无关的陌生第三方引流/致谢弹窗类 → 说明改包方自己也在打广告,审计报告应同时指出"改包方注入了自身推广组件"

**命中率排序**：单类多 getter 批量恒真(命中率高,模式统一) > 去广告部分(同 §4.3 难度) > 隐藏在壳/推断层面的判定(命中率低)。

**止损时机**：若文件名声称"纯净版"但实际改动只查到重签名+个别弹窗组件,广告判定链路"存在但未见明确恒真补丁" → 如实标注 [推断/未证实],**不要为了凑齐"纯净版"叙事而虚构确切改法**。

### 4.6 注入模块(n=3,判断范式完全不同——找的不是"改了哪一行",而是"挂载了哪个模块")

这一类**不改动主 APK 的业务 dex**,而是用 LSPatch/Xposed 打包器把一个独立的 Hook 模块和目标 APK 打包在一起,运行时用 Hook 框架接管。审计重点从"定位被改的一行代码"变成"识别打包器 + 定位被打包进去的模块"。

**优先 grep 锚点**:
1. Manifest:`android:appComponentFactory` 是否指向 `org.lsposed.lspatch.metaloader.LSPAppComponentFactoryStub` 或类似 `LSPApplication`/`AppComponentFactoryStub`
2. 配置文件：`assets/lspatch/config.json`,查 `sigBypassLevel` 字段(=2 即完全伪造签名回传给应用自查)
3. 内置 Xposed 模块本体：通常是一个独立、体积明显更大的 dex/目录,带自己的版本号水印,以 `XposedInit`/`IXposedHookLoadPackage` 作为入口
4. 目标行为：该模块具体 Hook 了 App 的哪个判定/展示方法(关注判定、广告SDK初始化、地区限制字段等)——这部分仍按 §4.2/§4.3 的方法名族去 grep,只是要在**注入的模块 dex** 里查,不是主业务 dex

**典型落点模式**：广告SDK初始化方法被置空(如 `WBAdSdkInit()` 一类命名)、`XposedInit` 挂钩内容访问/关注判定分支、独立 Xposed 模块挂钩地区限制字段解析链路

**命中率排序**：「是否被 LSPatch/Xposed 打包」这一判定本身命中率 100%(manifest 特征明显);「模块具体 Hook 了什么」命中率视模块混淆程度而定——商业级模块常见控制流平坦化 + 字符串加密 + 调用栈自省反分析,静态定位其 Hook 目标可能仍需止损。

**止损时机**：模块本身若做了控制流平坦化+字符串加密,只能确证"模块存在且挂载点是什么",Hook 的具体目标方法可能无法逐行还原,如实标 [推断：根据模块名与常见同类模块行为推测]。

## 五、静态止损总判据(跨类型通用——看到就该停,别硬猜)

| 触发信号 | grep 锚点 | 该怎么写 |
|---|---|---|
| 商业加固壳 | `SecShell` `com.stub.StubApp` `libjiagu` `ijiami` `assets/ijiami_*.VData` `Apk-Dex2C` `assets/protected_by_np` `assets/protected_by_yj` `云镜`/`云镑`/`yjaq.xyz` `dpt-shell` `nmmedit` `Smob` | "业务dex/关键方法被 X 壳保护,静态无法读取明文,以下结论基于旁证推断" |

## 六、给防御方的最小加固清单(呼应识别侧,详见同目录 INDEX.md §六)

1. **权益判定上移服务端**：会员/Pro/广告开关的最终裁决放服务端逐请求核验,客户端仅凭短时效签名令牌展示,杜绝单点字段/单个数据模型对象被恒真化或缓存被改即全线解锁。
2. **签名完整性多源校验且参与业务解密**：不要只依赖 `PackageManager.getPackageInfo(GET_SIGNATURES)`(已被 ApkSignatureKillerEx 式反射 Hook 完全绕过);应 native 直接解析 APK v2/v3 签名块字节做哈希比对,且校验结果**参与关键数据解密**而非仅 if 分支。
3. **运行时反 Hook/反注入自检**：扫描进程内存映射中 `liblshook`/`libpine`/`liblsplant`/`libEpic`/`libaliuhook` 等 ART Hook 引擎特征库;检测 `appComponentFactory` 被劫持、Application 继承链(`.super`)异常;检测高 `initOrder`/伪装系统包名的 ContentProvider。
4. **加固壳 ≠ 防篡改**：本批大量样本证明商业加固壳未能阻止"不碰加密dex、仅靠内存级 ART Hook"的绕过;加固需与签名校验、反Hook、服务端裁决协同,单独上壳无效。
5. **发行侧完整性**：接入 Play Integrity / 完整性检测,服务端对非原始签名包拒绝下发会员内容与广告配置;建立分发渠道监测识别已知模组作者水印与自签重打包分发。
6. **默认分支 fail-closed**：授权/校验遇网络异常、缓存缺失、未知状态时默认**拒绝**而非放行——本批多起破解正是利用"异常→默认放行"的收敛出口。
