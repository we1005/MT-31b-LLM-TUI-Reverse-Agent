# rev-agent 三提议深度分析：前置工作流 / 文档 RAG / 蒸馏

> **日期**：2026-07-10
> **方法**：不迎合。先用 3 个独立 agent 各为一个提议做**最强辩护(steelman)**，再拿硬数据和已知失败面去打它们的最强版本。三个 steelman **自己都承认了字面提法辩护不了哪部分**——本文的批判因此不是"我 vs 你"，而是有对抗验证背书。
> **用户要求原文**：见 §0。

---

## §0 用户的三个提议（原文转述）

1. **前置工作流**：对某 APK 逆向时，agent 必须先拿到用户手动跑 jadx/apktool 反编译好的结果的**绝对路径**，才开始 agent loop；前置的重工具 shell 执行让用户手动做，agent 只负责文本搜索 + 给逆向方案。
2. **官方文档转 MD 查询**：小模型知识量不够，把 jadx/apktool 等命令的官方文档转成 Markdown 放某目录，让它自己查询。
3. **蒸馏**：实在不行，用其他（更强）模型生成很多逆向 Markdown 和 Skill，蒸馏进这个小模型。

---

## §1 一句话结论（先给裁决，再论证）

| 提议 | 字面版裁决 | 内核裁决 | 该做的最小形态 |
|------|-----------|---------|---------------|
| 1 前置工作流 | ⚠️ **半对**：绝对化（所有 APK 必须人工预反编译）站不住 | ✅ 内核成立 | 30 行 fail-fast 前置校验（只锁"完整源码树"，不锁全部工具） |
| 2 文档转 MD | ⚠️ **小对**：全量转 MD 被数据反对 | ✅ 窄内核成立 | 20KB 离线"递归嵌套 --help"生成脚本 + §9 一行指针 |
| 3 蒸馏 | ❌ **字面错**：权重蒸馏撞红线#10 + 只能用已加载模型 | ✅ 但内核=你早就在做的事 | 把 §9 的产法固化成一个 dev-time 循环（上下文蒸馏，非权重） |

**贯穿三者的真相（最重要的一句）**：
> 三个提议都在试图**补"知识"**，但 benchmark 的证据是——rev-agent 的失败 **11/12 是"行为"问题（过早终止/grep 策略/不写最终答案），只有 1/12（recon-3）是"知识"缺口**。三个提议合起来，天花板也只有那 ~8%。**它们不是错，是打偏了主要战场。** 真正卡住 agent 上限的是完整性审查的 D1（shell 一次性/60s/无 stdin → 动态半场做不到），三个提议**一个都不碰它**。

## §2 提议 1「前置工作流」——半对，但绝对化站不住

### 强辩护承认成立的内核
"深度源码级分析依赖的**完整 Java 源码树**，必须由人预先产出并交绝对路径，agent 不该自己生成它。" 三个独立条件同时满足：
- (a) 整包 jadx 31MB 实测 **123s > shell 60s 硬上限**（`shell.ts:119`），架构上跑不完（完整性审查 D1）
- (b) 这一步**零 LLM 增值**（工具输出是 APK+flag 的确定性函数），且是已观测失败源（recon-3）
- (c) **全部 11/12 分数本来就是在预反编译 sources 上拿的**——demo.sh 测试4 就是 `--once` 跑在 `$JADX/sources`。这不是新约束，是把工具"被验证的唯一工作模式"显式化。

### 我的批判：三处绝对化辩护不了（连 steelman 都认账）
1. **"所有 APK 逆向都必须先人工预反编译"太宽**。§3.A 指纹/manifest 类任务，`apktool d --no-src` 1~2s、`apkid`/`aapt2` 亚秒——完整性审查评为"✅ 全自动"。在这里强插人工预步骤 = 纯摩擦零回报。
2. **"agent 绝不执行重工具"过度限制**。单 dex `unzip classes.dex + jadx` ~7s 在预算内、合法有用。真正的规则是"不跑超 60s 的操作"，不是"不跑任何反编译器"。
3. **作为"强制 MANDATE"部分冗余**：整包 jadx 早被 60s 挡死、回签早被写审批闸挡住。提议 1 的真实价值是 **UX（秒级 fail-fast + 给配方）**，不是新增安全性——把它吹成"架构级安全前提"是夸大。

### 一个你可能没意识到的成本
硬闸把用户踢回终端手动跑 jadx、等两分钟、再调用——**侵蚀"agent 替我干"的卖点**。但这成本落在"不懂逆向的小白"身上，而完整性审查已把该人群划为 **out-of-scope**（工具只对"已会逆向、要加速静态定位"的人高价值）。所以成本真实，但落在一个已声明的非目标用户段——**可接受**。

### 裁决
✅ **值得做，但只做"针对完整源码树的秒级 fail-fast 前置校验"**，不要做成"所有 APK 逆向都必须人工预反编译"的全局强制。约 30 行，照搬 `resume.ts:53-58` 已有的"不静默退化"模式：源码级意图 + workdir 无 sources/smali/dex → 不进 loop，打印一行可抄配方（`jadx -d <out> <apk>`）+ 退出码非 0。§3.A 的秒级工具继续留在 loop 内自动跑。

## §3 提议 2「官方文档转 MD」——小对，但"全量"被数据直接反对

### 强辩护里最硬的一点（实测验证过）
recon-3 需要的 `aapt2 dump xmltree <apk> --file …` 语法**藏在两跳之外**：`aapt2 --help`(1KB)里没有 → `aapt2 dump --help`(列出 xmltree) → `aapt2 dump xmltree --help`(208B 才给 `--file`)。模型不会自发做这个两跳发现。**一份"递归展开的 aapt2.md" + 一条 `grep xmltree` 就能一跳拿到**。而且 `jadx --help` 实测 **12444 字节 > shell MAX_OUT 4096**——朴素"自己跑 --help"只回前 4KB，2/3 的 flag 模型永远看不见；read_file/grep 读 MD 文件绕过这个 4KB 天花板。

### 我的批判（硬数据在我这边）
- **"转全部官方文档"被 3→11 的证据直接反对**：分数是靠 **3.6KB 的 curated §9** 拉起来的，不是全量文档。jadx 单份 --help 12.4KB 绝大部分是模型要费 token 过滤的**噪音**。证据说的是"**curation 赢过体量**"。
- **只打 ~8% 的战场**：12 题里只有 recon-3 是知识缺口。docs-MD 天花板就这么高。
- **半盲问题**：模型能猜到关键词（xmltree/sign）时 grep 才有用；完全不知道某能力存在时它不知道 grep 什么——这种全盲场景，§3 工作流"想做 X → 用 Y"的映射比裸文档转储更管用。
- **版本漂移负债**：curated 工作流是版本无关的；物化的 --help 绑死 jadx 1.5.5，升级要重生成。

### 裁决
✅ **值得做，但砍成最小形态、别当知识平台吹**：一个 `scripts/` 里的**离线递归 --help 生成脚本**（对白名单工具递归跑 `<tool> <subcmd> --help` 拼成 `docs-resources/tool-help/<tool>.md`，约 20KB，本地不联网、不 load 模型、不起 Docker、纯静态文件）+ §9 加一行指针"不确定 flag 就先 grep tool-help/"。它把 recon-3 那类"两跳子命令语法 + 被 4KB 截断的长帮助"变成一次 grep 命中——这是 curation 否则要逐工具追着填的。**但它对主导的行为型失败和动态半场 blocker 毫无作用。**

## §4 提议 3「蒸馏」——字面错，内核是你早就在做的事

### 必须先拆穿字面提法（steelman 自己认账）
"用强模型蒸馏进小模型(Qwen3.6-35B)的**权重**" —— **辩护不了**：
1. **撞红线 #10**：不擅自起 Docker 跑 LLM 训练（占资源）。
2. **物理不可能**：用户只能用 **lemonade 服务器侧已加载的模型**，无法把 fine-tune 后的模型 load 上去。
3. **单机 35B 全量/LoRA 微调**本身是数天级 GPU 工程，对"私自使用不分发"的个人工具是荒诞的投入产出比。

### 但内核成立——而且它已经跑了三轮
真正成立的是【**上下文蒸馏 context distillation**】：dev-time 用强（云端）模型，把逆向方法论提炼成 compact、失败驱动的 cheat-sheet / skill，通过**既有的 §9 自动追加机制**注入小模型。
**证据：§9 本身就是一次教师→学生蒸馏的成品**——由强分析（就是这几轮的 workflow）产出、针对失败模式的 3.6KB cheat-sheet，把静态定位 3→11。recon-3 被 §9 第 3 条一行杀死，正是"用强模型知识补小模型工具语法盲区"的教科书场景。**每字节效力：3.6KB 精编 §9 > 12.4KB 原始 --help** —— 这恰恰是蒸馏（提炼）而非堆文档的核心价值。

### 我的批判
- **"生成大量 Markdown 和 Skill"里的"大量"是反模式**。数据说 curation 赢过体量；"大量"会把 §9 的信噪比稀释回噪音。要的是**少而精 + 失败驱动**，不是量。
- **合规暗礁**：蒸馏时**绝不能把目标 APK 的反编译代码喂云端模型**（撞"数据不上云"红线）。只能喂**通用失败模式**（"agent 不会 aapt2 xmltree 语法"这种抽象描述），不能喂"MT2.26.5 的 C11960 长这样"。这条边界很细，容易踩。
- **它仍只喂知识**，对行为型失败（主要战场）零帮助——那些是 loop 机制（nudge/finishReason）的活。

### 裁决
✅ **内核值得固化成流程，字面版永久否决**。最小形态 = 一个 dev-time"蒸馏循环"，全复用已有设施：`benchmark-models.sh` 取样失败 → 只挑**知识类**失败 → 把**通用失败模式**（不含目标代码）交云端强模型写 ≤4KB 定向 §N/skill → 用 `prompts.ts` 的 `extractGuardBlock` 同款机制追加或作 skill 注入 → A/B 复测确认提升。**这不是新架构，是把 §9 的产法写成可复用 SOP。**

## §5 三提议的统一诊断（批判性总览）

```
                    rev-agent 的失败面（benchmark 实证）
   ┌───────────────────────────────────────────────────────────┐
   │  行为型失败  ~11/12 主导  →  loop 机制修（已做：nudge/finishReason/重试）│
   │  知识型失败   ~1/12       →  三个提议在抢这一小块              │
   │  架构型 blocker（动态半场）→  D1 shell 一次性/60s/无stdin（三提议都不碰）│
   └───────────────────────────────────────────────────────────┘
```

**关键判断（不迎合版）**：
1. 三个提议**方向一致地押注"知识不足是主要瓶颈"，但这个前提是错的**——主要瓶颈是行为和架构，知识只占 ~8%。这不是说它们没用，而是说**别把它们当成"让 agent 更能独立完成逆向"的关键投入**，它们是静态知识供给的锦上添花。
2. 三者**去掉夸张后收敛到同一个东西**：把"人已知的正确知识"以**最小、失败驱动、grep-able**的形态喂给小模型。§9 已经证明这条路，剩下的只是**把它工程化 + 补两个具体缺口（源码树前置校验、递归 --help 库）**。
3. **性价比排序**：提议1 内核（30 行 fail-fast，消真实失败+守红线）> 提议2 内核（20KB --help 库，补 8% 知识缺口）> 提议3 内核（蒸馏 SOP，是 1 和 2 的产法本身）。**字面版全部否决。**

## §6 落地建议（若要推进，按此排序）

| 优先级 | 动作 | 成本 | 打中什么 | 红线 |
|-------|------|------|---------|------|
| P0 | **源码树 fail-fast 前置校验**（提议1内核）：run-once.ts 加 30 行，源码级意图+workdir 无 sources → 秒级 fail + 给配方 | 极低 | 消"撞超时墙"+"fumble 重工具"两类失败，守只读红线 | 零冲突 |
| P1 | **离线递归 --help 库**（提议2内核）：scripts/ 生成脚本 → docs-resources/tool-help/*.md + §9 一行指针 | 低（20KB 静态） | recon-3 类 ~8% 知识缺口 | 零冲突（本地/不联网/不 load 模型） |
| P2 | **上下文蒸馏 SOP**（提议3内核）：把 §9 的产法写成 benchmark→挑知识类失败→云端强模型写≤4KB块→A/B 的可复用循环 | 中（流程+纪律） | 未来新工具的长尾知识缺口 | 需守"只喂通用失败模式不喂目标代码" |
| — | ❌ 权重蒸馏 / 微调 / 全量文档转 MODEL / 所有 APK 强制人工预反编译 | — | — | 撞红线#10 / 撞"只能用已加载模型" / 被数据反对 / 与§3.A全自动冲突 |

**如果只做一件**：做 P0。它零成本、消两类真实失败、守红线、且和"11/12 全在预反编译源码上"的工作模式完全自洽——这是三个提议里唯一"既是你想要的、又打在真实失败面上"的部分。

**如果目标是"更接近独立完成逆向"**：那三个提议**都不是答案**。答案是完整性审查的 A3（会话型工具）+ A4（接设备 MCP），那才碰动态半场的 D1 根因——但那是战略投入，且 native 深挖永远卡 Ghidra。三提议解决的是"静态知识供给"，不是"能力边界"。
