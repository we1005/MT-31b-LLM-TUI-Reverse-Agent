# 攻击机制图谱 —— 签名绕过 / 判定恒真化 / Dex2C原生化 / 免Root注入 / 加固壳 / 去广告

> 一句话定位：把 99 份 mod APK 只读取证审计中反复出现的 7 类攻击手法，逐个拆成"原理 + 静态指纹(可 grep 的类名/so名/字符串) + 如何确证 + 静态能走到哪/到哪为界 + 真实样本"，供本地模型审计新 APK 时按图索骥、按证据分级下结论。

> **合规声明**：纯防御 / 取证视角。本文只讲"审计员如何认出这种手法"与"防御方如何堵"，**不提供任何可直接复用的再破解步骤、脚本或 patch 配方**。凡是可能被误用为"怎么改这行就解锁"的具体操作序列，一律略去或改写为"审计如何识别"的判据。

## 0. 怎么用这份文档

**证据分级铁律**（所有结论都要按这三档标注，别自己加戏）：

| 级别 | 含义 | 何时能标 |
|---|---|---|
| **确证** | 直接读到字节码/字符串/文件，逻辑闭环 | smali 指令、硬编码字符串、文件路径确实存在 |
| **推断** | 有间接证据支持但未逐字节验证 | 符号名、时间戳、同批次交叉印证 |
| **静态上限** | 加密/原生化/VM化导致读不到，如实说明白，不瞎猜 | Dex2C native 桩、加密壳、Dart AOT、控制流平坦化到成本过高 |

**审计 30 秒建图顺序**（拿到新 APK 先按这个走一遍，再深入对应机制章节）：

```
1. apksigner verify --print-certs        → 判断重签名 + 签名方案(v1/v2/v3) + 证书DN
2. unzip -l 全量时间戳                     → "整体重打包"(全部归一) vs "定点dex补丁"(仅改动条目新时间戳)
3. grep AndroidManifest:
   - <application android:name>            → 是否被替换为陌生包名
   - android:appComponentFactory           → 免Manifest改Application的常见入口(§5)
   - 陌生 <provider>/<service> (尤其带 :daemon / initOrder 高值) → 注入引导点
4. 全局搜索 .super 继承链变化              → "移花接木"：Manifest 没改，但某基类(如 MultiDexApplication)的
                                             父类被换了(§2 典型手法)
5. 找标记目录/文件(工具指纹，见下表)      → 直接定位是谁的工具链
6. lib/*.so 与 assets/*.so 文件名 + strings → Hook引擎/Dex2C/加固壳库名比对(§4 §5 §6 速查表)
7. 对每个疑似判定方法读 smali opcode      → 按§3 六种恒真化子模式分级判断
```

**工具指纹速查表**（先 `unzip -l`/`find` 这些路径，一眼定位工具链）：

| 路径/文件 | 归属工具 | 含义 |
|---|---|---|
| `assets/protected_by_np/ApkDex2c_*.txt` | NP管理器 Apk-Dex2C | Dex2C 原生化完成标记，内含版本号+时间戳 |
| `assets/protected_by_np/ApkDex2CPro_*.txt` | NP管理器 Apk-Dex2C-Pro | 同上，Pro 版命名 |
| `assets/protected_by_yj/By.txt` | 云镜(yjaq.xyz) | 商业加固代工，内容含"魔改Dex2c/魔改Vmp/环境检测/frida注入" |
| `assets/SignatureKiller/origin.apk` | MT管理器"过签名校验" | 内嵌原始APK备份，配合 `bin/mt/signature/*` |

## 一、机制①：重打包 + 自签重签

**原理**：几乎所有样本的第一步都是"反编译(apktool/jadx/MT管理器/NP管理器) → 改字节码/资源 → 回编译 → 用模组作者自己的私钥重签名"。原开发者签名链必然被破坏。

**静态指纹判据**：

| 现象 | 解读 |
|---|---|
| `apksigner verify --print-certs` 证书 DN 非原厂已知信息(占位符如 `C=US`/`CN=L`/单词字典如 `CN=grass`) | 自动生成的一次性重签名证书 |
| v1=false 但 v2/v3=true，`META-INF/` 下仍有旧 `.RSA/.SF`残留但校验失败 | "回编译发生在v1签名之后"，典型二次打包工具链指纹 |
| `unzip -l` 全部条目时间戳归一(如 `1980/1981-01-01`) | apktool 全量反编译回编特征 |
| 仅少数条目(manifest/被改dex/签名文件)有真实近期时间戳，其余保留旧时间戳 | **定点 dex 补丁**(MT/NP管理器直接编辑 dex 后局部回写)而非 apktool 全量回编 —— 两者攻击面不同，后者改动范围通常更小更隐蔽 |
| 同批次多个不同 App 命中**完全相同**的证书 SHA-1/DN | 同一模组作者固定 keystore，可跨样本互证身份、建黑名单 |
| `META-INF/MANIFEST.MF` 保留 `Built-By: Signflinger`、`app-metadata.properties`(AGP版本)、`version-control-info.textproto`(git revision) | 说明dex/资源仍是官方构建产物，只是**签名区块被替换**，非重新用AGP全量编译 |

**样本**：几乎全部 99 份报告适用；典型强指纹见 `扫描王全能宝-6.8.69会员版-黯笙.md`(腾讯乐固原厂壳+同批次同证书交叉印证)、`拷贝漫画-3.0.9去广告版v2-鹿蜀.md`(证书DN全字段填"L")。

**静态上限**：签名本身不涉及静态上限，但"具体重签工具是MT管理器界面操作还是脚本化流程"通常只能推断，无法从产物逐字节区分。

**加固要点**：v1/v2/v3 全启用 + 服务端对非官方证书指纹拒绝下发内容/会员态；接入 Play Integrity/国内等效完整性校验做二次核验。

## 二、机制②：签名校验绕过

### 原理

多数原 App 会做"运行时自检自身签名，检测到被篡改/重签名就拒绝运行/自毁"。破解者重签名之后必须先**干掉这层自检**，否则改包直接崩溃或触发风控。这是"先有②才能有其他机制生效"的前置步骤——审计时看到某处有"检测到重签名就 `killProcess`/`exit`"的代码，**几乎必然存在配套的签名绕过注入模块**，两者要联动找。

### 核心手法：反射伪造 `PackageManager` 返回值

**共同判据**（不论哪个变体，核心都是这四招的组合）：

1. 反射替换 `android.content.pm.PackageInfo.CREATOR`(`Parcelable.Creator`)字段为自定义实现
2. 清空/替换 `PackageManager.sPackageInfoCache`、`Parcel.mCreators`/`sPairedCreators` 三处缓存
3. `<clinit>` 内硬编码一份 Base64/DER 编码的**原开发者真实证书**，伪造返回值时用它顶替
4. 部分变体额外做**文件系统层**路径重定向(`hookApkPath`)，对付不走 Java API、直接读 APK 文件字节做签名块校验的更底层检测

### 已见的四个变体（同源不同封装，别只认一个类名）

| 变体 | 典型类名/包名 | 强指纹字符串 | 样本 |
|---|---|---|---|
| **ApkSignatureKillerEx**(原始开源项目) | `bin/mt/signature/KillerApplication`、`com.android.bin`、`bin.mt.signature.<自定义名>` | 硬编码 `URL="https://github.com/L-JINBIN/ApkSignatureKillerEx"` | `扫描王全能宝-6.8.69会员版-黯笙.md`、`喵呜漫画-1.2.7去广告版-zhou45.md`、`小月历-GP-1.77.364.GP解锁版-NURIK.md` |
| **MT管理器专属键名**(比泛框架归因更进一步) | `bin.ghost.yrf`、`bin/ghost/*` | 硬编码字符串 `"mt.signature.killer.path1"`/`"mt.signature.killer.path2"` | `DevCheck系统硬件检测-6.46专业版-youarefinished.md`(专门适配 PairIP 保护) |
| **SRPatch**(config驱动、Application劫持透传) | `com.srp.patch.Init`/`Patch`/`com.Share.AppInfo` | `assets/patch/SRPatch_config.json` 内嵌伪造证书+`apkSize`；字段 `sFakeSignature`/`sPmsProxyMethod="IBINDER_PROXY"`/`ORIGINAL_CREATOR` | `追剧喵-4.0.4去广告版-zhou45.md`(同批次 `追剧达人` 复用同一套组件) |
| **srpatchv3**(SRPatch 后续版本) | `com.srpatchv3.Application` | 反射清空 PackageManager 签名缓存 + 硬编码原厂证书 | `微商助手-3.6.3会员版-鹿蜀.md`、`微粉猫-2.4.6会员版v2-鹿蜀.md` |

### "移花接木" —— 零 Manifest 改动的隐蔽接入手法（重点！）

不要只 grep `<application android:name>` 就下结论"没被劫持"。**典型手法是改写某个必经基类的 `.super`**，例如把 `androidx/multidex/MultiDexApplication.smali` 的 `.super Landroid/app/Application;` 改成 `.super Lbin/mt/signature/KillerApplication;` —— Manifest 里声明的 Application 类名**完全没变**，因为它继承自 MultiDexApplication，而 MultiDexApplication 的父类被换了。diff 面极小(只改一行)，是 MT 管理器该功能的标准接入方式。

**审计判据**：不能只看 Manifest 声明的 `android:name`，必须**全局搜索所有 `.super` 声明**，尤其是常见基类(`MultiDexApplication`、`AppCompatActivity`等)的父类是否被改成了陌生包名。

### 因果链验证范式（黄金样本）

`扫描王全能宝` 报告完整重建了这条因果链，是理解"为什么必须有②"的最佳参考：
```
原厂 MyApplication.onCreate()
  → 调用 TrackParamsBean.isGenuine()
      → SignCheck.check(): 取编译期硬编码的证书指纹(SHA1/SHA256/MD5)
                            与 PackageManager.getPackageInfo(pkg,GET_SIGNATURES) 运行时签名比对
      → 若不等 → Process.killProcess(); System.exit(0)  // 原厂反破解自毁
--- 破解者注入的 KillerApplication.killPM() 让 getPackageInfo() 恒定返回"原厂证书" ---
  → isGenuine() 恒为 true → 自毁分支永不触发
```

### 静态上限
- native 层 `libSignatureKiller.so`/`libyrf.so`/`libSRPatch.so` 内 `killPM`/`hookApkPath` 的完整原生实现通常未做反汇编，只凭符号/字符串推断行为。
- 判断"这段代码是原厂自带反破解逻辑、还是同样受 Dex2C/VM保护读不出"需结合§5 一起看，不要孤立下结论。

### 加固建议（精简版，通用于本机制全部变体）
- 不要仅依赖 `PackageManager.getPackageInfo(...).signatures`：该接口可被同进程反射 Hook 完全欺骗（本节即是铁证）。
- 签名/完整性校验放 native 且多点交叉验证(APK自身v2/v3签名块字节直读、文件哈希)，校验结果**参与业务解密**而非仅 if 分支。
- 检测 `PackageInfo.CREATOR`/`Signature.CREATOR` 等 `Parcelable.Creator` 字段是否被反射篡改；检测常见基类 `.super` 链是否异常。

## 三、机制③：判定恒真化

### 原理
把 `isVip()`/`isPro()`/`checkLicense()` 这类布尔判定方法的字节码，直接替换/追加为"无视任何输入、恒定返回 true"。这是本批次**出现频率最高**的破解手法（会员/VIP 25 例、高级/Pro 29 例中大量属此类）。

### 六种子模式（按 smali opcode 特征分类，附代码样例）

**(a) `.locals 0` + 复用 `this` 寄存器 —— 自动化工具指纹**
```smali
.method public isProBlocking()Z
    .locals 0
    const/4 p0, 0x1
    return p0
.end method
```
人工手写通常会写 `.locals 1 / const/4 v0,0x1 / return v0`；直接复用/覆盖 `p0`(即 `this`) 且 `.locals 0` 是**自动化"方法返回值改真"工具**的典型产物，非人工逐行改写。样本：`Photo-Lab照片编辑-3.13.108专业版-derrin.md`。

**(b) `.locals N` 保留 + `const/4 vX,0x1; return vX`，原逻辑变死代码**
```smali
.method public getMember()Z
    .locals 4
    const/4 p0, 0x1
    return p0
    ...（原读取 SharedPreferences/服务端同步逻辑仍在dex里，但因提前return永不可达）
.end method
```
样本：`天气通-9.46会员版-黯笙.md`(`UserInfoDataStorage#getMember()`)、`一木记账-6.5.6会员版-黯笙.md`(`User#isVip()`)、`今日水印相机-4.2.2会员版-PlatinumMods.md`、`强制转屏-v29.1.2-解锁高级版_@PJAPK.md`。
**反证对照技巧**：同一 APK 内找同类的"姊妹方法"(如 `ThemeChild.isVip()`)若仍是正常字段读取，两相对比即可确证"只有这一个方法被针对性改写"。

**(c) 三元恒真 `?true:true`（反编译器暴露的双分支收敛）**
```java
// jadx 反编译结果，两个分支都是常量 true
return aVar.b().f10624a > 0 ? true : true;
```
对应 smali 层面是"一处 `SharedPreferences.getBoolean(key, true)` 缺省值被从 `false` 改成 `true`" + "另一处整型缓存分支缺少写 `false` 的指令，导致殊途同归都读到方法开头就设好的常量寄存器"。**判据**：jadx 渲染出"两个分支返回同一常量"的三元表达式，本身就是"分支被阉割到只剩一半"的强烈信号，务必回读对应 smali 而非只看反编译Java。样本：`小月历-GP-1.77.364.GP解锁版-NURIK.md`(`Lei/k;->y()`，联动 `ThemePageKt` 同步解锁付费主题)。

**(d) SharedPreferences 缺省值篡改**：`getBoolean("remove_ads"/"is_vip", true)` —— 正常新装/未登录应默认 `false`，缺省值被反过来。判据：grep 常见 key 名(`remove_ads`/`is_vip`/`is_pro`/`premium`) 的 `getBoolean` 调用第二参数是否为可疑的 `true`。

**(e) 参数寄存器覆盖(setter 劫持)**
```smali
.method public final c(Z)V   # setter，原意写入调用方传入的布尔值
    const/4 p1, 0x2          # ← 残留的死指令(先写了一次)
    const/4 p1, 0x1          # ← 真正生效的覆盖(不论调用方传true还是false，都变成1)
    iput p1, p0, Lxx;->m:Z
.end method
```
判据：同一寄存器被连续两条 `const/4` 赋值(第一条恒为死代码)，是"补丁工具插入新指令但未清理旧指令"的残留特征；效果是"重置为未购买"的调用反而把状态写死为已购买。样本：`强制转屏-v29.1.2-解锁高级版_@PJAPK.md`(`Feature.c(Z)V`)。

**(f) 孤儿类/无引用内部类 —— 证明原方法体被摘除**
判据：编译器为原方法体生成的内部类(如协程 lambda `Xxx$isProBlocking$1`)在全工程 grep 引用命中为 **0**——原方法体被整体摘除后，其编译产物变成"永久孤儿"，是"这里曾经有真实逻辑、现在被删空"的确凿旁证。样本：`Photo-Lab照片编辑-3.13.108专业版-derrin.md`。

### 判据清单（审计时按此逐项过一遍）
- [ ] 目标方法 `.locals` 数与方法体指令数是否明显不匹配（`.locals 0` 却有分支逻辑，或 `.locals 4` 却只有2条指令）
- [ ] 是否存在"姊妹方法"可做反证对照
- [ ] jadx 反编译是否出现 `?true:true`/`?false:false` 这类双分支收敛的三元表达式
- [ ] 编译器生成的内部类(Lambda/匿名类)是否变成孤儿（全局引用数=0）
- [ ] 同一寄存器是否被连续多条 `const/4`/`const-string` 赋值（残留补丁痕迹）
- [ ] `getBoolean(key, default)` 的 default 是否与业务语义相反

### 静态上限
只要方法体本身能被 baksmali/jadx 正常反编译（未被§4 Dex2C 原生化、未被§6 加固壳加密），本机制**几乎总能确证到具体指令级别**——是本图谱七个机制里静态可视性最好的一类。一旦目标方法同时命中"native 化"或"整体加密"，立刻转入§4/§6 的判据与上限。

### 加固建议
- 关键判定不要用"读标志位→直接return"的可平凡改写形态；引入运行时完整性自校验（关键方法哈希、寄存器/返回值二次校验）。
- 权益判定上移服务端，客户端仅凭短时效签名令牌展示。
- 默认分支 fail-closed：网络异常/缓存缺失/未知状态时默认**拒绝**而非放行。

## 四、机制④：Dex2C / 方法原生化隐藏 patch

### 原理
把"关键 Java 方法"整体编译成 ARM/x86 机器码，Dalvik 侧只留一个跳到 native 的桩方法（方法体在 smali 里显示为 `native`），原始 Java 字节码从产物里彻底消失。**这是本批次让静态分析真正卡壳的核心手法**——常与§2/§3 组合使用：先在明文里定位/改写判定逻辑，再用 Dex2C 把改动点原生化，使"改了什么"从静态层面不可读，只剩"改动集中在哪个类"这个信息。

### 四个变体识别表

| 变体 | 归属 | 标记文件/字符串 | 承载 so | 样本 |
|---|---|---|---|---|
| **NP管理器 Apk-Dex2C** | NP管理器内置 | `assets/protected_by_np/ApkDex2c_<hash>.txt`(含`Function: Apk-Dex2C`/`Version`/`ProtectTime`) | `libstub.so`，符号 `np/dcc/protect/EntryPoint` | `4K影视-6.0.2会员版-zhou45.md` |
| **NP管理器 Apk-Dex2C-Pro** | NP管理器 Pro版 | `assets/protected_by_np/ApkDex2CPro_<hash>.txt` | 自定义命名(如`libcxapkmod.so`)，`JNI RegisterNatives`绑定入口类含 `<clinit>`调用`registerNativesForClass` | `快对AI-7.2.2会员版-辰夕.md` |
| **云镜(yjaq.xyz) 魔改Dex2C/VMP** | 第三方商业代工，**破解者自己花钱买的"保护我这次patch"服务** | `assets/protected_by_yj/By.txt`(明文含"魔改Dex2c/魔改Vmp/高强度环境检测/frida注入/so文件加固") | 视具体订单而定 | `红果免费短剧-7.2.8.32会员版-鹿蜀.md` |
| **YJ-Dex2C**(疑似原厂内部代号，非破解方新增) | **原厂**加固/防篡改(不要误判为破解手法本身) | smali `.source "YJ-Dex2C"` 注解 + 方法体声明 `native` | 与业务dex同期 | `喵呜漫画-1.2.7去广告版-zhou45.md`(`MyApplication.onCreate()`) |

**关键辨析：谁在用 Dex2C？——原厂 vs 破解者，两种含义完全相反**：
1. **原厂自带 Dex2C/VMP** = 保护正版逻辑不被静态分析，破解者遇到时的应对通常是**绕开而非硬破**（转去做§5 运行时Hook，而非试图逆出原生码里的逻辑）。
2. **破解者自己调用 Dex2C** = 把**自己新写的 patch 逻辑**（如"改会员判定"、"注入的Hook桩类"）原生化，目的是防止审计员/同行二次逆向出他的改动手法。

**判据**：看 `.source` 注解、`assets/protected_by_*` 标记文件的时间戳——若与整体重打包时间戳一致 → 破解者行为；若与原始构建期时间戳一致（早于重签名时间）→ 大概率原厂自带。

### 定位"被 Dex2C 化的方法藏在哪个业务域"的技巧

即使方法体本身读不到，`libstub.so`/`libcxapkmod.so` 等承载 so 的**字符串表**仍会明文暴露被转换方法所属的类名/字段名/字符串常量（因为符号引用、日志字符串、Retrofit 反射用的类名字符串通常不会被一并加密）。审计流程：
```
strings libstub.so | grep -iE "vip|pro|ad|config|splash|user" 
  → 得到一批高辨识度类名(如 VipAdConfig/SystemAdConfig/SplashAc/CmsUser)
  → 交叉 smali 里对应类的方法体是否全为 native
  → 即可"定位到哪个类被改了"而不需要读出"具体怎么改的"
```
样本 `4K影视` 报告示范了这个技巧：从 `libstub.so` 字符串反推出 `VipAdConfig`/`SystemAdConfig`/`SplashAc`/`CmsUserInfo$CmsUser` 是破解目标面，但明确标注"未能直接阅读被改动的字节码"。

### 整体 Activity/大范围原生化(比单方法更激进的变体)

`快对AI` 样本显示：不只是单个判定方法被 Dex2C，而是**整个 `MainActivity`(含所有生命周期方法、内部类桥接方法)全部转 native**，原始 dex 字节码整体消失。全仓库搜索绑定函数(如 `Lcxapkmod0/DtcLoader;->registerNativesForClass`)引用可以枚举出所有被此手法覆盖的类——这是审计能做到的**上限**：知道"哪些类被转了"，但转换前的具体逻辑差异（即"原始逻辑 vs patch 后逻辑"的 diff）无法给出。

### 静态上限（本机制最核心的诚实边界）
- **原始 Java 字节码已不存在**，`nm -D`/`strings` 通常无导出符号（strip后），无法给出"被替换指令的精确原始语义"。
- 只能确证：(1) 这里被 Dex2C 化的事实；(2) 承载 so 字符串暴露的目标类名/字段名范围；(3) 该类/方法此前在业务域中的角色（会员/广告/开屏等）。
- **不能**给出"原判定逻辑具体怎样被改写成什么"的逐指令 diff——需要动态调试(Frida hook)或原生反汇编(IDA/Ghidra)才能进一步坐实，这明确超出只读静态审计范围。**遇到此类情况应如实标注"静态止步于此"，不得据"没搜到明文逻辑"就臆断具体改法。**

### 加固建议
- 关键符号（`VipAdConfig`/`getVip_ad_config`/`isVip`等高辨识度类名/方法名）即使做了 Dex2C，仍可能从 so 字符串泄漏目标面——应叠加字符串加密。
- Dex2C 只解决"静态读不到指令"，不解决"运行时可被 Hook 拦截调用"——需配合反 Hook/反注入自检（见§5加固建议）。
- 完整性/签名自校验要"致命且多点、结果上移"：本批多个样本证明"壳/Dex2C都在但校验点单一非阻断"，改包依然能跑。

## 五、机制⑤：免 Root 注入模块 + ART Hook 引擎

### 原理
当业务逻辑因为§4(Dex2C)或§6(加固壳)难以直接静态打补丁时，破解者转而在**运行时**通过 ART 方法级 Hook 引擎拦截目标方法调用、替换返回值/行为，完全不触碰原始（可能加密/原生化的）dex。这类手法对"混淆强度""加固等级"基本免疫——因为它不需要理解目标代码的具体实现，只需要能在调用点截胡。

### 三种引导入口（如何在早于业务代码的时机拿到控制权）

| 引导方式 | 识别判据 | 样本 |
|---|---|---|
| **`android:appComponentFactory` 劫持**(标准做法) | Manifest 中该属性指向陌生类；系统实例化四大组件前必先调用其 `instantiate*` 方法 | LSPatch标准：`org.lsposed.lspatch.metaloader.LSPAppComponentFactoryStub`(`微博-16.6.3...md`)；自定义封装：`bfa.eae.Im`(`喵呜漫画`)、`occu.jr.f.OOoooOOOoO`(`囧次元-1.5.8.0去广告版v16-zhou45.md`，O/o大小写混淆命名) |
| **清单外 ContentProvider 引导**(比appComponentFactory更隐蔽) | Manifest新增陌生 `<provider>`，`android:initOrder`设高值(如100)，包名常伪装成应用中文名或系统风格 | `PineInitProvider`(`android:initOrder="100"`，包名`com.小熊电子证件照`)——见`小熊电子证件照v3.2.0.0高级版_@PJAPK.md` |
| **VirtualAPK 风格插件容器 + `:daemon` 附属进程** | 新增 `<provider authorities="...VirtualAPK.Provider">`、`<service>` 监听自定义广播，运行在独立`:daemon`进程 | `囧次元-1.5.8.0去广告版v16-zhou45.md`(配合17MB `groovy_shell.apk`脚本化插件包) |

### ART Hook 引擎库名速查表（`/proc/self/maps` 或 `assets/*/lib*.so` 里找这些）

| so 文件名 | 对应开源/商业引擎 | 强指纹符号 |
|---|---|---|
| `liblshook.so` | LSPlant(LSPosed团队ART方法Hook引擎，LSPatch核心依赖) | `lsplant::v2::Hook/UnHook/IsHooked`、`ArtMethod`/`ClassLinker`/`Instrumentation` |
| `libpine.so` / `top/canyie/pine/**` | Pine(canyie，ART内联Hook) | `Pine.smali`/`Pine$HookHandler`/`MethodHook`/`MethodReplacement`/`entry/Arm64Entry` |
| `libEpic_Svc.so` / `Epic/AV`,`Epic/Jni` | Epic(独立ART Hook框架) | `Hooker`/`HookerFrame` |
| `libaliuhook.so` / `aliucord/hook` | 阿里 AliuHook | — |
| `liblsplant.so` | 同LSPlant的另一命名变体 | 同上 |

判据：出现任意一个即可确证"存在ART Hook引擎注入"；同时出现3-4个(如`assets/Epic_so/`下按ABI各自打包 libEpic_Svc+libaliuhook+liblsplant+libpine)是**多引擎兼容框架**的典型特征——说明是预制的可复用注入模块，而非单一手写Hook。

### Xposed 兼容层 + 规则化描述（降低"每个App都要重新编译Hook逻辑"的成本）

- `de/robv/android/xposed/**`(标准Xposed API：`XposedBridge`/`XposedHelpers`/`XC_MethodHook`/`XC_MethodReplacement`)常与上述引擎搭配，用于**免Root加载标准Xposed模块**。
- 部分样本内嵌**规则/脚本引擎**使同一套原生Hook逻辑可跨App复用而不必重新编译：`org/luaj/**`(Lua虚拟机，`小熊电子证件照`)、`groovy_shell.apk`(Groovy脚本插件包，`囧次元`)。判据：看到 `luaj`/`groovy` 相关包 + 大量 `native` 声明的 `stub$N.smali`(每个对应一个Hook目标)，即为"规则驱动式通用Hook框架"。

### LSPatch 集成模式的完整指纹（最标准化、最易识别的一种）

```
assets/lspatch/config.json          # 关键字段: useManager(false=集成模式)/sigBypassLevel(2=最高级签名伪造)/originalSignature
assets/lspatch/loader.dex
assets/lspatch/modules/<模块包名>.apk # 真正的功能模块(如"微博猪手" com.skyhand.sinahelper)
assets/lspatch/origin.apk            # 内嵌的完整原版APK(可独立验签，常显示"未被篡改"，因为改动都在运行时Hook层)
assets/lspatch/so/*/liblspatch.so
```
**审计关键洞察**：`assets/lspatch/origin.apk` 逐字节验签通过 ≠ App没被破解——它只证明"业务dex本身没被静态改写"，所有行为差异来自运行时Hook。**外层容器签名(通常占位符DN)** 与 **内嵌origin.apk签名(可能是官方证书)** 要分开验证，别把两者混为一谈。样本：`微博-16.6.3-内置猪手2.5.3-348模块_Kunkka.md`(`sigBypassLevel:2`即"进程内Hook签名查询API，让被Hook的App自检时仍看到内嵌的原厂证书")。

### 静态上限
- Hook 模块本体通常经商业级混淆（控制流平坦化 + 字符串加密，`微博`样本约789个class被打散进60+个`pNNN`重命名包），**无法逐一枚举具体Hook了哪些类/方法**——需要反混淆或动态插桩(Frida/Xposed日志)观察实际Hook点，明确超出静态范围。
- Hook 回调体若声明为 `native`(逻辑在so里)，且 so 做了字符串加密/无导出符号，则连"Hook目标类名"都读不出（`小熊电子证件照`样本：`libfuck.so`扫描6151条字符串无一命中`isVip`/`Billing`等特征词）。**这种情况下唯一能确证的是"存在此类Hook机制"，不能确证"具体拦截了什么"。**

### 加固建议
- 检测常见Hook引擎特征库(`liblspd`/`liblsplant`/`libriru`/`libxposed`/`liblshook`/`libpine`/`libEpic`/`libaliuhook`等命名模式)是否出现在 `/proc/self/maps`。
- 检测 `appComponentFactory` 是否被篡改为非预期类；检测清单外的陌生 `ContentProvider`(尤其`initOrder`异常高)。
- 检测 Xposed兼容类(`de.robv.android.xposed.*`)是否可被 `Class.forName` 命中。
- 关键判定不要只放纯Java层单点方法——对混淆/Hook免疫的手法就是"改运行时行为而非改字节码"，纵深防御需要原生层反注入自检。

## 六、机制⑥：加固壳（爱加密/360/云镜VMP）与"壳 ≠ 防篡改"

### 原理
商业加固壳的核心手段是把业务 dex 加密，运行时解密后才在内存中加载执行，目的是让静态反编译拿不到明文代码。**本批样本反复证明：壳能挡住"改dex字节码"这条路，但完全挡不住"绕过壳、直接在运行时对已解密的Java方法做ART层Hook"这条路**——这是审计给客户最重要的一条反直觉结论。

### 常见壳识别表

| 壳产品 | 识别锚点 | 加密载荷位置 |
|---|---|---|
| **爱加密(Ijiami/天宇信息)** | `AndroidManifest.xml`: `android:name="com.stub.StubApp"`；`classes.dex`仅含`com/stub/StubApp`+`com/tianyu/util/{a,DtcLoader,Configuration}`4个类，无业务包 | `assets/ijiami_<id>.VData`(纯二进制)；`assets/libjiagu_a64.so`等藏在assets而非lib(规避对lib/目录的静态扫描) |
| **360加固(Jiagu)** | `com.stub.StubApp` 同名(注意：爱加密与360均可能用`StubApp`类名，需结合`libjiagu*`/`com.tianyu.util`等伴生特征区分厂商) | `libjiagu_a64/x64/mips.so`、`libapk_guard_core.so` |
| **EPIC/ArmEpic DEX加密壳** | `classes.dex`仅2-3KB，只含`Epic/ProtectApp`(`extends Application`)，`SoLoader()`反射加载`libEPIC.so` | `assets/EPIC/*.Epic`(高熵，文件头非标准dex/zip头，如`1011 0c7e 4447 4174…`) |
| **云镜(yjaq.xyz) VMP** | 见§4速查表，`assets/protected_by_yj/By.txt` | 视具体加固订单 |

### 证据链范式：如何证明"壳没挡住改包"

标准论证结构（`拷贝漫画`、`4K影视`、`喵呜漫画`三份报告均是这个范式的优秀样本）：
```
1. 确证壳存在(StubApp/加密载荷/壳loader类)
2. 确证壳内部自带签名自校验/反调试(strings扫描壳so，常见 GET_SIGNATURES/crc32/ptrace/TracerPid/frida-server 等字符串)
3. 但重签名+改包后的APK仍能正常运行 → 说明壳内自校验"要么不致命、要么仅上报、要么被一并绕过"
4. 找到破解者自带的、与壳供应链无关的第三方Hook引擎(如 liblshook.so 含lsplant符号) + 混淆脱壳工具残留
   (如 libDexHelper.so，社区内存脱壳工具名，Arkari/Hikari-LLVM混淆编译——商业壳没有理由自带"破解自己"的工具，
    这组合本身就是破解者工具指纹被一并打进最终产物的证据)
5. 结论：壳仅加密了"字节码可读性"，未能阻止"内存里已解密的Java方法被ART层Hook拦截"
```

**关键佐证**：广告SDK的Manifest声明(`<provider>`/`<receiver>`)、素材资源、原生库**全部原样保留、一个没删**——这是"运行时Hook拦截"而非"静态删代码"的强旁证：若走静态删代码，通常会连带清理Manifest里对应声明（否则留着没用还占体积）；现在"声明整整齐齐留着但不生效"，更像是方法调用层面被"截胡"。

### 静态上限
- **无法定位具体被Hook的类/方法**：目标信息大概率存在于加密的业务dex内部（本身就是审计从始至终读不到的部分），或被高度混淆的自定义Hook逻辑so内部（如`liblssec.so`用Hikari-LLVM控制流平坦化）。
- **无法确认Hook触发点**：若可见的壳loader smali文件中未发现对Hook引擎so的`loadLibrary`调用、也没有其他so通过`DT_NEEDED`依赖它们，说明触发逻辑本身也藏在加密业务dex内——这部分永远是黑盒，除非做内存dump/动态插桩。
- **壳归属存疑时不要乱认**：壳可能是原厂自带（用于保护正版逻辑），也可能是破解者为了防止"自己的patch被二次逆向"而重新加壳——两种解释需结合时间戳（壳文件时间戳与整体重打包时间是否一致）区分，静态无法100%排除任何一种。

### 加固建议
- 加固壳需与**签名校验、反Hook、服务端裁决协同**，单独上壳无效（本批多起证据）。
- 升级到指令级虚拟化(VMP)而非仅DEX加密壳，让"解密后即为明文Java方法"这条路径的收益大幅降低。
- 增加反Hook/反注入自检：扫描`/proc/self/maps`中已知Hook引擎特征库；检测关键ART方法(`ArtMethod`/`Instrumentation::Invoke`)入口字节是否被inline hook篡改。
- 关键业务判断不要只依赖单一native方法调用结果，建议多点校验+服务端二次确认。

## 七、机制⑦：去广告的两条路

### 路 1：静态 no-op / 删组件（改的是可读dex，攻击面小）

**特征**：目标App**未加固**或加固强度不足以拦截"直接改smali"，破解者选择最省事的路径——直接找到广告SDK初始化/展示方法，清空方法体。

**判据（教科书级样本 `笔趣阁纯净版-1.0.5去广告版-LWELY.md`）**：
```smali
.method public static init()V
    .locals 1          # ← 关键异常点：声明了1个寄存器却没有任何指令使用它
    return-void
.end method
```
方法体保留 `.locals 1` 却只剩 `return-void`，若本就是空方法编译器应输出 `.locals 0`——**这是"原方法体被删除、仅塞回一条return-void"的手工阉割残留特征**，与§3(a)的自动化"改真值"工具残留正好相反的方向（一个是塞常量真值，一个是塞空返回）。

**佐证清单**：
- [ ] 全部dex内该SDK的init调用次数 = 0(如`grep -c "TTAdSdk;->init"`)
- [ ] 该初始化回调的匿名内部类(如`Holder$1`)变成孤儿（`EnclosingMethod`指向已被清空的方法，但全局无引用）
- [ ] 调用方(如开屏Activity)仍在调用该方法，但因方法体已空转，效果上"广告拉取静默失败"
- [ ] **关键区分点**：业务门控方法(如`isHideAd()`/VIP到期判定)本身**未被改动**——说明破解者选择"让广告源发不出来"而非"改判定恒真"，App其余功能与流程完全正常

**首方(自建)广告位的特殊情况**：若App广告不依赖第三方SDK而是自建组件(如`XuAdStartView`/`XuAdPauseView`，服务端下发内容驱动显示)，且未发现任何字节级diff证据，审计应如实标注"最可能的作用面是(a)拦截字段清空/(b)短路挂载调用/(c)网络层拦截CDN请求"三选一或组合，**不能确证是哪一种**——因为没有原始版本做逐字节diff。样本：`好好看影视-3.4.0-无广告.md`。

### 路 2：运行时 Hook 广告 SDK 方法空跑（配合§5引擎，改的是加固/Dex2C保护的目标）

**特征**：目标App已加固(§6)或关键路径已Dex2C(§4)，静态改dex成本高/不可能，破解者转而部署§5的ART Hook引擎，在广告SDK方法调用点做"拦截替换返回值/行为"，SDK本体、Manifest声明、素材资源**全部保留不动**。

**判据**：
- [ ] Manifest里广告SDK的Provider/Receiver/权限(如`TT_PANGOLIN`穿山甲权限)完整保留
- [ ] 广告相关so库(`libpanglearmor.so`等)原样存在
- [ ] 同时命中§5的Hook引擎指纹(liblshook/libpine/libEpic等)
- [ ] 无法在可读smali里找到"某广告方法被恒假返回/no-op"的直接patch证据

**两条路的鉴别速查表**：

| 现象 | 路1(静态no-op) | 路2(运行时Hook) |
|---|---|---|
| 广告SDK方法体 | 可读smali中直接被清空/return-void | 方法体正常(甚至Dex2C/加密不可读) |
| Manifest/资源 | 通常SDK声明仍保留(未必删除) | 必然完整保留 |
| 是否伴随Hook引擎(liblshook/pine/Epic) | 通常没有 | 必然有 |
| 前置条件 | App未加固或加固弱 | App已加固(§6)或关键类已Dex2C(§4) |
| 典型样本 | `笔趣阁纯净版-LWELY` | `喵呜漫画-zhou45`、`拷贝漫画-鹿蜀`、`囧次元-zhou45` |

### 静态上限
路1若定位到具体清空方法即为确证级；路2的"具体Hook了SDK哪个方法"通常不可确证(见§5静态上限)，只能确证"存在Hook机制+SDK资源保留"这一组合特征，据此做**中高置信推断**而非逐指令确证。

### 加固建议
- 不要把"是否展示广告"这类关键判定放在能被`AppComponentFactory`/通用Hook引擎轻易接管的纯Java层单点判定上。
- 广告位配置(是否展示/哪家SDK/频次)由服务端下发并可远程收紧；广告曝光/点击做服务端异常检测(如同一设备长期0曝光但功能正常，可能是被Hook拦截广告请求的信号)。

## 九、总加固清单（汇总，防止各机制建议重复；新增本专题发现的检测点标 ★）

**客户端**
1. 权益判定(isVip/isPro/entitlement)不放在客户端可平凡改写的单点布尔判断上；关键路径避免"读标志→直接return"形态。
2. 签名/完整性校验放native、多点交叉验证(v2/v3签名块字节直读)，结果**参与业务解密**而非仅if分支。
3. ★ 全局检测 `.super` 继承链是否被篡改（不能只查`<application android:name>`，"移花接木"式注入manifest零改动，见§2）。
4. ★ 检测清单外的陌生ContentProvider(尤其`initOrder`异常高)与`appComponentFactory`是否指向陌生类（见§5）。
5. 反Hook/反注入自检：扫描`/proc/self/maps`已知Hook引擎特征库(liblspd/liblsplant/libriru/libxposed/liblshook/libpine/libEpic/libaliuhook)；检测Xposed兼容类是否可被`Class.forName`命中。
6. 加固壳升级到VMP/指令虚拟化级别，且与反Hook能力协同（★ 单独上DEX加密壳不足以防"绕壳、Hook已解密内存"的手法，见§6证据链）。

**服务端**
7. 会员/订阅/Pro/广告开关的最终裁决放服务端，客户端仅展示短时效签名令牌。
8. 授权令牌绑定设备完整性证明，服务端做重放与签名校验；默认分支fail-closed。
9. ★ 广告曝光/点击异常检测(同一设备长期0曝光但功能正常，可能是Hook拦截信号)。

**发行**
10. 接入Play Integrity/国内等效完整性校验，服务端强校验非官方签名/被篡改实例。
11. 建立已知破解证书指纹黑名单（★ 本批证明同一模组作者常年复用同一固定keystore，跨样本证书SHA-1可直接互证身份、批量打击）。
12. 渠道监测：★ 扫描`assets/protected_by_np/*`、`assets/protected_by_yj/*`、`assets/lspatch/*`、`assets/SignatureKiller/*`等工具指纹路径，可快速识别同源批量重打包分发。
