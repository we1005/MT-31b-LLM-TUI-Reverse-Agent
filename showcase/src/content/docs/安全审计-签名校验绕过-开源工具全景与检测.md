# 签名校验绕过 · 开源工具全景与检测(威胁情报)

> 回答一个审计/加固问题:手机端 MT 管理器把"过签名校验"做成一键,**PC/Mac 端有没有等价的开源工具?** 深搜 GitHub + 源码级机制研究得出结论,并给出**取证识别指纹 + 防御检测与加固**。
>
> **合规立场**:纯威胁情报 / 机制分析 / 检测与加固,面向"审计时认出用了什么 + 防御方怎么堵"。**不提供"用工具 X 给你的目标 APK 过签名"的操作步骤/命令**。文中工具名/仓库均为公开信息,且已在本项目 99 样本审计里作为指纹出现。

---

## 0. 直接结论:没有真正等价"MT 一键"的、当前可用的 PC 开源工具
源码级核实,PC 端"一键过签名"要么是**模板(要手动套)**,要么是**已停更/归档、只打得动老式校验**:

| 层次 | 代表 | PC 一键? | 现状 |
|---|---|---|---|
| **就是 MT 一键背后的模板本身** | `L-JINBIN/ApkSignatureKillerEx`(811★) | ❌ 安卓库/smali 模板,PC 要手动 apktool 反编译→塞 dex/so/asset→改 manifest→重打包重签 | 2023 初停更 |
| **唯一"真·单命令"经典派** | `ApkSignatureKiller`(2017,nkstool.jar)/ `Hax4us/Apkmod`(`--signature-bypass`) | ⚠️ 是单命令,但**停更 9 年/4 年**,只改 `PackageManager.getPackageInfo` 反射值,**对 v2/v3 签名块/API28+ signingInfo 无能为力** → 现代目标基本失效 | 事实废弃 |
| **最接近 MT 一键的 PC 工具** | `LSPosed/LSPatch`(9247★,`java -jar lspatch.jar`) | ✅ 真 PC jar、一条命令(解原签名→重签→改清单→注入 loader),含多级 sigbypass | **2023-12 官方 archived**;`JingMatrix/LSPatch` fork(3522★)仍活跃 |
| **生态里最"一键"的整合实现** | `SectionTN/ApkSignatureKill`(自称"used in MT Manager") | ❌ 是**安卓 App**(设备端整合 baksmali/dexlib2/AXmlDecoder/ApkSigner) | 一次性转储 |

**一句话**:PC 端"一键"**曾经被 LSPatch 短暂追平、随后归档夭折**;主线 ApkSignatureKillerEx 确实如 §九所述"要手动套模板";其余单命令工具都老到打不动现代签名方案。所以你 §九表格里"无一键"的判断成立,**LSPatch(及其活跃 fork)是唯一值得补充的"接近一键"例外**。

## 1. 三大机制流派(源码级)+ 检测指纹

### 流派 A:Java 反射伪造 PackageManager 返回值(最常见,本批 27 例)
- **机制**:注入一个 Application,在 `<clinit>`/`attachBaseContext` 里——① 反射把 `PackageInfo.CREATOR`(Parcelable.Creator)换成自定义实现,`createFromParcel` 里把 `signatures[0]` 和(API28+)`signingInfo.getApkContentsSigners()` 换成内嵌的**原厂证书**;清空 `sPackageInfoCache / mCreators / sPairedCreators` 三处缓存强制重走;或 ② 用动态代理整体顶替 `IPackageManager`(改 `ActivityThread.sPackageManager` + `ApplicationPackageManager.mPM`)。靠 `org.lsposed.hiddenapibypass` 绕 API28+ 隐藏 API 限制。
- **代表**:`ApkSignatureKillerEx`(`bin.mt.signature.KillerApplication`)/ 初代 `ApkSignatureKiller`(`cc.binmt.signature.PmsHookApplication`)/ `APKKiller`(aimardcr,JNI 下沉版)。
- **检测指纹**:类名 `bin.mt.signature.KillerApplication` / `cc.binmt.signature.PmsHookApplication` / `com.apksignaturekiller.HookApplication`;**未替换即暴露的模板占位串** `"### Signatures Data ###"`、`"### Applicaton Data ###"`(后者含拼写错,高置信);反射字段名 `sPackageInfoCache`/`mCreators`/`sPairedCreators`/`sPackageManager`/`mPM`;日志串 `"PmsHook success."`;`org.lsposed.hiddenapibypass` 存在本身即强信号;manifest `application android:name` 或 `MultiDexApplication.super` 指向上述类(**移花接木**:改 `.super` 而非改 manifest name)。

### 流派 B:native 文件重定向 / killOpen(更难挡,本批 srpatch/libyrf 系)
- **机制**:在 native 层用 **PLT/inline hook**(vendor 进 `iqiyi/xHook` 或 `bytedance/bhook`、`shadowhook` 源码)劫持 libc `open/openat/openat64`——当有代码(尤其**原生层完整性校验**、或走 `ApplicationInfo.sourceDir`/`/proc/self/maps` 自己读 APK 字节校验的)尝试读运行中 APK,把句柄**透明重定向到内嵌的干净原版**(`assets/SignatureKiller/origin.apk` / `hook.apk`)。专门对抗"不走 PackageManager、自己解析 APK 签名块"的更强校验。
- **代表**:`L-JINBIN/ApkSignatureKillerEx` 的 native 部分(`mt_jni.c` 内嵌 xHook,导出 `Java_bin_mt_signature_KillerApplication_hookApkPath`);srpatch/云镜系(闭源商用,同思路)。基础库 `xHook`(4.3k★)/`bhook`(2.5k★)/`shadowhook`(2.3k★)本身只是 hook 库、非工具。
- **检测指纹**:`/proc/self/maps` 里 hook 引擎特征;导出符号 `hookApkPath`、xHook 内部符号 `xh_core`/`xh_elf`/`xhook_register`(**即便 .so 改名成 `libyrf.so` 这类短随机名,符号表/字符串表内容仍在** → `nm`/`strings`/YARA 不受改名影响);资产里出现**内嵌的第二个完整 APK/ZIP**(`origin.apk`/`hook.apk`);运行时 `open/openat` 首字节被改成跳转(native 自检可查)。

### 流派 C:系统级关闭签名校验(改设备,不改 APK — 另一条路)
- **机制**:**不是给某个 APK 过验证**,而是 root + LSPosed 环境下 hook `system_server` 的 `PackageParser`/签名校验/`checkSignatures` 返回值,让**整个系统**允许安装/运行被改签名的包;或改 ROM(microG signature spoofing patch)。
- **代表**:`LSPosed/CorePatch`(3156★,活跃)、`XSpoofSignatures`、microG `FAKE_PACKAGE_SIGN`(LineageOS-for-microG)、闭源 Smali Patcher。
- **和 A/B 的区别**:A/B 是**在被 mod 的 APK 内部**注入(per-APK,可分发给普通用户);C 是**改攻击者自己的设备/ROM**(需 root,不随 APK 分发)——所以**审计一个 mod-APK 时不会看到 C 的痕迹**,C 属于"运行环境"而非"包内改动"。

## 2. 取证速查:看到指纹 → 大概率哪个工具
| 指纹 | 归因 |
|---|---|
| `bin.mt.signature.KillerApplication` + `"### Signatures Data ###"` | ApkSignatureKillerEx(新版 MT,手动套模板)——本批最常见 |
| `cc.binmt.signature.PmsHookApplication` | 初代 ApkSignatureKiller(2017)或 Apkmod `--killer=k1`,只打 PM 层 |
| `com.apksignaturekiller.HookApplication` + `"### Applicaton Data ###"`(拼写错)| SectionTN/ApkSignatureKill(安卓 App 产出) |
| native `hookApkPath` + xHook 符号 + 内嵌 `origin.apk` | ApkSignatureKillerEx native 对抗部分(编译产物,常改名 `libyrf.so` 等) |
| `com.srpatchv3.Application` / `libsrpatch.so` / `killOpen` | srpatch 系(本批鹿蜀/zhou45 多例) |
| `LSPApplication` + `assets/lspatch/` 元数据 + `appComponentFactory=org.lsposed…` | LSPatch(PC jar,最接近一键) |
| `bin.ghost.*` + `libyrf.so` | 本批 youarefinished 系(与上述 native 同族改名) |

## 3. 防御:检测清单 + 加固(重点)
**检测(取证/入库时批量扫,便宜高信号)**:grep 上表所有类名/占位串;`strings`/`nm`/YARA 扫 native 符号(不怕 .so 改名);查 manifest `application`/`appComponentFactory` 与常见基类 `.super` 是否指向陌生包;资产里有无内嵌第二个 APK;`org.lsposed.hiddenapibypass` 是否存在。

**加固(把这类绕过逼到无效)**:
1. **签名校验别只信进程内 PackageManager 单点**——流派 A 的核心就是伪造它。要**多源交叉**:同时读自身 APK 的 v2/v3 签名块字节(native 直读)+ `PackageManager` 结果 + 比对,任一路不一致即异常。
2. **native 读自身 APK 这一路会被流派 B 的 killOpen 重定向**——所以要**检测 `open/openat` 是否被 hook**,且**别只靠"读文件比对"**(本地任意执行代码下,读文件式校验终可被 IO 重定向绕过,这是本质限制)。
3. **校验结果参与业务解密、绑定服务端新鲜 nonce**(见《加固实施清单》§1/§2)——让"绕过校验"变成"解不出内容/服务端不认",而不是跳过一个布尔。这是唯一能同时对抗 A/B/C 三派的根:**因为 C(系统级)你根本检测不到,只有服务端裁决能兜底**。
4. 客户端加**运行时反 Hook/反注入自检**(流派 A/B 的注入有固定指纹);发行侧 Play Integrity(但注意 C 派可能连它一起绕,仍需服务端交叉)。

## 4. 映射到本项目 99 样本 & 结论
- 本批已确证的 `KillerApplication`/`srpatchv3`/`bin.ghost`/`libyrf.so`/lsposed hiddenapibypass 全部落在**流派 A + B**;Polish 的 `bin/mt/signature/nurik`、Kilonotes/MX Player 的 `bin.ghost.*` 都是这两派的改名变体。
- **对 §九工具链表的修订**:"过签名校验"这格,PC 端最接近一键的是 **LSPatch(已归档,`JingMatrix/LSPatch` fork 活跃)**;老牌单命令 `Apkmod`/`nkstool` 已打不动现代签名;主线 `ApkSignatureKillerEx` 确是"手动套模板"。
- **防御含义**:正因为 PC 端没有好用的"一键",且这类注入指纹明确、可检测,**客户端反 Hook + 服务端参与解密**能有效把这类攻击从"作坊套模板"抬到"要真功夫"。
