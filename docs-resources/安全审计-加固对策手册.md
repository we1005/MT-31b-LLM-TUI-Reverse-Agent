# 安全审计 — 加固对策手册（面向被 Mod 的 App 开发者）

> 一句话定位：从 99 份"被违规 mod 的安卓 APK 只读取证审计报告"中蒸馏出的**防御方加固对策手册**——按弱点类别给出"识别特征 + 加固对策 + 印证样本"，供开发者自查客户端权益/签名/广告防线的薄弱点。

> **合规声明**：本文档纯防御/取证视角，仅讲"如何识别被攻破的手法 + 如何加固防御"。**不包含任何可直接复用的再破解步骤、绕过配方或 patch 脚本**；所有"识别特征"是审计员/开发者自查己方 App 防线薄弱点用的判据，不是攻击操作手册。数据来源：`/Volumes/zhitai-7100/reverse-agent/_scratch/apk-2-audit/`（99 份独立只读反编译审计报告 + `INDEX.md` 总索引）。

## 0. 怎么用这份手册

- 你是开发者/审计员，想知道"我的 App 有没有类似弱点" → 看第 1 节六类弱点，对照"识别特征"自查己方代码/产物。
- 你只有时间做几件事 → 直接看第 2 节"加固优先级清单"，按序号做。
- 想知道某个可疑现象（如发现一个陌生 so 库/陌生 ContentProvider）大概率对应哪类手法 → 看第 3 节"识别决策树"。

## 1. 六类弱点 — 识别特征 × 加固对策 × 印证样本

### 弱点 A：权益判定客户端恒真化（entitlement 单点 return true）

| | |
|---|---|
| **攻击者利用了什么** | `isVip()`/`isPro()`/`isPremium()`/`getMember()` 一类判定方法被静态改写为无条件 `const/4 v0,0x1; return v0`，或在数据模型构造函数/SharedPreferences 默认值参数处做"参数级恒真化"；只要该判定是全局唯一调用入口（常见 20~250+ 处调用），一次 patch 即可绕过全部付费墙。 |
| **识别特征（自查线索）** | 1) 判定方法体异常短（仅 局部变量声明 + const + return），且与同名字段/真实计算逻辑脱节（如 `isVip:Z` 字段仍在但方法体已不读它）。2) 判定函数被极大量类引用（几十到几百处）却只有一处实现——检查该唯一实现是否"过于干净"。3) 出现孤儿协程/回调内部类（如 `xxx$1`）已无任何调用点——说明原判定逻辑被整体替换绕过。4) 数据模型构造函数的入参在调用点被硬编码常量覆盖（而非 getter 层恒真）。 |
| **加固对策** | entitlement 判定**上移服务端**，签发短时效签名令牌，客户端仅展示、不做最终裁决；杜绝"客户端单一布尔/枚举字段=最终真相"的设计；对计费相关类做重命名混淆+字符串加密，提高定位成本（辅助手段，非根本解）。 |
| **印证样本** | Kilonotes千本笔记(youarefinished) `UserInfo.isVip()` 恒真，254/18 处调用被一次打穿；天气通(黯笙) `UserInfoDataStorage.getMember()` 直接恒真；Rocks Player(HeroMods) `BaseActivityParent.isPremiumUser()` 恒真，24 处调用+全局静态开关同步置真；红果免费短剧(鹿蜀) `VipInfoModel` 构造函数 6/8 个入参被硬编码覆盖（参数级恒真化，非 getter 层）。 |

### 弱点 B：签名自校验单点可 Hook（PackageManager 反射路径可伪造）

| | |
|---|---|
| **攻击者利用了什么** | App 自身做了"防篡改自检"（比对 `PackageManager.getPackageInfo(GET_SIGNATURES)` 返回的证书是否为原厂证书），但该检查**完全依赖 Java 层单一 API**，可被反射/ART Hook 在运行时伪造回原厂证书哈希——检测被绕过而非被破解。这是本批出现频率最高的手法（ApkSignatureKillerEx 及其变体命中 27+ 个样本，加上 MT 管理器内置同类功能共 47 个）。 |
| **识别特征（自查线索）** | 1) 类名/字符串出现 `bin.mt.signature.*` / `KillerApplication` / GitHub `L-JINBIN/ApkSignatureKillerEx` 明文 URL / 方法名 `killPM()`、`killOpen()`、`hookApkPath()`。2) `com.srpatchv3.Application` / `com.srp.patch.Init`（SRPatch 系框架）。3) `AndroidManifest.xml` 中 `android:appComponentFactory` 或 Application 的 `.super` 继承链被改指向陌生注入类而非原声明类。4) 反射替换 `PackageInfo.CREATOR`、清空 `PackageManager.sPackageInfoCache`/`mCreators`/`sPairedCreators`。5) 伴生原生库：`libyrf.so`/`liblssec.so`/`libSRPatch.so`/`libSignatureKiller.so`。 |
| **加固对策** | 不要仅依赖 `PackageManager` Java API 做签名自检；改为 **native 层直接解析 APK 自身 v2/v3 签名分块字节**做哈希比对（绕开 Binder/反射路径），并做多点交叉校验（文件级摘要 + native JNI 独立实现 + PM 返回值三方比对）。**校验结果必须参与关键数据解密/密钥派生**，而非仅作 if 分支——否则被 Hook 后 if 判断为真依然是可执行路径，检测形同虚设。服务端二次核验签名指纹，接入 Play Integrity。 |
| **印证样本** | Remini(APKDADDY) `bin.LyerXz99.Apkdaddy` 反射伪造签名回灌原版证书；DevCheck(youarefinished) `bin.ghost.yrf`+`libyrf.so` 抢在 PairIP 授权前伪造签名骗过完整性校验；扫描王全能宝(黯笙) `KillerApplication` 注入，专门阻止了原厂 `isGenuine()` 判定失败后的 `killProcess+exit` 自毁分支；喜马拉雅/微商助手/微粉猫(鹿蜀) `com.srpatchv3.Application` 反射清空签名缓存 + xhook 文件重定向。 |

### 弱点 C：entitlement 本地缓存（本地存储被当作信任源）

| | |
|---|---|
| **攻击者利用了什么** | 会员/VIP 状态被持久化进 SharedPreferences/MMKV/Room（而非每次向服务端核验），攻击者只需一次性篡改缓存字段（写死 true/PRO/未来过期时间戳）即永久生效；更弱的情形是本地判定的默认值参数本身可被字节码改写（如 `getBoolean("isPremium", false)` 的默认值参数被改成 `true`），甚至无需碰任何判定逻辑，仅靠中间人代理伪造一次服务端接口响应写入本地缓存即可离线长期生效。 |
| **识别特征（自查线索）** | 1) SharedPreferences/MMKV key 命名含 `USER_IS_VIP`/`isMember`/`vipType`/`isSubscribed`，且判定逻辑只读该本地字段、无在线校验路径。2) `getXxx(key, defaultValue)` 调用点的 `defaultValue` 字面量在字节码层被改写。3) 用户信息接口（如 `basic-user-info`）响应未做证书锁定（无 `network_security_config` pinning），且客户端完全信任其中的会员字段。 |
| **加固对策** | entitlement 绝不能只靠本地缓存或无锁定的网络响应；服务端签发短时效、防重放的**签名令牌**，客户端验签而非信任明文 JSON；开启 certificate pinning + 禁用明文流量（`usesCleartextTraffic=false`），防止中间人篡改接口响应写入缓存。 |
| **印证样本** | 七猫免费小说(鹿蜀) `Lk29;.h0()/h1()` 的 `USER_IS_VIP` SharedPreferences 缓存字段被篡改；小月历(NURIK) `Lei/k.y()` 双补丁：缺省值 false→true + 删除整型缓存分支的 false 写入指令；CalcKit(Balatan) 全应用各功能页 `getBoolean("isPremium", false)` 默认值批量脚本化改真；微粉大师(鹿蜀) 唯一"完全未签名+中间人代理"样本，推断经中间人代理伪造 `basic-user-info` 接口响应写入本地 VIP 缓存字段。 |

### 弱点 D：加固壳被内存 Hook 绕过（"壳=防篡改"的错觉）

| | |
|---|---|
| **攻击者利用了什么** | 应用/发行方已采用商业加固壳（云镜 yjaq.xyz / 爱加密 Ijiami / 360 Jiagu / SecShell）对业务 dex 做加密隐藏，静态无法直接改写。但攻击者**根本不碰加密 dex**，而是在壳解密执行后的**运行时内存态**用 ART 方法级 Hook 引擎（Pine / LSPlant / Epic / AliuHook 等）直接劫持已加载的目标方法（会员判定/广告 SDK 方法），使其返回攻击者想要的值——壳的静态保护被完全绕开。本批 25 个已加固样本**全部**被此手法攻破，无一例外。 |
| **识别特征（自查线索）** | 1) `lib/` 目录出现 ART Hook 引擎特征库：`liblshook.so`/`liblsplant.so`/`libEpic*.so`/`libpine*.so`/`libaliuhook*.so`/`libDexHelper.so`。2) 伪装成知名 SDK 包名的 Hook 模块类，如 `com.bytedance.shadowhook.<某App名>.Hook`（并非真正字节跳动组件——真正的 shadowhook 不会以 App 名做子包）。3) 异常高 `initOrder`（如 `Integer.MAX_VALUE`/`2147483647`）的 `ContentProvider`，抢在应用启动最早期加载。4) Xposed 兼容 API（`de.robv.android.xposed.XC_MethodHook`）出现在非 Xposed 宿主环境。5) 业务 dex 仍完整加密在 `assets/classes0.jar` 等壳资产中，但外层出现上述特征库——这组合本身就是"壳被绕过"的强信号。 |
| **加固对策** | **加固壳不能单独依赖**，必须叠加运行时反 Hook/反注入自检：扫描 `/proc/self/maps` 中已知 Hook 引擎 so 特征名单；检测 ArtMethod 入口点/方法体是否在运行期被篡改（inline hook 检测）；检测 `appComponentFactory`/Application 继承链/`ContentProvider` 清单是否存在异常高优先级或非白名单条目；命中即降级或拒绝服务。签名/完整性校验结果应扩大覆盖面到这些运行时特征，而非只查一次静态签名。 |
| **印证样本** | 拷贝漫画(鹿蜀) 爱加密壳完整未破，`liblshook.so`(LSPlant) 在内存态拦截广告方法；浩克下载(鹿蜀/PJAPK) 360 Jiagu 壳完整，`liblsplant.so` 运行时 Hook 会员判定方法（"壳保护倒逼破解者从静态改码转向运行时 Hook"的典型案例）；囧次元(zhou45) 360 壳 + Flutter，同时装备 Epic/Pine/LSPlant/AliuHook 四套 Hook 引擎；每日英语听力/墨迹天气/一叶日记(辰夕系) 加密 dex 分片 + `libcxapkmod.so` ART Hook 引擎运行时替换判定结果。 |

### 弱点 E：默认分支 fail-open（异常/未知状态默认放行）

| | |
|---|---|
| **攻击者利用了什么** | 授权/校验代码本身的"未知状态""网络异常""缓存缺失"等边界分支被设计为**默认放行**而非拒绝，攻击者甚至不需要碰主判定逻辑，只需让流程走到这条兜底分支（或 patch 使其恒定命中）即可解锁；更隐蔽的情形是应用存在新旧两套授权链路，新链路校验很强，但攻击者刻意选择校验更弱的**遗留链路**作为切入点。 |
| **识别特征（自查线索）** | 1) 授权函数存在多个 return 点，检查"未命中/异常/超时"分支的返回值是否为 true/已授权（而非 false/拒绝）。2) 产品类型/等级映射函数存在"遍历末尾默认返回"逻辑——核实该默认值是最低等级（NONE）还是被篡改为最高等级（PRO）。3) 判定函数本应联网核验（如 `checkLicenseOnBackend`），但静态追踪发现所有路径（含网络失败路径）最终收敛到同一个返回值。4) App 内并存新旧两套 entitlement 体系（如 Firebase/Play-Billing 新链路 + 遗留 Licensing 旧链路），且旧链路未下线。 |
| **加固对策** | 所有 entitlement/签名/授权判定的"未知/异常/超时"分支**一律 fail-closed（默认拒绝）**；下线并合并任何并行的弱校验旧链路，不给攻击者挑"最弱分支"的机会；产品等级映射的默认值必须是最低权限而非最高权限。 |
| **印证样本** | Solid Explorer 3.5.14(NURIK) `SELicenseManager.checkLicenseOnBackend()` 的统一收敛出口被硬编码为 true——无论服务端返回未授权、本地缓存未授权、还是网络异常，一律放行；攻击者刻意绕开了 App 内本身更强的新版 Firebase/Play-Billing 体系，专挑遗留弱链路下手。CCleaner(Balatan) `AclBillingImpl` 产品类型映射的默认返回值被从 `NONE` 改为 `PRO`，任何未识别/空授权都判定为最高等级。小月历(NURIK) `Lei/k.y()` 缺省值 false 改 true，使默认路径本身即为恒真。 |

### 弱点 F：广告开关客户端可关（展示裁决全留在本地）

| | |
|---|---|
| **攻击者利用了什么** | 广告展示与否的最终裁决完全留在客户端（本地布尔判断/本地 JSON 配置/SDK 初始化调用点），攻击者无需服务端配合，仅需 no-op 化 SDK 初始化方法、清空本地广告位配置字段、或整类删除广告桥接类，即可全局去广告；广告 SDK 本身及素材资源常常完整保留未被物理删除（说明是"抑制触发"而非"移除组件"，更难被开发者事后察觉）。 |
| **识别特征（自查线索）** | 1) 常见广告 SDK 初始化类的 `init`/`doInit`/`show` 方法体被阉割为 `return-void`，与同一 App 内其它 SDK 方法体体积差异明显。2) `assets` 下的广告位配置 JSON（如 `SDK_Setting_*.json`）中某场景 `status`/广告位 ID 被清空，而其它场景保留真值——局部清零而非整体删除，更隐蔽。3) Flutter 桥接插件类（如 `FlutterGgPlugin`）整个从多个 dex 中消失，但 `GeneratedPluginRegistrant` 自带的 try/catch 让 App 不崩溃、请求静默失败——攻击者利用了框架自带的容错特性。4) 广告 SDK 本体（gms.ads/穿山甲/GDT/快手等）类与 manifest 组件声明仍然完整——佐证"抑制调用"而非"删除依赖"。 |
| **加固对策** | 广告展示策略与开关**下发到服务端**（短时效 token/动态配置），客户端仅渲染、不做终判；对关键 MethodChannel/广告桥接类的注册结果做运行时自检，不能依赖"注册失败也不崩溃"的静默容错（应改为注册失败即拒绝启动核心功能或上报）；把完整性校验覆盖面从 dex/so 扩大到配置类资产（JSON/xml），防止"只护代码不护配置"的盲区。 |
| **印证样本** | 笔趣阁(LWELY) `ADConfig.TTAdManagerHolder` 的 `init`/`doInit`/`reset` 方法体被阉割为 `return-void`；追剧达人 v2.1.2(鹿蜀) `FlutterGgPlugin` 整类从全部 4 个 dex 中删除，利用 `GeneratedPluginRegistrant` 容错静默失败；猫番阅读(zhou45) `SDK_Setting_*.json` 中 `novel` 阅读场景广告位 status/ID 被清空，`feed`/`small_video` 等其它场景保留真值。 |

## 2. 加固优先级清单（投入产出比排序）

> 排序依据：该对策能覆盖本批 99 个样本中多大比例的攻击面 / 是否为报告中明确指出的"被攻破根因" / 实现成本相对高低。**越靠前投入产出比越高，建议按序落地**。

| 序号 | 对策 | 覆盖面（本批依据） | 为什么排在这里 |
|---|---|---|---|
| **P0** | 补齐/建立**签名指纹自校验**（哪怕只是最基础的比对证书 SHA-256 白名单） | 99/99 样本原厂签名均已被替换 | 多份报告明确指出"原包完全无自检是被一把改包的根因"（如 CalcKit）——没有这一步，后面所有防线都无从谈起；成本最低、覆盖面最广，**必须第一优先** |
| **P1** | entitlement/权益判定**上移服务端**（短时效签名令牌），废除客户端本地布尔判定 | 会员/VIP 25 + 高级/Pro 29 + 解锁完整 5 = **59/99**（近六成） | 覆盖面最大的攻击类型；"客户端恒真化单点"是攻击者最低成本的手法（一处 return true 即可打穿几十到几百处调用），对应防御的 ROI 也最高 |
| **P2** | 授权/签名/entitlement 判定的默认分支改为 **fail-closed**，下线并行弱链路 | 案例数少但破坏力极大（系统性设计漏洞） | Solid Explorer 案例证明：就算新版校验体系本身没坏，只要留一条弱"遗留链路"就全盘失守；这是设计层面的一次性修复，成本不高但极易被忽视 |
| **P3** | 签名自校验**多源化**（native 层直读 v2/v3 签名块，绕开 PackageManager 反射路径）+ 校验结果**参与业务解密** | ApkSignatureKillerEx 类手法命中 27，MT 管理器内置同类功能命中 47，合计影响近 **74/99** | 做了 P0 之后，如果自检只查 `PackageManager.getPackageInfo()` 这一条 Java 路径，几乎必被反射/Hook 绕过；这一步是把"有没有自检"升级为"自检能不能被绕过" |
| **P4** | 广告开关/展示策略**服务端化**，客户端仅渲染 | 去广告类型 **30/99** | 覆盖第二大攻击类型；本批手法（阉割 init/清 JSON 字段/删 Flutter 桥接类）证明纯客户端广告开关极脆弱且易被自动化批量攻击 |
| **P5** | 运行时**反 Hook/反注入自检**（扫描 ART Hook 引擎 so 特征、检测 ContentProvider 异常优先级、检测 appComponentFactory 篡改） | LSPatch/Xposed 命中 37，Pine/LSPlant/Epic ART Hook 命中 22 | 技术门槛更高，但这是唯一能挡住"内存态绕过壳/绕过签名校验"这条**最先进攻击链**的手段；没有这一层，P0/P3 建的签名校验本身也可能被 Hook 绕过 |
| **P6** | 加固壳（Dex2C/VMP/商业壳）作为纵深防御**最后一层**，但绝不能单独依赖 | 云镜/爱加密/360/VMP 命中 25，**25/25 全部被绕过** | 加固壳本身只提高静态分析成本，不是决定性防线；必须与 P0-P5 配合，否则会像本批 25 个样本一样被内存 Hook 完全绕过而"壳完好、逻辑已破" |
| **P7** | 发行侧接入 **Play Integrity**（服务端对非原始签名包拒绝下发内容）+ 客户端 **certificate pinning**（防中间人篡改接口响应） | 兜底覆盖全量分发环节 + 微粉大师式 MITM 场景 | 最后一道闸门：即使前面全部被绕过，服务端仍可基于设备完整性证明拒绝服务；证书锁定则专门堵住"篡改网络响应写入本地缓存"（弱点 C）这条最低成本路径 |

## 3. 识别决策树（看到 X → 大概率是 Y → 去查 Z）

```
发现 App 被重打包(签名已换) ──→ 先确认原包本身有没有做过签名自检
  │
  ├─ 若原包无任何自检 ──────────────────→ 攻破根因=P0缺失，攻击者无需任何绕过手法即可运行
  │
  └─ 若原包有自检，但被绕过：
       ├─ 类名/字符串含 bin.mt.signature / ApkSignatureKillerEx / killPM / srpatchv3
       │     ──→【弱点B】PackageManager反射伪造签名 ──→ 查 Application .super / appComponentFactory 是否被改写
       │
       ├─ so目录出现 liblshook/liblsplant/libEpic*/libpine*/libaliuhook*
       │     ──→【弱点D】ART Hook引擎运行时绕过 ──→ 查是否伴随高initOrder的ContentProvider + 伪装知名SDK包名的Hook类
       │
       └─ assets下有壳资产(classes0.jar/加密dex分片)但仍能看到上述Hook特征库
             ──→ 壳被绕过而非脱壳，业务逻辑改动发生在内存态 ──→ 静态分析到此为界，别再往加密dex里找patch

发现会员/Pro判定方法体极短(仅 const+return) ──→【弱点A】权益恒真化 ──→ 查全局调用点数量(常见20~250+)
发现SharedPreferences/MMKV里有vip/member/premium类key且无在线校验 ──→【弱点C】本地缓存被信任 ──→ 查是否有certificate pinning
发现广告SDK init/doInit方法体被阉割为return-void，或JSON配置局部字段被清空 ──→【弱点F】广告开关客户端可关
发现授权函数的"网络异常/未知状态"分支返回true，或产品等级映射默认值不是最低等级 ──→【弱点E】fail-open设计缺陷
```

**静态分析边界（诚实标注）**：凡业务逻辑已被 Dex2C 原生化 / VMP 虚拟化 / 商业加固壳加密、或改动载荷本身经 Hikari/OLLVM/Arkari 等控制流混淆编译进 native 代码的情形，静态只能确证"壳/工具指纹/攻击框架存在"，**无法坐实具体被改的类.方法**。这是本批 99 份报告中近半数标注为"中"置信度的共同原因——遇到这种情况应如实标注为"推断"而非编造具体行号，动态分析/内存 dump 之外无法进一步坐实。
