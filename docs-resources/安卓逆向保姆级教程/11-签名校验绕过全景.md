# 签名校验绕过全景：五大流派

> 一句话点题：**"过签名校验"从来不是一招鲜的黑科技,而是五条工程路线各自拿"隐蔽性、改动量、自动化程度、能打赢多强的校验"做四选一交易——本文把它们摆在一张桌上,让你一眼看出报告里出现的每个手法属于哪条路线、为什么有效、以及防御方从哪个缝去堵。**

读前提醒：本篇是**导读 + 全景图**,负责把五大流派的**边界和取舍**讲清楚,让你看懂《总报告》里"MT 一键""killPM""killOpen""LSPatch""CorePatch"这些词到底是谁、属于哪条路线。每条路线的**逐字节实证**(哪个类、哪个字段、哪行 smali)在下面两篇专文里,本文不断指路,不重复贴证据。

---

## 0. 先把"签名校验"是什么、为什么能被绕过讲清楚

如果你是跳页进来的,先花 1 分钟对齐几个词(完整版见 `05`/`06`):

- **APK 签名**：类比你熟悉的**代码签名**(Authenticode/GPG 签发布物)——开发者用私钥对整个安装包算一遍摘要并签名,塞进包里(v1 在 `META-INF/`,v2/v3 在文件末尾一段专用的 **APK Signing Block**)。任何人改了包内容,摘要对不上,签名就失效。
- **`getPackageInfo(pkg, GET_SIGNATURES)`**：安卓系统服务 `PackageManager`(可以理解成系统里管"每个包的元数据"的一张**数据库表**,类似你后端的一个 `packages` 表)暴露的一个查询接口——App 运行时问系统"我自己(或另一个包)的签名证书是什么",拿到的是系统**在安装时校验并缓存下来**的结果。API 28(Android 9)之后新增了 `signingInfo.getApkContentsSigners()` 这个更细粒度的等价接口(区分"当前签名"和"历史签名沿革",详见 `05` 的证书轮换 lineage)。
- **`checkSignatures(pkg1, pkg2)`**：同一套 `PackageManager` 家族里"比较两个包签名是否一致"的接口,常被 App 自己用来做"防止被二次打包"的自校验——**这行比较,就是本文五大流派要攻陷的靶心**。
- **应用自校验 vs 系统校验**：系统在**安装时**就会拒绝签名不合法的包(这一层普通用户很难绕,靠证书链数学关系保证);但很多 App **自己在运行时又加了一遍**校验——调用上面两个接口,把结果拿来跟自己代码里写死的"官方证书指纹"做比较,不一致就退出或功能降级。**这道"应用自加的门"才是本文讨论的对象**——系统校验保证不了"这个包有没有被人开箱改过内容再重签",而应用自校验就是为了补这个洞,但恰恰是这道"补丁门",本身也能被同样的手法绕过。
- 一句话总结这场攻防的本质：**"校验"本质上是一次函数调用 + 一次比较**(`签名A == 签名B ?`)。既然是函数调用和比较,那所有能**改代码**、**改函数返回值**、**改比较结果**的手段,理论上都能绕过它——五大流派的区别只在于"在哪一层改、改得多干净、需不需要运行时框架"。

## 1. 一个绕不开的取舍：四个维度不可能同时拉满

在展开五大流派之前,先建立这张"全景地图"的坐标系。业界(以及报告里)所有绕过手法,都是在下面**四个维度**里做取舍,**没有一种方案能同时把四个都拉满**:

| 维度 | 类比 | 意思 |
|---|---|---|
| **Footprint(改动量/静态特征)** | 你给一个二进制打 patch,是改 3 个字节,还是塞进去一整个运行时库 | 改得越多,静态扫描(`grep`/YARA/字符串匹配)越容易抓到 |
| **隐蔽性(能不能躲过人工/自动审计)** | 改一行 vs 整个目录多出一个 `assets/lspatch/` | 就算改动量小,如果改的位置本身很显眼(比如 manifest),也不隐蔽 |
| **一键/自动化程度** | 手写 patch vs 点一下按钮全自动 | 一键意味着背后有工具把"定位校验点→改逻辑→重打包重签"全流程做成了模板 |
| **覆盖面(能打赢多强的校验)** | 只能过老式反射校验,还是能连 native 自读字节、v2/v3 签名块、多因子交叉校验都一起绕 | App 加固程度越高,需要的绕过手法越"重" |

**为什么不可能都拉满**：改动量小(比如只在 smali 里改 3 个字节)天然只能打最基础的校验点——一旦目标有 native 层自校验、多处交叉比对,3 字节 patch 顾此失彼,必然要么加更多改动(牺牲 footprint)、要么上运行时框架接管更多逻辑(牺版"静态改包"的干净)。反过来,覆盖面拉满的方案(运行时 hook 框架、系统级改设备)必然引入更大、更容易被扫描出来的痕迹。**这条"四选一"贯穿全篇,读完你会发现五大流派其实就是这张表在五个不同点上的取值。**

```
                  隐蔽性 ↑
                     │
        流派①静态patch │      流派②MT反射注入
       (改动极小但要盯   │      (模板化、footprint 小、
        每一个校验点)    │       靠继承链隐蔽触发)
                     │
   ──────────────────┼────────────────────→ 覆盖面(能打赢多强校验)
                     │
       流派④native   │      流派③运行时hook框架
       killOpen       │      (Xposed/LSPatch/Frida,
       (专治自读字节)  │       覆盖面大但静态特征明显)
                     │
                     │      流派⑤系统级(CorePatch/microG)
                     │      (覆盖面拉到最大,但只能在
                     │       攻击者自己设备上生效)
```

好,坐标系搭好了,下面逐条拆解五大流派。

## 2. 流派①：静态 patch——直接把比较结果改成"永远为真"

### 2.1 是什么 / 怎么工作

最朴素的一条路。用 `baksmali`(把 DEX 字节码反汇编成 **smali**——一种比 x86 汇编好读得多的"DEX 汇编",详见 `02`/`07`)把 App 反编译出来,**肉眼或工具定位**到调用 `getPackageInfo`/`checkSignatures` 之后紧跟着的那个 `if` 判断,直接在 smali 层把判断逻辑**改恒真或 NOP 掉**(NOP = No Operation,汇编里"什么都不做"的占位指令,你在改可执行文件时用它"抹掉"一整条指令但不打乱后续代码的字节偏移),然后用 `smali` 重新汇编回 DEX、`apktool` 重打包、拿任意新 key 重签。

给你一个 before/after 直觉(伪代码,不是真实反编译产物):

```
// Before(反编译还原出的等价 Java 逻辑)
Signature[] sigs = getPackageManager()
        .getPackageInfo(pkg, GET_SIGNATURES).signatures;
if (!sigs[0].equals(OFFICIAL_SIGNATURE)) {
    System.exit(0);   // 签名不对就退出
}

// 对应的 smali 关键几行(概念示意,不是可执行片段)
invoke-virtual {...}, Landroid/content/pm/Signature;->equals(...)Z
move-result v0
if-eqz v0, :label_exit
...
:label_exit
    invoke-static {}, Ljava/lang/System;->exit(I)V
```

**改法**通常是三选一：①把 `if-eqz`(等于则跳)改成 `if-nez`(不等于则跳,逻辑取反,直接让判断条件对调)、②把整段 `if` 判断连跳转目标一起 NOP 掉、③在 `equals` 之后强行 `move-result v0` 覆写成常量 `1`(true)。**改动通常只有几条指令**,如果 App 只有这一处校验、且没混淆到让你难以定位,几分钟就能改完。

### 2.2 Footprint / 隐蔽 / 覆盖面

- **Footprint**:**极小**——diff 出来往往就是几条 opcode 的改变,不新增任何类/文件。
- **隐蔽性**:**对着资产扫描(找特征文件/特征类名)几乎隐形**,因为压根没新增东西;但**对着控制流做人工/自动化审计时很显眼**——一段"读了签名却什么都不判断"或者"判断结果被硬编码"的代码,懂行的人一眼假。
- **覆盖面**:**最窄**。这条路线的死穴有三个：
  1. **要逐个校验点手动定位**——App 里如果校验散落在 5 个不同方法里(常见的加固写法就是故意多点分散),你得每处都找到、每处都改对,漏一个就白干。
  2. **一旦上了控制流混淆/字符串加密**(详见 `09`),连"这段代码是在校验签名"这件事本身都要先靠人工读懂,自动化脚本很难通用。
  3. **一旦校验挪到 native 层**(.so 里用 C/C++ 直接读 APK 字节做校验,或者用 JNI 把关键判断沉到 native),smali 层已经无从下手,得转向逆 ELF 二进制——这正是第④流派要专门解决的问题。

一句话：**流派①是"手工作坊"路线**——对简单 App(只有一处明文 Java 校验、没混淆)是最快最干净的一刀,但**完全不能自动化到批量处理**,也扛不住任何形式的加固升级。这正是为什么 MT/NP 这类"一键"工具**不会**只用这条路线——它们要处理成千上万种不同 App,必须走下面第②条"模板化"的路。

## 3. 流派②：静态注入 + 运行时反射——MT 的 `KillerApplication` 打法

这是报告里**篇幅最重、最值得吃透**的一条路线,因为它就是 MT 管理器"一键去签名校验"的真实实现,已经在 `../安全审计-MT一键过签名校验-机制逆向与正向实现路径.md` 里逐字节坐实。这里给你一个**保姆级但不重复证据**的讲法。

### 3.1 核心心智模型：不改判断逻辑,改"判断的输入"

流派①改的是"`if` 怎么判断";流派②换一个更聪明的靶子——**不碰 App 自己的判断逻辑一个字节**,而是在 App 启动的最早时机,**抢答系统查询接口,让它返回一份伪造的"正确答案"**。类比你更熟悉的场景：与其去改 100 个调用点各自的 `if (result != expected)`,不如直接**在系统 API 的返回路径上做手脚**,让所有调用点查到的都已经是"合格"的假数据——这就是为什么它比流派①**覆盖面大得多**:App 里不管有几处校验、写得多分散,只要都是通过 `PackageManager` 这条官方接口查询,**一次伪造,处处生效**。

### 3.2 三个部件怎么拼起来

**部件一：预置的模板 dex,不是现场写代码**

MT 内置一份编译好的 `bin.mt.signature.KillerApplication`(源自开源项目 `L-JINBIN/ApkSignatureKillerEx`)。这个类本身不认识目标 App,靠"一键"时**把目标的包名和目标的原厂证书 base64 填进它的 `<clinit>`(类初始化块,详见 `03`——类第一次被加载时自动跑一次的静态初始化代码,类比 C++ 全局对象的构造函数或 `__attribute__((constructor))`)常量里**,变成"专属于这个目标"的一份。这就是"模板化"——工具库存一份通用逻辑,注入时只填两个字符串,所以能对任意 App **秒级完成**,这是它区别于流派①"每次都要人工定位"的关键。

**部件二：`killPM`——反射伪造 `PackageInfo.CREATOR`**

`<clinit>` 触发后跑的第一件事,是用写死的原厂证书构造一个假的 **`PackageInfo.CREATOR`**(`Parcelable.Creator` 是安卓里"如何把一份数据从跨进程传输的字节流,反序列化成对象"的标准接口,你可以类比成一个自定义的反序列化钩子/工厂函数)。用**反射**(Reflection——运行时**按字符串名字**查找类/字段/方法并操作,你最熟悉的类比是 **RTTI + 在运行时按符号名手动 `dlsym` 出函数指针来调**,只是安卓反射的能力范围更大、能直接读写 `private` 字段)把系统里真正的 `PackageInfo.CREATOR` **整个替换**成这份假货。之后**任何**代码调 `getPackageInfo(..., GET_SIGNATURES)`,反序列化出来的 `signatures[0]` 都会是伪造的原厂证书——因为反序列化这一步,已经被换了个"假工厂"。

同时反射清空三处缓存(`sPackageInfoCache`/`Parcel.mCreators`/`Parcel.sPairedCreators`)强制系统重新走一遍这个被顶替的反序列化路径(不清缓存的话,已经查过一次的结果会命中缓存,不会再触发假 CREATOR),并调用 `org.lsposed.hiddenapibypass.HiddenApiBypass`(Android 9/API 28 起,系统对"非官方 SDK 接口"的反射调用加了运行时限制,这个开源库就是用来豁免这条限制的,详见 `03`)保证反射操作不被拦。

**部件三：`killOpen`——native 层文件重定向(专治"不问系统、自己读字节"的校验)**

`killPM` 只能拦住"**问系统**要签名"这条路。但如果 App 更狠——**根本不调用 `PackageManager`,而是自己在 native 层用 `open()` 系统调用直接打开运行中的 APK 文件、手动解析里面的 v2/v3 签名块字节**做校验,`killPM` 就完全拦不住,因为压根没走它伪造的那条路径。

这时候上第二层：`killOpen` 通过 `System.loadLibrary` 加载一个内嵌的 native 库,读 `/proc/self/maps`(Linux 进程的**内存映射表**,记录这个进程把哪些文件映射到了哪段虚拟地址——App 想知道"我自己的 APK 文件当前在磁盘上的路径"最简单的办法之一就是查这张表里 `base.apk` 那一行)定位到当前正在运行的、**已被改过的**这份 APK 路径,再从自己内嵌的 `assets/` 目录里掏出一份**干净的原版 APK**,最后对 libc 的 `open`/`openat` **做 PLT hook**(改写 ELF 的**过程链接表**,让所有对这个符号的调用先跳到你插入的代码——这跟你在 C++ 世界最熟悉的 **`LD_PRELOAD`** 劫持符号、或者手写一个 detour 换函数入口跳转,是完全同一类手法,只是安卓上没有 `LD_PRELOAD` 这个环境变量式的省事入口,得手动改 GOT/PLT 表项),把"打开当前这份被改过的 APK"这个动作**透明重定向**成"打开我藏起来的干净原版"。这样 native 校验代码以为自己在读真实运行中的文件,实际读到的是内嵌的原版字节——自然校验通过。

### 3.3 触发方式："移花接木"——改 `.super`,manifest 保持不变

前两个部件解决了"伪造什么",还差"怎么在进程启动最早的时刻自动跑起来,而且要藏得够深"。MT 选的手法非常巧妙,值得单独拎出来讲：

正常来说,如果你想让一段代码在 App 启动时自动执行,最直接的做法是改 `AndroidManifest.xml`(详见 `04`)里 `<application android:name="...">` 指向的那个类。但这样一改,**manifest diff 一目了然**,自动化审计工具第一眼就能揪出来。

MT 的做法是：几乎所有现代 App 为了突破 DEX 的"单个文件最多 65536 个方法引用"限制(详见 `02` 的 64K 方法数),都会用 `androidx.multidex.MultiDexApplication` 当作自己 `Application` 子类的父类。MT **不碰 manifest 一个字节**,而是直接改写**`MultiDexApplication` 这个类本身的 `.super`**(父类描述符,类比 C++ 里改一个基类的继承声明)——把它从 `extends android.app.Application` 偷偷改成 `extends KillerApplication`,再让 `KillerApplication` 自己 `extends android.app.Application`。继承链变成：

```
目标自己的 App 类  ──▶  MultiDexApplication  ──▶  [被插入的 KillerApplication]  ──▶  android.app.Application
                                                    ↑
                                        注入者插进来的一环,manifest 里完全看不到
```

安卓加载 `Application` 子类时会**逐级触发父类的静态初始化**,所以 `KillerApplication.<clinit>`(部件二、三所在的代码)会在目标 `App` 类真正跑起来之前**自动被执行**——**不需要目标代码里加一行调用,不需要动 manifest**。这就是"移花接木"这个名字的由来：嫁接点选在几乎每个 App 都会用、开发者自己也不会去检查的第三方基类身上,比直接改 manifest 隐蔽得多。

### 3.4 Footprint / 隐蔽 / 覆盖面

- **Footprint**:**小**——新增一个 dex(模板类)+(可选)几个 .so + 一份内嵌原版 APK,改动集中在一个类的 `.super` 描述符,manifest **完全不变**。
- **隐蔽性**:**相当高**——常规审计习惯查 manifest 的 `application name` 有没有被改,而这条打法专门避开了这个最显眼的检查点;必须专门去查"某个基类的 `.super` 是否被改写"这种非常规角度才能揪出来。
- **覆盖面**:**中到高**——`killPM` 单独就能打赢"只走 `PackageManager` 查询"的绝大多数应用层校验;配上 `killOpen` 能再打赢"native 自读字节"这一档。但对**混淆到静态根本找不到、或者用了 Dex2C/VMP 把校验逻辑本身原生化**(详见 `10`)的极端加固,这条路线的**模板化优势会被削弱**——因为"往哪个类的 `.super` 嫁接"这件事本身也可能被高度混淆的目标搞得难以自动定位。
- 需要强调：**这条路线的"一键"靠的是"模板通用 + 每次只填两个字符串(包名、证书)",不是靠什么智能分析**——这也是为什么它对现代 v2/v3/native 强校验会逐渐失效的原因,深潜见开源工具全景篇。

> 完整字节级证据(`mt-apkt/assets/killer_*`、`.super` 被改的真实 smali、Lite Writer 样本里"`killPM` 生效但 `killOpen` 空转"的对比)、以及为什么"这是静态改包不是运行时框架"的逐点论证,请转
> **[../安全审计-MT一键过签名校验-机制逆向与正向实现路径.md](../安全审计-MT一键过签名校验-机制逆向与正向实现路径.md)**——本节只给你先验直觉,别在这重复啃。

## 4. 流派③：运行时 hook 框架——Xposed / LSPatch / Frida 直接接管调用

前两条流派都是"改包一次,以后每次启动都靠改过的代码自己生效"——**静态**。流派③换一套完全不同的哲学：**不改 App 的 DEX/native 代码本身,而是在 App 真正跑起来之后,把一个"运行时框架"注入进程,由这个框架实时接管你指定函数的调用**。

### 4.1 是什么(先建立直觉,详细讲解见 `08`)

- **Xposed / LSPosed**：一套"**Hook 框架**"(Hook 这个词你可以类比成运行时改写一个函数的行为,跟你熟悉的**改写 PLT/GOT 表项、`LD_PRELOAD` 劫持符号、或者写一个 detour 库**是同一类操作,只是安卓上要 hook 的是 ART 虚拟机里的 Java 方法,而不是 ELF 里的 native 符号)——需要 root 权限,常驻在 zygote(所有 App 的"母进程",详见 `08`)里,任何 App 启动时都能被提前挂钩。
- **LSPatch**:Xposed 生态里一个特化分支——**免 root**,把整套 Xposed 运行时(`liblspatch.so` + loader dex + metaloader)**直接打包塞进目标 APK 内部**,这样不需要 root、不需要常驻系统,APK 自己带着"迷你 Xposed"跑。它的"签名绕过"能力本质是**为了让被改过的 APK 能通过自己的自校验、从而顺利加载 Xposed 模块**这件事的副产品,只是客观上功能和"专门去签名破解"完全吻合。
- **Frida**：一个跨平台的**动态插桩**工具,你可以理解成"运行时往目标进程里注入一段 JS 脚本,在你指定的函数上下断点/改参数/改返回值",同样是 hook 的一种,更偏向研究/调试用途而非"一键处理海量 App"。

### 4.2 怎么用它绕签名校验

思路直给：不管 App 自己的校验代码写成什么样、混淆到什么程度,只要它最终要调 `PackageManager.getPackageInfo`(或者 API28+的 `signingInfo.getApkContentsSigners()`)这几个**固定的系统 API**,hook 框架就可以**直接在这几个 API 的入口/出口**做手脚——**返回值直接换成原厂证书**,完全不需要理解 App 自己的判断逻辑写在哪、写成什么样。LSPatch 具体是同时 hook `signatures[]` 数组字段和 `signingInfo.getApkContentsSigners()` 方法,再配合 native 层的 `openat` 重定向(和流派②的 `killOpen` 思路一致,方案无关地覆盖"自读字节"这一档)。

### 4.3 Footprint / 隐蔽 / 覆盖面

- **Footprint**:**大**——需要把整套运行时(loader、metaloader、hook 引擎 .so)塞进 APK,`assets/lspatch/` 这类目录、`appComponentFactory` 被替换成 `LSPAppComponentFactoryStub` 都是**非常显眼的静态特征**,一眼扫描就能发现"这个包被 LSPatch 处理过"。
- **隐蔽性**:**低**——这是它相对流派②最大的短板,MT 的模板尽量藏进一个不起眼的基类 `.super`,而 LSPatch 的痕迹几乎写在包结构表面上。
- **覆盖面**:**理论上最广**——因为 hook 点在系统 API 这一层,不管上面的业务代码怎么混淆、怎么分散校验点,只要最终经过这几个固定 API,都能拦下来。但**覆盖面广不等于无死角**：真实 issue 显示,对银行/支付类高安全 App(如 BHIM UPI、Axis、三星 Card),这类运行时注入本身就会被目标自己的反注入/反 Hook 检测识别并拒绝运行——**"能 hook 系统 API"和"能骗过一个专门防 hook 的目标"是两回事**。

**一句话定位**：流派③是"通用钥匙",对**没有专门反注入防护的中低强度目标**几乎无脑通杀,PC 端一条命令(`java -jar lspatch.jar app.apk -l 2 -o out/`)就能跑,这也是为什么 PC/Mac 端"确实存在一个当前可用、开源的一键工具",但**代价是牺牲了隐蔽性**,且遇到真正做了纵深防御的目标(反 hook 自检、服务端交叉裁决)会直接失效。

## 5. 流派④：native killOpen 单独拎出来讲——为什么"自读字节"是根本难题

流派②里已经出现过 `killOpen` 这个部件,但它值得单独当作一条流派来理解,因为它对应的是**签名校验里"最难被上层通用手段一次性打赢"的那一类目标**:App **不问系统、自己在 native 层直接读运行中的 APK 文件字节**,手动解析 v2/v3 签名块(甚至干脆算一遍摘要跟写死值比对),完全绕开 `PackageManager` 这整条 Java 层路径。

### 5.1 为什么它单独构成一个"流派"而不只是流派②的附属

- **流派①(静态改判断)对它无效**：校验代码根本不在 smali 里,是 native 机器码,想改就得先逆 ELF 二进制。
- **流派②的 `killPM`、流派③的 hook 系统 API 对它也无效**：因为这条校验路径**压根没调用**它们能拦截的那几个系统 API,伪造 API 返回值这件事对这类目标是"打了个寂寞"。
- **唯一能打的手法**就是本节讲的：在 native 层劫持更底层的 **`open`/`openat`/`openat64`** 这几个 libc 系统调用入口——不管上层业务代码用什么姿势读文件,最终都得走这几个固定的系统调用,劫持点选在这里,"生效范围"覆盖了所有走文件 IO 的自读校验,这跟流派③"选在系统 API 层拦截"是**完全同构的思路,只是拦截点从 Java 层的 API 下沉到了 native 层的系统调用**。

### 5.2 怎么工作(承接第 3 节部件三,这里补充通用机制)

技术上是标准的 **PLT hook**(过程链接表劫持,ELF 里所有对外部符号的调用都要先查这张表再跳转,改写表项就能让调用先经过你的代码)或 **inline hook**(直接改写目标函数开头几条指令,插入跳转到你的代码,原函数逻辑跑完再跳回去——这跟你熟悉的 detour 库、或者手写 trampoline 完全一样)。业界现成的开源 hook 引擎库(如 `iqiyi/xHook`、`bytedance/bhook`、`shadowhook`)本身只是"提供劫持能力的库",真正"劫持 `open` 之后要做什么"(重定向到内嵌原版 APK)是攻击代码自己拼上去的业务逻辑。

### 5.3 Footprint / 隐蔽 / 覆盖面

- **Footprint**：中等——多一个/几个 .so、多内嵌一份**完整的原版 APK 文件**(这个"包里有第二个 ZIP/APK"的特征本身就很显眼)。
- **隐蔽性**:.so 可以随意改名(`libyrf.so` 这类随机名),**但内部的符号表/字符串表内容不受改名影响**——`nm`/`strings`/YARA 扫描依然能命中 `hookApkPath`、`xh_core`、`xh_elf`、`xhook_register` 这些**hook 引擎自身携带的、开发者很难清理干净的内部符号**。这是这条流派"看似隐蔽实则留了硬指纹"的关键。
- **覆盖面**:**专精但有本质天花板**——能打赢"自读字节做校验"这一档,但打不赢下一节的"系统级"和"服务端参与裁决"这两类更硬的防御(因为重定向的前提是"进程内可以任意执行代码去劫持系统调用",这个前提本身在服务端裁决面前不成立)。

---

## 6. 流派⑤：系统级——不改 APK,改设备/ROM/`system_server`

前四条流派有一个共同前提：**改动发生在被处理的这份 APK 内部**,改完之后这份文件可以**分发给任何人**、装到任何设备上都生效——这也是审计一个"mod APK"样本时,你能在**包本身**里找到痕迹的原因。第五条流派彻底不同。

### 6.1 是什么 / 怎么工作

不去动目标 APK 一个字节,而是在**攻击者自己的设备**上(需要 root)动手脚：

- **`LSPosed/CorePatch`**(WebSearch 核实：截至 2026-07,约 3.2k★,近期仍有版本发布,活跃维护)：以 LSPosed 模块形式运行,直接 hook Android 系统里 `system_server` 进程(所有系统服务运行的宿主进程,`PackageManager` 服务本体就跑在这里面)的**签名校验相关逻辑**(如 `PackageParser`/`checkSignatures` 返回值),让**整个系统**层面允许安装/运行签名被改过、甚至版本降级的包。
- **microG 的签名伪装(signature spoofing)补丁**：改的是 **ROM 本身**(如 LineageOS-for-microG),让系统级的 `FAKE_PACKAGE_SIGN` 权限生效,任何声明了这个权限的 App 都能让系统"谎报"自己的签名——这条路线最初是为了让开源的 microG(Google Play 服务替代品)能"冒充"官方 Google 服务的签名以兼容依赖签名检查的第三方 App,但同一机制自然也能被用来对抗任意 App 的自校验。

### 6.2 和前四条流派的本质区别

| | 流派①②③④(改 APK 本身) | 流派⑤(改设备/ROM) |
|---|---|---|
| 改动对象 | 目标 APK 文件 | 攻击者自己的手机系统 |
| 能否分发 | ✅ 改完的 APK 可以发给任何人装 | ❌ 只对"已经把自己设备改成这样"的这一台手机生效,不随 APK 分发 |
| 审计一份 mod-APK 样本能看到吗 | ✅ 能——痕迹在包里 | ❌ **完全看不到**——这份 APK 文件本身干干净净,没被动过 |
| 需要 root | 视流派而定(流派②③大多免 root) | **需要**(hook `system_server` 需要系统级权限) |

### 6.3 Footprint / 隐蔽 / 覆盖面

- **Footprint(对被审计的 APK 而言)**:**零**——这是它和前四条最大的不同,也是防御方最头疼的一点：**你拿到的 APK 样本本身完全正常,签名、代码、资源一个字节都没被动过**,静态分析、甚至动态跑一遍 hash 校验都通过,因为"作弊"发生在系统这一层,不在 App 这一层。
- **隐蔽性(相对"审计这份 APK"而言)**:**天然满分**,因为压根不给你审计对象里留任何东西。
- **覆盖面**:**理论最大**——因为它是在校验发生的"地基"(系统服务本身)动手,不管上层 App 用了多复杂的分散校验、native 自读、甚至 Dex2C/VMP 原生化,只要最终还是要调系统提供的这套 API,系统这一层说"通过"就通过。但代价也最大：**只在攻击者自己已经 root 并装了这套环境的这一台设备上生效**,没有"分发给别人一份改好的 APK 就能用"这个属性——这也是为什么第 4 节"MT/NP 一键处理产物"这类**能分发的成品**,一定走流派①②③④,不会是流派⑤。

**对防御方最重要的含义**：流派⑤意味着**"客户端能做的所有检测,在系统级被攻破的设备上都不可信**"——因为检测代码本身也是通过这套已经被 hook 的系统 API 去查"我是不是被 hook 了"。这正是为什么加固的终极手段永远落在"**服务端交叉裁决**"(参与业务解密、绑定服务端 nonce),而不是"客户端把检测做得更复杂"——客户端所有的检测逻辑,在流派⑤面前都跟被检测的目标站在同一个不可信的地基上。

## 7. 五大流派横向总表

| 流派 | 改动位置 | 触发方式 | Footprint | 隐蔽性 | 一键/自动化 | 覆盖面 | 典型代表 |
|---|---|---|---|---|---|---|---|
| ①静态 patch | smali 判断逻辑本身 | 改过的代码自然执行 | 极小(几条 opcode) | 对文件扫描隐形,对控制流审计显眼 | ❌ 需人工逐点定位 | 窄(单点、怕混淆、怕 native 化) | 手工 baksmali 改 `if` |
| ②静态注入+反射 | 新增模板类+改基类 `.super` | 继承链 `<clinit>` 自动触发 | 小(1 类+可选 so) | 高(manifest 不变) | ✅ 模板化秒级 | 中到高(打赢 PM 查询+可选 native 自读) | MT 一键 / `KillerApplication` |
| ③运行时 hook 框架 | 不改包,注入运行时/或系统常驻 | 框架接管系统 API 调用 | 大(整套运行时) | 低(特征目录+替换点明显) | ✅ PC 一条命令 | 广(但怕目标自带反 hook 检测) | LSPatch/NPatch、Xposed、Frida |
| ④native killOpen | libc `open/openat` 入口 | PLT/inline hook 劫持系统调用 | 中(so+内嵌原版 APK) | 中(符号名难藏) | 常作为②③的附属部件 | 专精"自读字节"这一档 | `killOpen`、srpatch 系 |
| ⑤系统级 | 攻击者自己的设备/ROM/`system_server` | root 后常驻 hook | 对 APK 本身为**零** | 对被审计 APK 天然满分 | ✅ 但不能分发 | 理论最大,但**不随包走** | CorePatch、microG 签名伪装 |

再用第 1 节的四维坐标系收个尾：**没有一个流派同时拿到"改动最小 + 最隐蔽 + 全自动一键 + 打赢一切校验"**——流派①改动最小但最不能自动化;流派②在"小改动+隐蔽+能自动化"三者之间取得了目前最好的平衡,代价是覆盖面对顶级加固逐渐力不从心;流派③用大 footprint 换来了几乎最广的覆盖面和真正的一键;流派④是专治一个细分死角的补丁;流派⑤覆盖面理论最大,但彻底放弃了"可分发"这个属性。**理解了这张表,报告里任何一个具体样本用的手法,你都能立刻归位到某个格子里,并预判它的检测思路和失效边界。**

## 8. 检测速查(串联,细节见深潜篇)

- **流派①**：很难靠固定字符串抓,得靠**控制流审计**——一段"读了签名却没有任何后续判断"或者判断永远走同一分支的代码。
- **流派②**：类名 `bin.mt.signature.KillerApplication`(或改名变体 `bin.ghost.*`)、占位串 `"### Signatures Data ###"`、反射字段名 `sPackageInfoCache`/`mCreators`/`sPairedCreators`、`org.lsposed.hiddenapibypass` 存在本身即强信号;**关键动作**是去查常见基类(`MultiDexApplication` 等)的 `.super` 有没有指向陌生包,而不是只看 manifest。
- **流派③**:`assets/lspatch/` 目录、`appComponentFactory` 被换成 `LSPAppComponentFactoryStub`、`LSPApplication` 类名。
- **流派④**：内嵌的**第二个完整 APK/ZIP** 文件(`origin.apk`/`hook.apk`);即使 .so 改名,`nm`/`strings`扫描仍能命中 `hookApkPath`、`xh_core`、`xh_elf`、`xhook_register` 这类 hook 引擎自身符号。
- **流派⑤**:**审计单份 APK 样本时原理上看不到**——只能靠设备侧检测(root 检测、Xposed/LSPosed 常驻特征、`/system` 分区完整性校验)或服务端行为异常侧面感知。

## 一页速记

- **本质**：签名校验说到底是"一次函数调用 + 一次比较",所有绕过手法都是在**改代码、改函数返回值、或改比较结果**这三选一,只是选在不同层。
- **四维不可能全拉满**:Footprint(改动量)、隐蔽性、一键/自动化、覆盖面(能打赢多强的校验),五大流派各自在这四维上取舍,没有一种同时占全。
- **①静态 patch**:baksmali 直接把判断改恒真/NOP,改动最小但要逐点定位、怕混淆、怕 native 化,不能自动化。
- **②静态注入+反射(MT `KillerApplication`)**：模板化注入一个类,`killPM` 用反射伪造 `PackageInfo.CREATOR` 让所有查询系统 API 的校验点"一次伪造、处处生效",`killOpen` 用 native `open/openat` hook 专治自读字节;靠改一个常用基类的 `.super`(移花接木)自动触发、manifest 不留痕——小 footprint + 高隐蔽 + 能自动化的最佳平衡点,但对顶级加固覆盖面逐渐吃力。
- **③运行时 hook 框架(Xposed/LSPatch/Frida)**：不改包本身,注入/常驻运行时,直接在系统 API 层拦截,覆盖面最广、PC 端真有一键(`JingMatrix/LSPatch`),但 footprint 大、`assets/lspatch/` 等特征明显,对有反注入检测的高安全 App 会失效。
- **④native killOpen**：专治"不问系统、自己读 APK 字节校验"这一档,靠 PLT/inline hook 劫持 `open/openat`,常作为②③的附属部件;.so 可改名但内部符号表(`xh_core` 等)难藏。
- **⑤系统级(CorePatch/microG)**：不改 APK 一个字节,改攻击者自己的设备/ROM/`system_server`;对被审计的这份 APK 而言 footprint **为零**、审计单个样本原理上看不到,但改动**不能分发**、只在攻击者自己已 root 的设备上生效。
- **防御方的根本落点**：客户端所有检测在流派⑤面前都和被检测目标站在同一个不可信地基上——治本靠**让校验结果参与业务解密 + 绑定服务端新鲜 nonce**,把"绕过一个布尔判断"变成"解不出内容/服务端不认"。
