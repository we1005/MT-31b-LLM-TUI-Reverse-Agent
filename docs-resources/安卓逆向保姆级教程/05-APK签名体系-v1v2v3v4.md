# APK 签名体系：v1/v2/v3/v4、证书、密钥库

> 一句话点题：APK 签名要解决的问题和你熟悉的**代码签名/GPG/HTTPS 证书**完全一样——"这个包到底是谁发的、有没有被人动过手脚"——只是安卓在 20 年里换了四套实现方案(v1→v4),每一套都在补上一代的漏洞,而报告里那些"过签名校验"的骚操作,几乎全部是在这四套方案的边界和实现细节上做文章。

---

## 0. 先建立坐标：代码签名到底解决什么问题

你写后端服务时,大概率遇到过这几个东西：

- **GPG 签名**：发布一个 release tarball 时,附一个 `.asc` 签名文件,别人用你的公钥验证"这个 tar.gz 确实是你打的包,内容没被 CDN 中间人替换"。
- **Authenticode**(Windows 可执行文件签名)/**codesign**(macOS)：给 `.exe`/`.app` 签名,系统安装时弹"发布者：XXX 公司",没签名或签名失效就报"来源不明"。
- **TLS 证书链**：浏览器验证网站证书时,检查"这个证书是不是由受信任的 CA 签发的""证书对应的私钥持有者是不是这个域名的所有者"。

APK 签名要解决的是同一类问题,但场景更贴近前两者(代码签名),而不是 TLS(它**不需要**一个全局信任的 CA 根证书链):

1. **完整性(Integrity)**:APK 内容有没有被篡改?哪怕改一个字节,验证都要能发现。
2. **身份延续性(Identity Continuity)**：同一个包名(比如 `com.tencent.mm`)升级安装时,新版本必须是"同一个人"签的,否则系统拒绝覆盖安装——这是防止"别人做个假的微信升级包,把你手机上的真微信换掉"的关键防线。

注意一个和 TLS 证书**本质不同**的地方：**安卓不要求签名证书由权威 CA 签发**,自签名证书(self-signed certificate,自己给自己签的证书,没有第三方背书)完全合法且是**主流做法**——App 商店级别的身份认证交给 Google Play 后台去做实名审核,系统本身只关心"证书前后一致"这一件事。这个设计差异,是本篇后面所有内容的大背景。

## 1. 密钥学基础：证书、X.509、DN、指纹

在讲四代签名方案之前,先把几个每次都会冒出来的名词钉死。

### 1.1 非对称密钥对

跟你熟悉的 SSH/TLS 一样：一对数学上关联的**私钥(private key)**和**公钥(public key)**。私钥留在开发者手里签名,公钥(打包在证书里)随 APK 一起分发,任何人都能用它验证签名,但反推不出私钥。

### 1.2 X.509 证书 = "公钥 + 身份信息 + 签发者签名"的标准封装格式

X.509 是一个**通用的证书编码标准**,TLS 网站证书、代码签名证书、S/MIME 邮件证书全都用它,你可以把它类比成"一个带元数据的公钥文件格式"(有点像 protobuf 定义了字段,X.509 定义了证书里必须有哪些字段)。核心字段包括：

- **Subject DN(Distinguished Name,可分辨名称)**：标识"这个证书是谁的"的一组键值对,常见字段 `CN`(Common Name,常用名)、`O`(Organization,组织)、`OU`(Organizational Unit)、`L`(Locality)、`ST`(State)、`C`(Country)。类比：一个 `struct Identity { string CN; string O; string OU; ... }`。AOSP 官方测试证书的 DN 就是 `CN=Android, O=Android, OU=Android, L=Mountain View, ST=California, C=US`(后面第 6 节详说)。
- **Issuer DN**：签发者是谁(自签名证书里 Issuer 和 Subject 是同一个)。
- **公钥**、**有效期**、**签名算法**(证书本身也要被签发者签一道,证明"这个证书没被篡改")。

### 1.3 证书指纹(fingerprint)

对整个 DER 编码的证书二进制内容做一次哈希(现在通行 **SHA-256**,早年也有用 SHA-1/MD5 的),得到一串定长十六进制串,就是"指纹"。作用等价于 SSH 里的 `known_hosts` 指纹或 Git commit 的 hash——**内容一旦变化,指纹必变**,是识别"这到底是不是同一张证书"最方便的手段。你会在报告和各种安全工具里看到 `SHA256: A4:0D:A8:0A:...` 这种写法,就是这个东西。系统在做"新版本证书是否和旧版本一致"的判断时,底层比较的正是证书数据(等价于比较指纹)。

## 2. 密钥库(Keystore)：私钥+证书的"保险柜文件"

私钥不能裸奔存在磁盘上,得有个带口令保护的容器文件——这就是密钥库(keystore)。类比你更熟悉的东西：有点像一个**加密的 `.pem` 文件打包器**,或者说是 Java 生态版本的 "带密码的证书钱包"。安卓开发链条上会遇到三种格式：

| 格式 | 全称 | 类比 | 现状 |
|---|---|---|---|
| **JKS** | Java KeyStore | Java 生态自己发明的私有二进制格式 | 老项目遗留,新版 JDK 已不推荐 |
| **PKCS12**(`.p12`/`.pfx`) | Public-Key Cryptography Standards #12 | 跨语言/跨平台标准格式,和你 `openssl pkcs12` 打交道时用的是同一个标准 | **现在的默认推荐格式**,`keytool` 新建 keystore 默认就是这个 |
| **BKS** | BouncyCastle KeyStore | BouncyCastle(一个知名开源密码学库,Java/Android 生态常用)实现的私有格式 | 主要出现在**App 自己内置的信任库**场景(比如自己实现证书锁定 pinning 时打包一份受信任证书),不是签名场景的主流 |

管理这些密钥库最常用的命令行工具是 **`keytool`**(JDK 自带),功能上大致对应你熟悉的 `openssl genrsa` + `openssl req`(生成密钥对 + 自签证书)的合集,只是全都塞进一个带密码的容器文件里管理,一份 keystore 里还能装多个"别名(alias)"对应的多组密钥对,类似一个小型密钥管理系统。

## 3. v1:JAR 签名方案(逐文件摘要)

### 3.0 背景：APK 本来就是个 ZIP

回到系列第 01 篇的结论——**APK 文件本质就是一个 ZIP 包**,改后缀成 `.zip` 直接能用 unzip 打开。而 v1 签名方案根本不是安卓专门发明的,它是**直接照搬 Java 的 JAR 签名规范**(JAR 包本身也是 ZIP),所以也叫 **JAR 签名(JAR Signature Scheme)**。签名产物就是三个纯文本/二进制文件,塞进 ZIP 内部的 `META-INF/` 目录：

```
APK(=ZIP)
├── META-INF/
│   ├── MANIFEST.MF   ← 每个文件的摘要清单
│   ├── CERT.SF       ← 对 MANIFEST.MF 的"摘要的摘要" + 逐条目摘要
│   └── CERT.RSA      ← 对 CERT.SF 的数字签名 + 证书本体(PKCS#7 格式)
├── classes.dex
├── AndroidManifest.xml
├── resources.arsc
└── res/...
```

### 3.1 三层文件各自的作用

1. **`MANIFEST.MF`**：遍历 ZIP 里几乎每个文件条目,对每个文件的**内容**算一次摘要(早期 SHA-1,现在普遍 SHA-256),写成 `Name: xxx / SHA-256-Digest: base64(...)` 的清单。类比：一份"每个源文件的 md5sum 清单"。
2. **`CERT.SF`(Signature File)**：先对整个 `MANIFEST.MF` 文件算一次摘要写在文件头;然后**再把 `MANIFEST.MF` 里每一条目的那一小段摘要块单独再摘要一次**,逐条写进 `.SF`。这个"摘要的摘要"设计不是为了炫技,是为了防御一种具体攻击：如果只签 `.SF` 头部那个整体摘要,攻击者理论上可以在**不改变整体摘要**的前提下,想办法在 `MANIFEST.MF` 里塞入格式技巧(比如利用某些解析器忽略的空白/换行差异)来偷换个别条目——逐条目再摘要一次就把这条路堵死了。
3. **`CERT.RSA`(或 `.DSA`/`.EC`,取决于算法)**：用私钥对 `.SF` 文件做真正的数字签名,产物是标准的 **PKCS#7(SignedData)** 结构,里面**打包了签名值 + 完整证书本体**——验证方不需要额外获取公钥,证书就在包里。

### 3.2 验证时的三级校验链

```
验证方拿到 APK →
  1. 用 CERT.RSA 里的证书公钥,验证 CERT.SF 的签名 ✅/❌
  2. 重新计算 MANIFEST.MF 整体摘要,比对 CERT.SF 头部记录的值 ✅/❌
  3. 对包内每个文件重新计算摘要,比对 MANIFEST.MF 里对应条目 ✅/❌
→ 三级都通过,才认为"完整性 OK,且是这个证书对应的私钥签的"
```

这条链的核心逻辑和 GPG 签一个 tarball 完全同构,只是拆成了"清单—清单的清单—清单的签名"三层,而不是直接对整个文件签一次。

### 3.3 致命缺陷：只管"ZIP 里列出来的条目内容",不管"ZIP 容器结构本身"

v1 方案摘要的对象,是"**MANIFEST.MF 里列出来的每个文件的解压后内容**",它完全不关心：

- ZIP 的**中央目录(Central Directory)**、每个 Local File Header 里的额外字段(extra field)、条目的先后顺序、是否存在"重名条目"——这些 ZIP 容器层面的结构完全不在签名覆盖范围内。
- 不同的 ZIP 解析器(比如"负责校验签名的那个解析器" vs "负责真正加载 dex/资源跑起来的那个解析器")在读取"重名文件该取哪一份""怎么处理额外的垃圾字节"这类边角情况时,行为可能**不一致**。

这就给攻击者留了一个经典套路：**让两个不同的解析器,对同一个 ZIP 文件"读出不同的内容"**——签名校验那个解析器看到的是干净的原版内容(所以签名照样通过),而实际运行时加载代码的那个解析器却被"喂"进了被篡改/植入的内容。这类"双重解析不一致(parser confusion / parser differential)"漏洞在历史上出现过不止一次：

- **Master Key 漏洞(2013,俗称"主密钥"漏洞)**：利用 ZIP 里存在重名条目时,签名校验流程和 dex 加载流程"各取一份不同的重名条目"这种不一致,使得签名依然对得上,但真正跑起来的代码却是被替换过的。
- **Janus 漏洞(CVE-2017-13156,2017)**：利用的是"一个文件可以同时是合法 ZIP 又是合法 DEX"这个巧合——DEX 文件格式允许在文件头之前有一段被忽略的前导字节,而 v1 签名只覆盖 ZIP 内声明的条目内容,不覆盖"ZIP 起始位置之前额外塞进去的字节"。于是理论上存在一种构造方式：往一个已签名 APK 的最前面插入一段数据,让这个文件"作为 ZIP 打开"看到的还是原来的东西(v1 签名照样通过),但"作为 DEX 直接加载"时会读到插入的那段新字节。这个漏洞只影响**仅有 v1 签名、且目标 minSdkVersion 落在 Android 5.0~8.0 区间**的 APK——**v2 签名的引入正是为了从根子上堵上这整类问题**(v2 对全文件字节做整体摘要,任何位置插入任何字节,摘要都会变)。

> 这类"证书对得上,但运行的代码不是原版"的机制,是理解报告里"签名一致性攻击/校验绕过"章节的重要背景知识,深入的绕过手法本身在 [`11-签名校验绕过全景.md`](./11-签名校验绕过全景.md) 和 [`../安全审计-签名校验绕过-开源工具全景与检测.md`](../安全审计-签名校验绕过-开源工具全景与检测.md) 里专门讲,这里只讲"为什么会有这个口子"。

## 4. v2:APK Signing Block(Android 7.0+,API 24)

### 4.1 设计思路的转变：不逐文件摘要,对"整个文件"分块摘要

v2(APK Signature Scheme v2,Android 7.0 Nougat 引入)彻底改变了摘要对象：**不再关心"ZIP 里有哪些逻辑条目",而是直接对 APK 文件的物理字节做整体摘要**——这样 ZIP 解析器怎么理解条目结构就完全不重要了,只要文件的字节序列有任何变化,摘要就对不上。这也**直接堵死了 Janus 那类"插入额外字节"的把戏**。

### 4.2 APK Signing Block：一个"夹"在 ZIP 结构里但普通 ZIP 工具"看不见"的区块

v2 的签名数据存放在一个新增的区块——**APK Signing Block**——里,它的物理位置很巧妙：

```
APK 文件物理布局(v2/v3 签名后):

┌──────────────────────────────────┐
│ ZIP Local File Headers + 数据    │  ← classes.dex / resources.arsc / res/... 的实际内容
├──────────────────────────────────┤
│ 【APK Signing Block】            │  ← v2/v3 签名数据全部塞在这里
│   size(8字节) ...                │
│   ID-Value 键值对们              │
│   ... size(8字节,和开头一致)     │
│   魔数 "APK Sig Block 42"(16字节)│
├──────────────────────────────────┤
│ ZIP Central Directory            │  ← 记录每个条目在哪
├──────────────────────────────────┤
│ End of Central Directory(EOCD)   │  ← 记录 Central Directory 在哪、多大
└──────────────────────────────────┘
```

妙处在于：普通的 ZIP/unzip 工具打开一个文件时,是**从文件末尾找 EOCD**,靠 EOCD 里记录的"中央目录偏移量"跳过去读 Central Directory,再由 Central Directory 找每个条目——它压根不会去看 EOCD 和 Local File Header 之间那一大块"多出来的" APK Signing Block,所以一个 v2 签名的 APK**依然是一个完全合法、能被任意 ZIP 工具正常打开的 ZIP 文件**,只是安卓的包管理器额外知道去这个特定位置找签名。识别这个区块靠的就是那个固定的 16 字节魔数字符串 **`"APK Sig Block 42"`**——扫描工具/脱壳脚本经常靠 grep 这个魔数字符串来快速定位一个 APK 用了哪代签名方案。

区块内部是"长度前缀 + ID + 内容"的键值对序列,每种签名方案对应一个固定的 ID:v2 对应 `0x7109871a`,v3 对应 `0xf05368c0`(v4 不占用这个区块里的 ID,原因见第 5 节)。

### 4.3 摘要内容：分块 + 两级哈希(便于流式/增量校验)

v2 具体摘要哪几部分内容：①ZIP 条目数据区、②Central Directory、③EOCD(计算时把里面记录中央目录偏移量的字段临时清零,因为这个值本身依赖 Signing Block 的大小)。其中①这部分体积通常最大,v2 把它切成固定大小的分块(比如每 1MB 一块)分别求摘要,再对"所有分块摘要拼起来的结果"求一次顶层摘要——这是一种**类似 Merkle 树**的两级结构,好处是校验器可以**边读边算、流式处理超大文件**,不需要一次性把整个 APK 读进内存,这对安装时性能很关键。

### 4.4 v2 相比 v1 的核心提升总结

- **覆盖整个文件字节**,堵死"ZIP 解析歧义"这条老攻击面;
- **验证速度更快**(整体哈希 + 分块并行,不用像 v1 那样对每个条目单独 inflate 解压再摘要);
- 依然是"证书自签、系统只比对证书一致性"的信任模型,没变。

## 5. v3：证书轮换(lineage),Android 9+(API 28)

### 5.1 要解决的新问题：私钥要不要能换?

v1/v2 都有一个隐含假设：**一个 App 从第一次发布到生命周期结束,永远用同一把私钥签名**。现实中这个假设经常撑不住——签名私钥可能被离职员工带走、可能因为公司架构调整(收购/合并)要迁移到新的密钥管理体系、也可能单纯是密钥强度升级(比如从老算法换成更强的算法)。但前面讲过,"覆盖安装同包名 App 必须证书一致"是安卓的硬规则——**换了私钥,新签名的证书指纹必然变,系统直接拒绝覆盖安装,用户只能先卸载再装,数据全丢**。

### 5.2 lineage(证书世系/轮换链)机制

v3 在 v2 的基础上,额外塞进一段叫 **lineage(世系,也叫 proof-of-rotation,"轮换证明")** 的结构：一条记录"证书 A → 证书 B"的轮换声明,并且**这条声明本身是用旧证书 A 对应的私钥签的**——本质是"旧钥匙亲口签字承认新钥匙是合法继任者",类比 PGP 生态里"用旧密钥给新密钥做交叉签名(cross-signing)"的做法,或者证书自动续期时"旧证书为新证书背书"的思路。系统在校验新版本 App 时,如果发现证书变了但能顺着 lineage 链一路验证回原始那把受信任的证书,就依然认为"身份延续、合法升级",允许覆盖安装。lineage 里还能携带一些精细权限位,比如"新证书是否有权限继续共享同一个 UID""是否允许回滚到旧证书签的版本"等。

### 5.3 使用场景

大型 App 厂商的密钥迁移、多产品线合并签名体系、密钥泄露后的"体面下线旧钥匙",都是 v3 lineage 的典型用武之地。

## 6. v4：增量/流式签名(Android 11+,API 30)

v4 和前三代思路不同,它不是"换一种摘要整个文件的方式",而是专门为**增量安装/边下边装**场景设计的**旁挂机制**:

- 产物是一个独立的**`.apk.idsig`** 附属文件(不塞进 APK 内部),内容是对 APK 按固定页大小(常见 4KB)切块后建的 **Merkle 哈希树**(每个叶子是一页数据的哈希,层层往上聚合成一个根哈希)。
- 好处是配合安卓的 **IncFS(增量文件系统)**/`fs-verity` 机制,设备可以**一边流式接收 APK 的字节、一边逐页校验**,不必等整个文件下载完才能开始装/跑——这对"边玩边下"式的大型游戏安装体验(Google Play 的"Play Feed"/增量安装、`adb install --incremental`)是关键支撑。
- **v4 不能单独存在**：它的 Merkle 树根哈希本身要作为一个"额外摘要算法"的结果,被塞进 v2/v3 签名覆盖的"签名数据"里一起签名——也就是说信任根依然锚定在 v2/v3 上,v4 只是给"这份内容还没完全落地磁盘之前就能分页校验"这件事提供数据结构支持。

## 7. 系统到底用哪一层校验?—— 按 SDK 版本"就高不就低"但要求兼容

安卓包管理器(PackageManager,系统里负责管理"设备上装了哪些包、每个包的元数据/权限/签名"的核心系统服务,可以类比成一个内建的"包数据库")在安装/校验一个 APK 时,大致遵循这个逻辑：

1. **优先用 APK 里出现的最高版本签名方案**做校验(有 v3 用 v3,没有 v3 但有 v2 用 v2,都没有才退回 v1)。
2. 但如果这个 APK 的 `minSdkVersion`(声明支持的最低系统版本)低于某代方案要求的系统版本(v2 要求 API 24+,v3 要求 API 28+),那么在**跑在更老系统上的设备**上安装时,只能靠 v1(JAR 签名)校验——所以**打包工具默认会让 v1/v2/v3 同时存在、内容互相一致**,以兼顾新老设备。这也是为什么真实构建产物里 `META-INF/` 目录(v1 残留)和 APK Signing Block(v2/v3)经常**同时存在**,不是谁取代了谁,而是"分层兼容"。
3. 现在做签名操作用的官方工具是 **`apksigner`**(Android SDK build-tools 自带),它取代了老的通用 Java 工具 `jarsigner`——因为 `jarsigner` 只懂 v1 那套 JAR 签名规范,根本不认识 v2/v3 的 APK Signing Block,用它签出来的包在新系统上会退化成"只有 v1 保护",安全性打折。

## 8. 签名一致性：为什么"改一个字节都必须重签",以及升级覆盖的铁律

把前面几节串起来,现在可以回答两个报告里反复出现的关键问题：

**Q1：为什么改了 APK 内容(哪怕只改一行 smali、换一张图标)之后,必须重新签名?**

因为不管 v1 还是 v2/v3,签名覆盖的都是"内容的摘要"。内容变了 → 摘要变了 → 原来那份签名(是对"旧摘要"的签名)在验证时**必然对不上新内容重新算出来的摘要** → 验证失败。这不是安卓的"额外刁难",是数字签名机制的数学必然性,任何代码签名体系(GPG/Authenticode 同理)都一样：**内容和签名是绑死的,内容变了签名就失效,唯一出路是用私钥对新内容重新签一遍**。

**Q2：为什么"重签"之后,原来的 App 覆盖不上去,必须先卸载?**

因为改包的人(不管是破解者、汉化组还是你自己做实验)手上**没有原开发者的私钥**——私钥从来不随 APK 分发,只有开发者自己保存(这是整个信任模型能成立的前提,类比你不会把 SSH 私钥和公钥一起发给别人)。所以重签只能用**另一把自己生成的私钥/自签名证书**去签,产物的证书**指纹必然和原版不同**。而安卓有一条从 v1 时代延续至今、从未改变的硬规则：

> **同一个包名的 App,覆盖安装(不卸载直接装新的)时,新旧两个 APK 的签名证书必须一致**(v3 引入后放宽为"或能沿着 lineage 链验证到一致")。

一旦证书不一致,系统直接拒绝覆盖安装(常见错误提示是"应用未安装""签名冲突"一类),用户唯一的路是先卸载旧版(数据全丢)再装重签后的新版。**这正是"改机"类工具(MT 管理器、NP 管理器这类)存在的核心动机之一**：普通用户不愿意卸载丢数据,所以工具要么帮用户在系统层面"关掉/绕过"这条一致性校验,要么想办法让重签后的产物依然能通过校验——这部分具体机制留给 [`06-签名校验与防篡改.md`](./06-签名校验与防篡改.md)、[`11-签名校验绕过全景.md`](./11-签名校验绕过全景.md)。

## 9. AOSP testkey:AOSP 官方公开的"测试用"签名密钥

AOSP(Android Open Source Project,安卓的开源上游项目)源码仓库里,`build/target/product/security/` 目录下自带几对**公开的测试密钥**(`testkey`/`platform`/`shared`/`media` 等几个用途各异的 alias),用来给**工程/调试版固件**里预置的系统 App 签名,方便开发者本地编译刷机不用自己折腾一套密钥体系。这几对密钥的证书 DN 都类似 `CN=Android, O=Android, OU=Android, L=Mountain View, ST=California, C=US`,**私钥和公钥都直接躺在开源仓库里,谁都能拿到**。

这就带来一个众所周知的风险点：

- **AOSP 官方文档和整个安全社区都反复强调**:testkey **绝对不能**用来给正式发布的固件/产品签名——一旦某个真实设备厂商偷懒直接拿这套公开密钥去签发行版固件(历史上确有厂商翻过车),那么**任何人**都能用同一把公开私钥,签出一个能被那台设备当作"系统级/平台级签名"接受的恶意 App,直接绕过大量权限限制。
- 反过来,这个"公开"的特性也让它成为**安全检测/取证的天然指纹**：因为 testkey 证书的内容(DN + 公钥)是完全固定、公开发布的,它的**证书指纹(SHA-256)也是一个固定不变的已知值**(常见写法形如 `A4:0D:A8:0A:...` 这样的十六进制串,各类静态扫描工具、`apksigner`/`androguard` 之类分析库里都会内置这份"已知测试证书指纹表")。所以扫描工具只要抓到一个 APK 的签名证书指纹**命中这份已知列表**,就能高置信度地判定"这个包被工程测试密钥签过"——常见于两种场景：①开发者调试期间没切换到正式签名就打了包外泄;②改机/破解工具偷懒直接复用了这套公开密钥重签(这是一个非常低成本但极易被检测识破的做法,详见 [`../安全审计-签名校验绕过-开源工具全景与检测.md`](../安全审计-签名校验绕过-开源工具全景与检测.md) 里"取证识别"部分)。

```
                打包阶段(开发者机器)
  源码/dex/资源 ──► 压缩打包成 ZIP(APK)
                        │
              apksigner + 私钥/证书(来自 keystore)
                        │
        ┌───────────────┼────────────────┐
        ▼               ▼                ▼
   v1: 塞 META-INF/   v2/v3: 插入 APK    v4: 生成旁挂的
   MANIFEST.MF/       Signing Block      .apk.idsig
   CERT.SF/CERT.RSA   (逐块摘要+签名)    (Merkle 树)
        └───────────────┬────────────────┘
                         ▼
                  签名后的 APK 文件
                         │
                安装到设备(安装阶段)
                         │
      PackageManager: 按 minSdkVersion/设备API 挑最高可用方案校验
                         │
        ┌────────────────┴─────────────────┐
        ▼                                  ▼
  全新安装:证书记录进包数据库           覆盖安装(同包名已存在旧版):
                                       比对新旧证书是否一致/可 lineage 验证
                                             │
                                   一致 → 允许覆盖    不一致 → 拒绝安装
```

## 一页速记

- **签名要解决什么**：身份(谁发布的)+ 完整性(有没有被改),类比 GPG/Authenticode,但**不需要**权威 CA 根链,自签名证书是主流。
- **证书**:X.509 格式,核心字段是 Subject DN(CN/O/OU 等)和公钥;识别证书身份靠 **SHA-256 指纹**。
- **密钥库**:JKS(老)/**PKCS12**(现在的默认,`.p12`)/BKS(BouncyCastle,常见于 App 内置信任库而非签名场景),用 `keytool` 管理。
- **v1(JAR 签名)**:`MANIFEST.MF`(逐文件摘要)→`CERT.SF`(摘要的摘要)→`CERT.RSA`(PKCS#7 签名+证书)。**只管条目内容,不管 ZIP 容器结构**→留下 Master Key、**Janus(CVE-2017-13156)**这类"双重解析不一致"漏洞的口子。
- **v2(Android 7+/API24)**：插入 **APK Signing Block**(魔数 `"APK Sig Block 42"`),对**整个文件字节**分块+两级摘要,普通 ZIP 工具因为只认 EOCD/Central Directory 而"看不见"这个区块,但完整性覆盖面变成了全文件。
- **v3(Android 9+/API28)**：引入 **lineage(证书轮换链)**,允许"旧私钥签字认证新证书",支持密钥合法轮换而不破坏升级覆盖。
- **v4(Android 11+/API30)**：旁挂 `.apk.idsig` 里的 Merkle 树,支撑边下边装的流式/增量安装校验,**依附于 v2/v3**,不能单独作为信任根。
- **系统选层规则**：就高不就低,但受 `minSdkVersion` 约束,所以构建产物通常 v1/v2/v3 同时存在以兼容老设备。
- **AOSP testkey**:AOSP 源码公开的测试密钥,私钥人人可得,**绝不能签正式产品**;因为公开且固定,其证书指纹是检测工具的"已知黑名单"特征之一。
- **核心铁律**：内容变 → 摘要变 → 旧签名必然失效 → 必须用某把私钥重签;重签后证书指纹必然和原版不同 → 触发"覆盖安装证书必须一致"规则 → 这正是改机类工具要突破的第一道墙。
