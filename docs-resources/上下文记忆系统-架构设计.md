## 0. 目标系统约束(设计的地基,先钉死)

| 约束 | 含义 | 对设计的强制影响 |
|---|---|---|
| 后端 = 本地 Qwen3.6-35B-A3B MoE(3B 活跃) | 行为近"小模型",lost-in-middle 在远未填满窗口时就退化 | 有效工作集必须远小于 256K,关键信息钉首尾、中段留空 |
| 上限 256K,temp>0 | 名义大但精确召回长度短;非确定 | 不能"塞满就算能用";一切 LLM 步骤(尤其摘要)要有确定性兜底与熔断 |
| lemonade 单并发,必须串行 | 父+子/前台+后台同时在线会卡死后端(已踩过) | 禁止并发子代理、禁止后台记忆蒸馏;所有额外 LLM 调用串行且尽量为零 |
| SWA/llama.cpp,前缀缓存极敏感 | 只复用"从 token 0 起逐字节相同的最长公共前缀";一字节变化→从该点全量重 prefill | 静态进头部、动态拼末尾、历史 append-only;中段绝不改写 |
| 工具仅 shell/grep/read_file/append_note | 无 embedding、无向量库、无检索工具 | 检索靠 grep+read;结构化知识靠宿主侧零-LLM 派生;不引入第五工具 |
| 任务 = APK 逆向(读反编译树/多跳调用链/安全审计) | 检索的是精确标识符(类名/方法/行号),不是语义近似 | grep > embedding;证据必须 verbatim(file:line);抽取式压缩,禁抽象式摘要 |

### 四条硬约束(违反则设计作废)

- **(a) 台账/动态内容绝不进 system 头部**,只拼 messages 末尾 ephemeral(不写回持久 messages)。`ContextManager.system()` 只返回静态 `systemPrompt`。
- **(b) prefix-cache 命中率(cachedInputTokens/inputTokens)是一等 benchmark 验收门**:收尾步 ≥90%、全程均值 ≥60%。不是可选遥测。
- **(c) 不设计"每步重折叠"的重机器**。对 SWA,折叠=改历史中段=从折叠点起前缀全量重算。保留"逼近 256k 才折一次止血"(`compactThreshold=160k`),阶段2 折叠降级为**可选**;主力回收机制改为**写入即落盘**(见 §3.3),它是前缀安全的。
- **(d) 核心"调用边"捕获不能只依赖正文正则**(chm-medium 实测 `promoteFromProse` ✓率仅 26%)。改为**从 grep 命中 + read 范围零-LLM 派生**调用边,`promoteFromProse` 降为兜底。
- **(e) 解掉死锁**:`hasRead` 去重守卫会拦住"内容已被驱逐/折叠、模型需要重读"的合法重读。

## 1. 现状盘点(阶段1 Ledger 已有什么 / 缺什么)

### 1.1 `src/memory/ledger.ts` 已有

- **数据模型**:`Hop{raw,from,to,evidence,corroborated}`、`ReadEntry{path,ranges[]}`、`GrepEntry{pattern,path,hitCount}`、`LedgerState`。
- **系统自动抽取(零 LLM)**:`observeToolResult(name,args,result)` 从 `read_file` 抽 `reads[]`、从 `grep` 抽 `greps[]`(含命中数、同 pattern+path 去重留最新)。这是治"小模型不自律写台账"的核心,方向正确。
- **正文提升(正则,零 LLM)**:`promoteFromProse(text)` 从 assistant 正文捞 `跳N: A→B | 证据 file:line`,按 `hopKeyPart(from→to)` 语义键去重,与 `reads[]` 交叉核验标 `corroborated`。
- **去重守卫**:`hasRead(path,start,end)`(范围覆盖即命中)、`hasGrep(pattern,path)`。
- **渲染**:`render(maxChars=4000)` 出紧凑台账;`renderChainGraph()` 收尾 O(1) 出链路草稿。
- **遥测**:`stats()` 返回 `{hops,corroborated,reads,greps}`。
- **持久化钩子**:`toJSON/fromJSON`(供 resume)。

### 1.2 `src/agent.ts` 已有(与记忆相关)

- **SWA 稳定前缀已落地**(`callLLM` 307-323):`system: this.systemPrompt`(静态);台账 `led=ledger.render()` 每步临时拼 `[...messages, {role:'user', content:'【系统进度台账…】\n'+led}]`,**不写回** `this.messages`。实测 0%→97% 前缀复用。
- **前缀缓存遥测**(706-717):`cachedInputTokens/inputTokens` 每步打印,聚合进 `cacheSum/cacheCount/cacheMin`,收尾进 `[SCORECARD]`。
- **保留式折叠**(`compactHistory` 425-471):`compactThreshold=160k` 门控,只有真逼近上限才折一次;折叠成带**可抄重读指令**的 stub(`read_file(path=…,start=,lines=)`),永不折 append_note/assistant 正文;`foldedIds` 记录已折 id。
- **诚实标尺**(`contextTokens` 386-392):对当前 messages 估算一次(非累加),独立于被污染的 `budget.used`。
- **止损/防断链一大簇**:`stallCap/readHopStallCap/exploreCap/enoughHops/forcedFinish/maxForcedSteps/nudge/dedupHit/stuckIntervene`。这些是"行为支架",实测对 35B load-bearing,保留。
- **计分卡**(`emitScorecard` 400-416):steps/ledger/cache/max_ctx/folded/dedup/nudges/stall/forced/interventions。

### 1.3 缺什么(本设计要补的 gap,按杠杆排序)

| # | Gap | 症状/证据 | 对应硬约束 |

## 2. 设计原则(从百家提炼 + 明确取舍)

每条给出**借鉴谁 / 为什么 / 针对 256K 小模型的理由 / 放弃什么**。

### 原则 1:静态钉头部,动态拼末尾,历史 append-only(SWA 第一铁律)
- **借鉴**:Claude Code(稳定内容钉头部+压缩后原位重注入)、Codex(BodyAfterPrefix,前缀不重写只 append)、Pi(lazy-skill via read 落尾,"without busting the prompt cache")、前缀缓存研究(LCP 复用)。
- **为什么**:llama.cpp 只复用逐字节相同的最长公共前缀。我们已实测 0%→97%。
- **256K 小模型理由**:末尾恰是 U 型曲线的 recency 高注意力位,尾置台账**既保缓存又对抗 lost-in-middle**,一举两得。
- **放弃**:MemGPT 的"记忆块居前 + self-edit in-place"(实测命中 43.9% vs append-only 98.5%,是我们 0%→97% 的镜像反例);OpenCode/Anthropic 的 `cache_control` 显式断点与服务端 `cache_edits`(llama.cpp 无此能力);vLLM 块哈希/SGLang RadixAttention 中段块复用(llama.cpp 不做内容寻址,除非之前每字节相同否则不复用)。

### 原则 2:回收=写入即落盘,不做事后折叠改中段(取代旧文档的重折叠机器)
- **借鉴**:Claude Code Tool Result Budget(大工具结果落盘只留 ~2KB 预览+路径,`O_CREAT|O_EXCL` 以 tool_use_id 为键幂等)、OpenCode `prune`(确定性、不调 LLM)、长上下文综述(蒸馏进台账后丢原始回显)。
- **为什么(关键洞见)**:"事后折叠"改的是历史数组中段的老消息 → 对 SWA 从改动点起缓存全失效。而"**写入即落盘**"是在工具结果**第一次**进入 messages 时就写成截断 stub(全文另存 scratchpad),此后逐字节冻结、永不重写 → **前缀安全**。这从根上取代了每步重折叠。
- **256K 小模型理由**:源头就把整棵反编译树/巨 grep dump 挡在模型 context 外,活跃工作集常驻几 K(loop 已观测 5k 平台化),中段轻,精确召回好。
- **放弃**:旧文档的"每步重折叠";`compactThreshold=160k` 的事后折叠降为**可选止血**(仅极端逼近 256k 时兜底,接受那一次重算)。

### 原则 3:调用边从"grep 命中 + read 范围"零-LLM 派生,正文正则降为兜底
- **借鉴**:Aider(tree-sitter def/ref 静态抽符号)、长上下文综述(抽取式、逐字保留符号/行号)、mem0 反面教训(把多跳链"压平"丢结构是逆向大忌)。
- **为什么**:`promoteFromProse` 依赖 35B 在 temp>0 下稳定吐出规范"跳N"格式,实测 ✓率仅 26%;而"模型 grep 了 callee 符号 + read 了包含该命中的范围"这两个**确定性事实**足以由宿主侧派生出一条"caller→callee | file:line"边,零 LLM、不受 temp 影响。
- **256K 小模型理由**:把最脆弱的一环(模型自述链路)从热路径移除,edge 捕获不再受模型发挥波动。
- **放弃**:mem0 的 LLM 抽实体建图(Mem0g 涨点微、LLM 翻倍);任何 embedding 语义抽取。

### 原则 4:检索即时化(just-in-time),宿主侧精排,绝不全量预载
- **借鉴**:长上下文综述(即时检索)、Aider(signatures-only outline + PageRank)、continue.dev(召回多→精排少,但零 LLM 版)、Pi(read 带 offset/limit、tool result 双表示截断)。
- **为什么**:256K 够大不等于该塞满(context rot 远未填满就掉点);逆向是"大树里找具体函数"的小-needle 领域任务(掉幅最大)。
- **256K 小模型理由**:小模型对 distractor 极敏感,反编译树里同名/相似函数是最伤的干扰项,grep 命中要 rerank 只留 top-K。
- **放弃**:continue.dev 的 embedding 向量库 + LLM rerank(无本地 embedding、单并发不能后台建索引、会抢并发槽);MCP 一次性预载大量 schema。

### 原则 5:结构化台账系统维护,不指望模型自律;有界、抽取式、verbatim
- **借鉴**:MemGPT core-memory 块 schema(label+description+char-limit)但**反转 self-edit → 系统维护**;mem0 整数 ID anti-hallucination + SAGE 启发式新颖度门;Codex/OpenCode 续接式结构化摘要模板。
- **为什么**:实测最大痛点就是"小模型不自律写台账"。系统 `observeToolResult` 零-LLM 抽取已验证有效。
- **256K 小模型理由**:关键跳被系统固化在尾部台账,而非埋在长历史中段(lost-in-middle 免疫)。
- **放弃**:MemGPT `memory_rethink` 整块重写每轮跑(35B temp>0 昂贵且幻觉掉 verbatim);mem0 每写 2 次 LLM 的写路径(单并发下阻塞主生成);LLMLingua/抽象式摘要(丢精确符号/行号=逆向命脉)。

### 原则 6:压缩/摘要以零-LLM 为主,LLM 摘要是罕见的最后手段且加熔断
- **借鉴**:Codex 非-LLM token-budget 压缩(用 WorldState/ledger 种子开 fresh window,省一次串行往返)+ 6 行 handoff prompt + summary_prefix("另一个模型写的")、OpenCode "压完 token 未降就终止"、Claude Code 最便宜优先级联。
- **为什么**:lemonade 无服务端 compaction;每次 LLM 摘要独占唯一并发槽、temp>0 非确定、可能"压不下去"(已知无限压缩循环/压缩自身溢出)。
- **256K 小模型理由**:多次摘要丢链是长程调用链追踪头号风险(Codex 官方 issue 已确认);对策=append-only 累积 ledger,别对摘要再摘要。
- **放弃**:并发/后台记忆蒸馏、fork 子 agent 摘要、extended-thinking 两阶段草稿摘要、autocompact 自动重读近 5 文件(级联翻倍)。

### 原则 7:静态知识钉头部并做小;协议是行为支架不可砍
- **借鉴**:Aider repo map(有界、静态)、Codex AGENTS.md(32KiB 有界拼接)、Claude Code(CLAUDE.md 目标 <200 行)、Pi(sub-1K prompt——**只借放置纪律,不借极端最小化**)。
- **为什么/256K 小模型理由**:Pi 的极简前提是"前沿模型被 RL 训到天生懂 agent 行为",对 Qwen3.6-A3B 不成立;我们的 4 阶段协议+7 铁律是 load-bearing(memory 已判定主瓶颈是行为 11/12 不是知识)。但静态前缀也别撑肥(大前缀把活跃任务挤到窗口深处伤小模型注意力)。
- **放弃**:Pi 式砍协议;启动全量加载整套 CLAUDE.md 层级+所有 import。

### 原则 8:跨会话 = append-only rollout + 从 checkpoint 反向扫描 + ledger 种子重建
- **借鉴**:Codex append-only JSONL rollout + reconstruct-from-last-checkpoint、我们已有的 `resume.ts`/`ledger.toJSON`。
- **为什么**:resume 不该回放全量原始历史;ledger 就是机器态 WorldState 快照(Codex 验证此模式)。
- **放弃**:bun-sqlite/drizzle/MessageV2 层级(对轻量 CLI 过度工程);插件式学习型记忆。

## 3. 定制架构

### 3.1 分层记忆总览

```
┌─ L0 静态知识层(stable prefix,整会话逐字节不变,走前缀缓存)───────────┐
│   system = systemPrompt:                                              │
│     · 4 阶段渐进探索协议 + 7 铁律 + Token 预算(≤~180 行)              │
│     · 4 工具 JSON schema(固定顺序,冻结)                              │
│     · APK 静态地图(Aider PageRank 枢纽,≤8K token,阶段4)             │
│     · skill 一行清单(阶段4,正文按需 read 落尾)                       │
└──────────────────────────────────────────────────────────────────────┘
┌─ L1 工作集(live messages,append-only,byte-frozen once written)─────┐
│   [user 任务] [assistant 正文+tool-call] [tool 结果或落盘 stub] …      │
│   · 大工具输出写入即落盘(§3.3),只留 ~2KB 预览 + scratchpad 路径      │
│   · assistant 正文(含跳结论)与 append_note 结果永不落盘              │
└──────────────────────────────────────────────────────────────────────┘
┌─ L2 结构化台账 Ledger(带外,每步拼 messages 末尾 ephemeral,不写回)──┐
│   goal · CallGraph(边,零-LLM 派生)· reads(带 live 标记)· greps    │
│   render() ≤4K,始终是整段 prompt 的最后一个东西                       │
└──────────────────────────────────────────────────────────────────────┘
┌─ L3 长期/跨会话(scratchpad 磁盘,append-only)──────────────────────┐
│   · transcript.jsonl(全量 ModelMessage,审计流,永不删)              │
│   · ledger snapshot(toJSON)· 落盘的工具全文(tool_use_id 为键)      │
│   · resume:反向扫描到最近 checkpoint + ledger 种子重建窗口           │
└──────────────────────────────────────────────────────────────────────┘
检索层(横切):grep→read_file 即时取证;宿主侧 PageRank 精排 grep 命中;
             read outline 模式(只回签名);零 embedding。
```

**双层分离(OpenCode 招)**:L3 transcript 是唯一真相/永不删;发给模型的 L1+L2 只是它的一个"廉价、偏近期、可重建的投影"。裁剪/落盘只动投影,不动真相。

### 3.2 256K 预算怎么花(BodyAfterPrefix 计量)

采用 Codex 的**前缀外计量**:压缩预算只算"前缀之后新增的正文",触发时绝不改前缀。

| 区段 | 预算 | 说明 |
|---|---|---|
| L0 静态前缀 | ~8–16K(含 APK 地图) | 冻结、缓存;`baseline = prefill_input_tokens` |
| L1 工作集(body) | 目标常驻 **≤30–50K** | 靠 §3.3 落盘保持小;实测已 5k 平台化 |
| L2 台账 ephemeral 尾 | ≤4K(`render` 上界) | 每步重拼但只在末尾,重算成本 O(尾巴) |
| 输出预留 | 8K(`maxOutputTokens`) | 防单轮爆炸 |
| 安全缓冲 | 20K | 给摘要自身留余量(OpenCode COMPACTION_BUFFER 招) |

**阈值(全部对"body-after-prefix"计量,不是名义 256K 的百分比)**:

- **软目标**:工作集 body ≤ 50K。正常情况下(有落盘)根本到不了。
- **`ctxCeiling` 硬止损收尾**:body 超 120K(现状值,保留)→ 强制收尾报告已确认证据。
- **`compactThreshold` 折叠止血**:body 逼近 160K → 折一次(可选,罕见)。
- **理由**:35B lost-in-middle 远在 256K 之前就退化,触发点必须大幅前移(约 40–50% 而非前沿模型的 87/90%),且 keep 要保"当前调用链工作集"而非机械丢最旧。

### 3.3 前缀缓存友好的消息布局(核心)

**装配唯一入口** = `ContextManager.buildCallMessages()`(阶段3),现阶段即 `agent.ts:callLLM` 307-323 的逻辑,规范化为:

```
system  := systemPrompt                         // L0,静态,永不含动态内容(硬约束 a)
messages := [                                    // L1,append-only,逐条 byte-frozen
   ...this.messages                              // 真实历史(含落盘 stub)
]
callMessages := led
   ? [...messages, { role:'user',                // L2,ephemeral 尾,不写回
        content:'【系统进度台账·非用户输入,直接用,别重新推导已确认的跳】\n'+led }]
   : messages
```

**写入即落盘(取代事后折叠,前缀安全)**:`appendToolResult`(957)在把工具结果推入 `this.messages` **之前**:
1. `ledger.observeToolResult` 先吃**全文**(抽 reads/greps/派生边);
2. 若结果体积 > 阈值(如 2KB / ~500 token):把全文以 `tool_use_id` 为键幂等写入 scratchpad(`O_EXCL`),messages 里只放 `{folded:true, tool, path, range, hits, preview(~2KB), reread:'read_file(path=…,start=,lines=)'}`;
3. 该 stub 一次写定、逐字节冻结、永不重写 → **前缀不破**。

**为什么这比 `compactHistory` 好**:`compactHistory` 是事后回扫改老消息(改中段,破前缀);写入即落盘是第一次就写小的,历史保持 append-only。`compactHistory` 因此降级为极端兜底(body>160k 才动,接受那一次重算)。

**确定性序列化(保逐字节稳定)**:grep 命中按 `file:line` 排序(显式 `--sort path`);read_file 固定行区间;stub JSON 固定 key 顺序;去掉一切时间戳/随机 id。

**冷启动预热**:进程启动、接首个真实查询前,先发一条只含 L0 静态前缀、`max_tokens=1` 的预热请求,把巨型静态前缀 KV 提前算进 slot 0。首个查询只重算查询尾巴。

**单槽纪律**:`-np 1`(单并发天然单槽);`--cache-ram` 足以容纳一条 256K 会话 KV,空闲时 slot 0 不被逐出。

> **SWA 窗口剪枝待验**:需确认本地 Qwen3.6-A3B 构建是否真开 SWA、`n_swa` 窗口多大(看 llama-server 启动日志)。若窗口 < 工作上下文且在剪枝(症状:命中率随 ctx 长度系统性下滑,阈值≈窗口大小),则加 `--swa-full` 关窗口剪枝恢复完整前缀可缓存,并用 `--cache-type-k q8_0 --cache-type-v q8_0` 抵消显存。这由 §6 的"命中率对 ctx 长度曲线"驱动决策。

### 3.4 调用边零-LLM 派生(硬约束 d 的落点)

在 `ledger.ts` 新增 `CallGraph`,与散文 hop 分离:

```
interface Edge { from: string; to: string; evidence: string /*file:line*/;
                 source: 'derived'|'prose'; corroborated: boolean }
```

**派生规则(零 LLM,确定性)**:
1. `observeToolResult('grep', {pattern=S}, {hits})`:记下"符号 S 在 file F:line L 被引用"的候选(callee=S)。
2. `observeToolResult('read_file', {path=F}, {range∋L})`:在**已读到的该范围文本**里,用宿主侧确定性解析找 L 所在的**外围方法**(Java:向上回扫最近的方法签名 `修饰符? 返回类型 方法名(...)`;smali:最近的 `.method`)。得 caller。
3. 产出边 `caller → S | F:L`,`source='derived'`,与 reads 交叉核验标 `corroborated`。
4. **兜底**:`promoteFromProse` 仍跑,但产出的 `source='prose'` 边只在没有对应 derived 边时保留;去重键 `from→to`,derived 优先覆盖 prose。

**为什么可行且零 LLM**:grep 命中的 file:line 与 read 的范围文本都是我们手里的确定性事实;外围方法定位是纯字符串/正则解析(必要时用 tree-sitter-java WASM,见阶段4),不调模型。这把 ✓率从 26%(纯正文)拉到派生上限。

`renderChainGraph()` 改为优先渲染 `CallGraph` 的 derived 边,prose 边作补充。

### 3.5 去重守卫 vs 驱逐后重读的死锁解法(硬约束 e)

**病根**:`compactHistory`/落盘把某 read 范围的类体驱逐出 live 上下文并留"请重读"stub,但 `ledger.reads[]` 仍记着该范围 → `hasRead` 命中 → `dedupHit`(agent.ts:475)拦截重读 → 模型永远拿不回被驱逐的类体(loop 已观测"追对却因类体被折叠产不出图")。

**解法**:给 `ReadEntry.ranges` 每段加 `live: boolean`。
- 正常 read → `live:true`。
- 被落盘/折叠驱逐 → 新增 `ledger.markEvicted(path, range)` 置 `live:false`(在 `appendToolResult` 落盘时、`compactHistory` 折叠时调用)。
- `hasRead(path,start,end)` **只对 `live:true` 的范围返回命中** → 被驱逐的范围可合法重读。
- 结构化条目本身保留(仍用于 §已读类展示与边派生),只是不再当作"内容在场"。

重读回来后该范围重新 `live:true`。这样"去重"只在内容**确实在场**时生效,驱逐即解锁重读。

### 3.6 压缩/摘要触发与策略(级联,最便宜优先)

严格串行,按成本升序:

1. **写入即落盘(零 LLM,§3.3)** —— 常态、主力。工具结果第一次就写小。
2. **台账沉淀(零 LLM)** —— `observeToolResult`/派生边持续把探索沉淀进 L2;原始回显落盘后靠台账+磁盘指针召回。
3. **事后折叠止血(零 LLM,可选)** —— 仅 body>`compactThreshold`(160k) 触发一次(接受那次重算);现状 `compactHistory` 保留但极罕见触发。
4. **LLM 结构化摘要(最后手段,罕见)** —— 仅当上述都压不住且必须继续时,**串行**跑一次:
   - 用 Codex 6 行 handoff prompt + 逆向补充清单(已确认调用边 / 未解析的 hop / 已发现的安全 sink);产出**结构化字段写进 ledger**,不产自由文本。
   - 用 summary_prefix 显式框定"另一个模型写的",避免 35B 误当自己先前推理续编。
   - **熔断**:压完 token 未下降 → 终止;连续失败 → 停,不无谓重试。
   - **append-only 重建优先**:优先用 Codex 非-LLM 路径——直接用 ledger 当种子开 fresh window,省掉这次串行往返;只有 ledger 不足以续接才真调 LLM 摘要。绝不"对摘要再摘要"。

### 3.7 检索:何时 grep/read 而非全量

- **即时取证**:上下文只留轻量标识符(路径/类名/grep query),`grep` 定位 → `read_file` 按需取,逐跳"摸"链。绝不 dump 整树。
- **宿主侧精排(零 LLM)**:`grep` 常返几百条 → 用 §3.4 的候选 + APK 地图 PageRank 分对命中排序,只回 top-K + 命中总数(`hitCount` 已存)。这是 continue"召回多→精排少"的零-LLM 版。
- **outline 模式**:`read_file` 加 `mode: outline|range|full`,默认 outline(只回方法签名+行号,函数体折成 `…`)。追链先 outline 看签名、再 range 精读单方法,每跳花很少 token。
- **复述式再锚定(零成本 prompt)**:在让模型下审计结论/多跳推理前,协议要求先逐字复述刚检索到的目标函数签名 + file:line + 调用边,再推理(对不能改权重的本地模型是唯一可行增益档 +4~15%)。

### 3.8 去重 / 衰减

- **reads**:范围去重靠 `hasRead`(带 live 标记);驱逐即失效可重读。
- **greps**:同 pattern+path 留最新(已有)。
- **边**:`from→to` 语义键去重,derived 覆盖 prose。
- **衰减**:L2 不做时间衰减(逆向证据不因旧而失真);L1 的旧大结果靠落盘"衰减"成指针。**新颖度门(SAGE 招)**:若真要在 `append_note` 前做任何 LLM 抽取(阶段3 摘要),先过零成本门(本轮是否触达新文件/新类/新符号),不达标不抽取,把写侧 LLM 频率压到最低。

### 3.9 跨会话持久化

- **transcript.jsonl**:append-only 写全量 ModelMessage(L3 真相);落盘工具全文以 `tool_use_id` 为键。
- **ledger snapshot**:`toJSON` 定期落盘(在硬止损/收尾/每 N 步的确定性 checkpoint,借 Codex pre-compact hook 时机)。
- **resume**:`resume.ts` 反向扫描到最近 checkpoint,**不回放全量原始历史**;用 ledger(goal + CallGraph + reads/greps)当种子重建一个干净窗口 + 最近若干真实 turn。续接式(Codex/OpenCode)。

| 调用边 | 依赖正文正则 | **grep 命中+read 范围零-LLM 派生**,正则兜底(硬约束 d,✓率 26%→目标 >60%) |
| 去重 vs 重读 | 未处理死锁 | **live 标记**,驱逐即解锁重读(硬约束 e) |
| 命中率地位 | 可选遥测 | **一等 benchmark 门**(收尾 ≥90%、均值 ≥60%)(硬约束 b) |

一句话:**静态钉头部、动态拼末尾、历史 append-only;回收靠源头落盘而非事后改中段;调用边靠确定性派生而非模型自述;台账系统维护、有界、verbatim、尾置——既保 SWA 前缀缓存,又把关键证据放到 35B 最敏感的 recency 位,一举两得。**

## 7. 红队复审（V2）与落地前提（务必先读）

> 本节由独立红队对上文 V2 设计复审后追加。**裁决：方向对、比旧文档强（三条 SWA/单并发铁律贴合约束），但立论悬空、局部照搬云端重装备——落地前必须先解决下列硬伤。**

### 7.1 落地前提（在写任何阶段2代码之前先做）
1. **先补 benchmark 地基，否则所有决策门都是空中楼阁。** 设计的头条指标（`promoteFromProse ✓率 26%→>60%`、边✓率、多跳成功率、rubric 质量分）所依赖的 **题库 / per题 ground-truth 边标注 / 自动边匹配打分器 / 可离线运行的判分口径** 在 repo 里都不存在（现只有 test-guards.ts/demo.sh/test-resume.sh）。→ 先落地：`bank` + 每题 ground-truth 边集 + **纯机械判分器**（`边命中的 file:line 是否落在 ground-truth 集合`，确定性、离线、不需强模型）。**放弃 rubric 主观分**除非明确单并发/离线下的判分执行者（同一 35B 自评逆向质量+核对 verbatim 行号不可靠）。连头条动机数字 26% 目前在 repo 内都无产出脚本、不可复现——补上。
2. **加一条离线确定性单测进 `test-guards`（最高价值守卫）**：断言 **`system` 前缀在所有步骤逐字节相同** + 台账只出现在 `messages` 末尾且不写回 `this.messages`。这一条同时守硬约束 (a)(b)，是**唯一不依赖在线后端**就能防回退踩 SWA 铁律的守卫，远比"改注释(G5)"有力。

### 7.2 边派生（§3.4）正确性风险 = 一等公民（错边零容忍）
零-LLM 边派生把"脆弱"从模型自述**搬到了宿主正则**，确定性 ≠ 正确：
- "在已读范围里向上回扫最近方法签名"在 **outline/窄范围 read**（签名在窗口上方）、**lambda$/access$/合成方法/匿名内部类嵌套/重载** 下会**系统性错配**，产出 `corroborated=true` 的**高置信错边**污染链路图——可能比 26% 的诚实失败更糟。
- `deriveEdge` 的 **grep 候选↔read 配对算法**（命中 >60% 的技术核心）在设计里**完全缺失**，必须写清。
- 修法：只在 **read 范围确实包含外围方法完整签名**时才产边，否则标 `uncertain` 而非猜"上方最近签名"；对 lambda/合成/匿名给明确降级策略；**宁可少产边也不产错边**。阶段2 要么引入最小 tree-sitter，要么**明确承认只做 smali**（`.method` 回扫可靠）、Java 边推迟。
- **native/JNI 边界**：零-LLM 对 JNI 产不出边（无源码文本），设计缺"链在 libX.so 续接"的表示与判分口径——签名校验链这类跨 native 测试会直接记 miss，需先定义判分口径。

### 7.3 砍掉过度设计（把预算投给正确性与可测性）
- **§3.6 第4级 LLM 结构化摘要**（Codex 6行 handoff + summary_prefix + 熔断）：默认不开、门槛 160K（offload 本应让它永不触发）——典型"大模型重装备照搬"。**削到只剩一句**：`body 撑爆就用 ledger 种子开 fresh window（零 LLM）`。
- **阶段4 全量 PageRank**（tree-sitter WASM + power-iteration + Aider 边权）对单 APK needle-finding 是杀鸡用牛刀。**先降级**为 `Manifest 入口 + Retrofit 接口的 grep 派生清单`（现有 shell/grep 拿 90% 入口定位价值、5% 成本），验证小模型 first-hop 真受益后再决定要不要上 tree-sitter+PageRank。
- **§3.9 反向扫描 rollout resume**：`resume.ts + ledger.toJSON` 已让 test-resume 7/7 过，非实测痛点——镀金，降级。
- **阶段3 context-manager 门面**：纯重构、不改行为/指标，诚实标为"整洁性重构"而非杠杆项。

### 7.4 未 surface 的耦合张力（设计需正面回答）
- **offload stub 长任务泄漏**：stub"一次写定永不重写"保前缀（对），但每次大工具调用都在末尾**永久留 ~2KB**、append-only 无法回收 → 40 步多次大 read 下 body 线性增长，"工作集常驻 ≤30–50K"在长任务站不住。**保前缀 vs 保工作集小在长程上冲突**——给出 stub 上界与增长模型。
- **offload 缩 body 反噬命中率百分比**：ephemeral 台账尾（≤4K）每步重算、永不进缓存前缀；body 越小，固定 4K 尾占比越大 → 未缓存分子/更小分母 → **命中率百分比反降**。"收尾步 ≥90%"硬门与"工作集 ≤50K"软目标部分对着干——给出 **body 下限**（低于它则台账尾占比过高、90% 门不可达）。
- **`render()` 上界是 4000 CHARS 不是 4K token**（ledger.ts:159）：CJK+verbatim Java 路径下 ≈1.5–2K token，§3.1/§3.2 预算表有 2–3× 偏差；长链(6+跳)台账超界会 slice 截断（ledger.ts:175）丢证据——需"台账自身超界怎么保关键跳"策略。
- **A/B 方差**：temp>0 下模型路径分叉常呈双峰（找到/迷路），offload on/off 单变量 A/B 的方差主要来自路径分叉而非被测变量，"3 次取中位数"对双峰不稳——需量化重复次数，或用确定性 mock 承担更多控制流验收。
- **迭代成本**：每阶段决策门几乎全依赖在线后端指标，单并发下 A/B×3次×多题×多层 串行可能数十小时级——被低估，需要离线冒烟承担更多。

### 7.5 修正后的实现顺序（取代 §5 的天真顺序）
**阶段 2a（先做，全部离线/确定性）**：benchmark 地基（bank + ground-truth 边 + 机械判分器）+ `system 前缀逐字节不变`单测 + 复现 26% 基线。
**阶段 2b**：边派生（先 smali-only 可靠版 + grep↔read 配对算法 + 错边零容忍）+ 死锁(e) + 工作集回收(写入即落盘)。用 2a 的机械判分器验证 ✓率真升。
**阶段 3**：门面收口（标注为重构）+ 跨会话（若实测痛点才做）。
**阶段 4**：先 `Manifest+Retrofit grep 清单`验证 first-hop 收益，再决定 tree-sitter/PageRank。LLM 摘要层删到一句零-LLM 兜底。

## 8. 消融实验结果（验证每处设计"有用且必要"，防过度设计）
> 方法论（血泪，见 安全审计文档 R3-P1）：**单跑聚合无效**（temp>0 双峰）。故:①按题型分指标(前缀缓存命中率=低方差可单跑；任务✓率=需多seed中位数);②单变量受控(只改一个 env 开关)。三个开关:`REV_AGENT_LEDGER_IN_SYSTEM`(台账位置)/`REV_AGENT_NO_LEDGER_RENDER`(是否给模型看台账)/`REV_AGENT_NO_EDGE_DERIVE`(零-LLM边派生)，默认全开=现行设计。

### 8.1 台账位置(拼 messages 末尾 vs 放 system 头部) —— 验证 SWA 头号设计
指标=前缀缓存命中率(cachedInputTokens/inputTokens,低方差)。3 题 × {tail默认, system}：

| 题 | tail(设计) cache_avg/min | system(旧) cache_avg/min | Δ |
|---|---|---|---|
| duolingo-2 | **84% / 69%** | 37% / 0% | **+47%** |
| kuwo-vipstate | 83% / 55% | 89% / 71% | −6%(单跑噪声/台账稳定) |
| clone-02 | 超时无数据 | 16% / 0% | — |

**⚠️ 诚实修正(核验 wswpmrcfh 抓到我先前的统计过度声称)**:先前写的"均值 84% vs 47% = +37%"是**非配对聚合、虚高**——tail 均值只算 2 题(clone-02 tail 超时无数据被剔),system 均值算 3 题(含 clone system=16 低分)。**干净配对**只有:
- duolingo-2:tail 84% vs system 37% = **+47%**(强)
- kuwo-vipstate:tail 83% vs system 89% = **−6%**(单跑噪声)
- clone-02:tail 超时,无法配对

→ **两侧都有数据的配对均值 = +20.5%**(tail 83.5 vs system 63.0),非 +37%。样本极小(3题/单seed)。

**结论(收敛后)**:拼末尾在 duolingo-2 上 +47%(强)、kuwo −6%(噪声),**配对 +20.5%,方向支持 SWA 但幅度别夸大**。真正的硬证据不在这 3 题小消融,而在**机制层**:SWA 修复的原始实测 **前缀缓存 0%→97%**([[swa_stable_prefix]])+ 演练全程 66–90%(§ 具体题目演练)。台账位置设计**有用、非过度设计**,但"+37%大赢家"措辞已按核验降级为"+20.5%配对、方向正、机制层证据更强"。→ **保留。**

### 8.2 边派生 / 台账渲染 —— 综合消融进行中
bank-multi 20 题 BASE 验证(满足≥20题) + 6 边多题(链路追踪/跨包综合)×{BASE/NO_EDGE/NO_RENDER}×3seed 取中位数,用机械锚点判分器量化。**跑完补此表**;若某机制 on/off 的中位 recall/✓率 Δ 不显著 → 判为过度设计、砍掉。


### 8.3 2b-2「写入即落盘」必要性判定 —— 决定：暂不实现（防过度设计）
设计 V2 §3.3 提过"写入即落盘"(大工具结果第一次进 messages 就截断成 stub)取代事后折叠。**经必要性检测，决定暂不实现**，理由（用户红线：防过度设计、每处设计必须证明必要）：
- **无证据表明需要**：具体题目演练(via-01)与消融跑的 BASE 全程 `folded=0`、`max_ctx≈10k`——日常工作集远小于 256K，现有 `compactHistory`(160k 阈值兜底)从不触发；写入即落盘要解决的"body 膨胀"在实测里不存在。
- **现状已够**：小 ctx 下不折叠=最省(保稳定前缀);真逼近上限时 compactHistory 折一次止血 + 死锁修复(2b-e)已保证折叠后能重读。
- **加了反而有害**：写入即落盘会在**每次**大 read 后改 messages(截断)，虽是首次写定"前缀安全"，但红队已指出它在长任务下 stub 永久线性堆积、且与"给模型看完整刚读内容"冲突——为一个未观测到的问题引入常驻复杂度，正是要避免的过度设计。
- **触发条件**：若未来实测出现 body 常驻 >50K / max_ctx 频繁逼近阈值 / 折叠频繁触发拖累，再实现 2b-2。当前**不做**。

→ **最终实现集(定稿)**：2a-1 前缀守卫 + 2a-2 机械判分器 + 2b-e 死锁修复 + 2b-1 边派生 + 3 消融开关。**2b-2 与阶段4 全量 PageRank/LLM 摘要层均按"无证据不加"原则排除**（对齐 §7.3 红队削减建议）。


### 8.4 ≥20 题验证(BASE 基线,bank-multi,机械锚点判分)
20 题多跳/找类/跨包/安全点/加固题,BASE(全机制默认开)跑过并判分:

| 指标 | 值 |
|---|---|
| 跑过题数 | **20**(满足目标"≥20题验证") |
| 完成/超时 | 13 完成 / 7 超时(180s;超时=难题算力不足,亦为有效数据点) |
| 锚点召回 | 均 0.32 · 中位 0.32 · **完成题均 0.41** |
| 高召回(≥0.7) | 3 题(via-02=1.0、modv6-01=0.88、mtmod-02=0.71) |
| 边派生实证 | **mtmod-02 ✓hop=10**(边派生确定性贡献 10 条 corroborated 边) |

**读法(诚实)**:这是**小模型 35B 在多跳逆向上的真实基线**——易/中题(可读、边清晰)召回高(via-02 满分),难题(native/重混淆/深链)超时或低召回。记忆系统让它**追得动的题追得干净**(mtmod-02 靠边派生攒了 10 条已核验边),但**不改变模型本身的能力上限**(难题该超时还超时)。符合已标定的能力边界。→ ≥20 题验证提供了 BASE 基线,供后续任何改动做 A/B。


### 8.2 边派生 / 台账渲染 消融(4 题×{BASE,NO_EDGE,NO_RENDER}×2seed,机械锚点召回中位数)
| 题 | BASE recall | NO_EDGE recall | NO_RENDER recall |
|---|---|---|---|
| via-02-webview-config | 1.0 | 0.5 | 0.75 |
| chm-01 | 0.389 | 0.5 | 0.5 |
| np-02 | 0.15 | 0.0 | 0.05 |
| modv6-02-signer-hierarchy | 0.467 | 0.8 | 0.4 |
| **✓hop 中位** | **0** | **0** | — |
| **recall 中位** | **0.389** | 0.45 | **0.472** |

**诚实判定(直接服务"防过度设计"):**
- **边派生**:这 4 题上 ✓hop 中位 = **0**——保守判据下**根本没触发**(这些题的调用点不满足"干净具名外围方法"严格条件),故 recall 的 BASE/NO_EDGE 差异是**纯 temp>0 噪声**、与边派生无关。但在 ≥20 验证里 mtmod-02 触发并贡献 **✓hop=10**(§8.4)。→ 结论:**边派生极保守、罕触发;空转零成本、触发即正确(6 单测证无错边)、情境性有益**。**不是过度设计**(无常驻成本),但其**聚合收益小/依题**。保留(默认开,零成本),诚实标注"低产、情境性"。
- **台账渲染**:NO_RENDER 中位 recall **0.472 > BASE 0.389**——**给模型看台账在此样本上没带来益处、甚至略负**(疑似冗长台账占注意力/挤 context)。但 **2 seed 太薄**(temp>0 双峰),**不足以据此砍核心机制**;且台账的主要价值在**守卫底座(stall/dedup/enoughHops 都读 ledger stats)+ O(1) 收尾链路图**,不止于"给模型看"。→ 结论:**"给模型看台账"的益处未在薄样本上确立(甚至存疑)**,需更多 seed 收紧;台账本体(守卫底座+收尾)仍由守卫测试与演练(§ 具体题目演练)支撑。**这正是消融该暴露的东西——不自欺地宣称"有用"。**

**综合结论(每处设计的"有用性"裁决):**
| 机制 | 裁决 | 依据 |
|---|---|---|
| 稳定前缀/台账位置(SWA) | ✅ **有用** | 配对 +20.5%(小样本);机制层 0%→97% 前缀缓存([[swa_stable_prefix]]) |

| 零-LLM 边派生 | ⚠️ 情境性/低产,非过度设计(零空转成本、触发即正确) | ✓hop 消融=0(罕触发)但 mtmod-02=10;6 单测无错边 |
| 台账"给模型看"(render) | ⚠️ **薄样本未确立益处(存疑)** | NO_RENDER 0.472 ≥ BASE 0.389,需更多 seed |
