# 测试语料广度分析：技术栈 × 保护手段（是否太单一？）

> 缘起：用户指出"现在测试范围太单一(9 个 mod APK,基本都是 native Android + 本地布尔破解),真实 App 有 Kotlin/RN/Flutter/Vue-WebApp/Unity 等不同技术栈,以及各种混淆/加密/反逆向手段,组合起来很多"。
> 本文对该观点做**辩证分析**（认同 + 修正 + 反驳），结合实测栈指纹与 2026 现状 web 调研，给出**可执行的测试矩阵**与对 rev-agent 的改进方向。
> 合规：全程只读分析 + 防御审计视角，不产出破解/绕过工具；分析加固/反调试仅限"理解机制 + 给防御建议"。

## 一、裁决：观点基本成立，但需分两个正交轴，而非笼统"样本太少"

**认同**：现有语料确实偏窄——但不只是"数量少",而是**几乎只覆盖了"逻辑在 dex 里、破解点是本地布尔/getter 短路"这一种情形**。这只测了 rev-agent 的一个维度（jadx 可读源码上的静态定位 + 抗混淆 + 抗幻觉）。

**但要修正一个隐含假设**：`加更多技术栈样本 ≠ 能测出更深的分析能力`。原因见下——对 Flutter/Unity/RN/加固壳，**逻辑根本不在 jadx 可见的 dex 里**，一个纯 jadx-读源码的 agent 物理上"看不到"，此时测的是**另一个能力维度**（识别栈 + 诚实报告边界 + 路由到对的工具），不是分析深度。

## 二、实测：现有 9 样本的栈分布（已经不全是 native Java）

对已反编译样本探栈指纹（grep io/flutter、com/unity3d、com/facebook/react + unzip 看 lib/assets）：

| 样本 | 主栈 | 关键发现 | jadx 能看到破解逻辑吗 |
|---|---|---|---|
| device/battery/podcast/code/easynotes | native Java/Kotlin + R8/DexGuard 级混淆 | 破解点=本地布尔/getter 短路，**在 dex 里** | ✅ 能（已实测 battery 91/podcast 82 优秀） |
| snaptube | native + JS 广告 SDK | 破解=smali invoke 替换 + PinkiePie stub | ⚠️ 能但隐蔽（实测 8 分，漏了） |
| **Duolingo** | **native + Unity 混合** | `assets/aa/Android/*monoscripts*.bundle`（Unity Addressables/IL2CPP），游戏化逻辑在 IL2CPP/.so | ❌ 大量逻辑**不在 dex**（jadx 空白） |
| **Clone_App** | native + WebView JS | `assets/iads/*.js` JS 广告 | ⚠️ 部分逻辑在 assets JS |
| 酷我音乐 | native + 海量 Tencent SDK + JSON 配置 | VIP 文案在 assets json，破解点待查（可能 dex 或加固） | 待验 |

→ **结论**：即便这 9 个里，也已经出现 Unity 混合(Duolingo)、WebView-JS(Clone) 这种 jadx 够不着的成分。用户的"太单一"判断正确；且实测已暴露：对非 dex 栈，现有"grep 本地布尔"打法失效。

## 三、正交两轴（真正决定 rev-agent 表现的是这两轴，不是"App 数量"）

### 轴 A：业务逻辑在哪（决定 jadx-读源码 agent 能否"看到"）
| 栈 | 逻辑载体 | jadx 覆盖 | 正确工具 | rev-agent 该做什么 |
|---|---|---|---|---|
| Java/Kotlin native | classes.dex | ✅ 全 | jadx/apktool | **深度静态分析**（核心能力） |
| Flutter | libapp.so（Dart AOT snapshot） | ❌ 几乎空 | **blutter / reFlutter**（读 Dart snapshot 恢复类/方法名,即便 --obfuscate） | 识别 Flutter→说清逻辑在 libapp.so→路由 blutter→不幻觉 |
| Unity | IL2CPP（libil2cpp.so + global-metadata.dat）或 Mono DLL | ❌ dex 只是壳 | **Il2CppDumper / Il2CppInspector**（有 metadata 可恢复符号） | 识别 Unity→逻辑在 IL2CPP→路由 dumper |
| React Native | `assets/index.android.bundle`（JS,常 Hermes 字节码） | ❌ 逻辑在 JS | **hermes-dec / 直接读 bundle**（Hermes 需反汇编） | 识别 RN→逻辑在 bundle→(Hermes 则需专用工具) |
| Vue/WebApp(Cordova/Capacitor) | `assets/www/*.js`（明文/压缩 JS） | ❌ 但 assets 明文可读 | 直接读 assets JS + beautifier | 识别 WebView→逻辑在 assets/www→直接读 JS(反而简单) |
| 加固/packer(乐固/梆梆/爱加密/360) | 运行时解密的 dex + native 壳(DexVMP/DexToCPP) | ❌ dex 是 stub 加载器 | 脱壳(FRIDA-DEXDump/frida-unpack,动态) | 识别壳签名(libjiagu/libshell/StubApp)→说清"dex 被加固,静态只见壳,需脱壳" |

**关键洞见**：对 A 轴的非 dex 栈，rev-agent(纯 jadx 静态)**做不了深度分析**——这不是 agent 的缺陷,是工具边界。测这些样本，真正测的是 agent 的**元能力**：①识别栈；②诚实说清"逻辑在哪、jadx 能看到多少"；③路由到对的工具；④**绝不对空白 dex 幻觉**。这恰恰是专业安全审计 agent 的关键素养(我们已有的 native-boundary 诚实性题 + 反幻觉铁律是雏形，但应升级为**主动栈探测**)。

### 轴 B：保护/混淆强度（决定 dex-visible 时静态读的难度）
无混淆 → R8/ProGuard(名字混淆) → DexGuard(名字+字符串加密+控制流平坦化+算术混淆+多态完整性注入) → 加固(DexVMP/DexToCPP/manifest 防篡改/native 加密) → 全 VMP。
- 现有语料已覆盖 R8~重混淆(NP 20655 文件重混淆、mt 系 l/ 控制流平坦化)——B 轴中段测过。
- **缺口**：DexGuard 级(字符串加密 + 控制流平坦化)专门样本、加固壳样本(测"能否识别壳、说清需脱壳")。

### 第三类：保护机制识别（对静态只读 agent 是"枚举"而非"绕过")
反调试 / 反 Frida / root 检测 / SSL pinning / 签名校验 / Play Integrity / 完整性自校验。
- 对**静态只读**agent：测"能否从代码认出并枚举这些防御机制"(防御审计视角,合规)。
- **不测**"绕过"(那是动态 + 越"只读不破解"红线)。

## 四、反驳/修正用户观点中需辩证的地方

1. **"组合起来很多"→ 对,但组合爆炸不可穷举**。栈(6+) × 保护强度(5) × 破解手段(N) = 无穷。**不应追求覆盖全组合**,而是用**代表性矩阵**(每轴挑高价值代表 + 少量真实混合样本如 Duolingo)。盲目堆样本是伪广度。
2. **"加更多栈"的真实收益是测元能力,不是分析深度**。对 Flutter/Unity,rev-agent 给不出深度分析(工具边界)。若误以为"加 Flutter 样本能测更强分析",会得出错误结论(agent 在 Flutter 上"差"其实是 jadx 的锅)。正确目标:测它**识别栈+诚实+路由**,而非苛求它静态分析 Dart AOT。
3. **有些"手段"对静态只读 agent 不构成分析任务**。如反调试/root 检测——静态只能"识别有这机制",谈不上"复现绕过"(动态+越红线)。把它们纳入"识别/枚举"范畴,别错设成"绕过"目标。
4. **广度 vs 深度的取舍**：与其一个栈一个样本浅尝,不如**核心栈(native)上做深(多种混淆/多种破解手段)** + **非核心栈上做元能力(识别+路由)**。深度在核心栈,广度在识别层。

## 五、推荐测试矩阵（可执行、分优先级）

| 优先级 | 目标能力 | 样本类型 | 出题方向 |
|---|---|---|---|
| **P0** 核心 | dex 深度分析 + 抗混淆 + **抗幻觉** | native Java/Kotlin,覆盖 无混淆/R8/DexGuard级/加固后可dump的dex | 破解点定位 + 技术 + 链路 + 修复(现有审计题即此类) |
| **P1** 元能力 | 栈识别 + 诚实边界 + 工具路由 + **不幻觉** | Flutter(libapp.so)、Unity(IL2CPP,Duolingo已有)、RN(Hermes bundle)、WebApp(Cordova assets JS)、加固壳 | "这是什么栈?业务逻辑在哪?jadx 能看到多少?该用什么工具?(不许对空白 dex 编造)" |
| **P2** 防御审计 | 保护机制枚举 | 含 SSL pinning/root检测/反Frida/完整性校验 的样本 | "枚举出哪些反逆向/防篡改机制 + 各自在哪 + 给绕过它们的攻击者视角下开发者该如何加强(防御)" |
| 混合 | 分清 dex vs 非 dex | Duolingo(native+Unity) 等真实混合 | "哪部分逻辑在 dex、哪部分在 IL2CPP/.so?VIP 解锁点在哪一侧?" |

**样本获取(合规)**：用户提供 / 从开源或官方 demo 找(Flutter gallery、RN sample、Unity demo、Cordova sample)+ 现有 mod。加固壳样本可用公开的加固 demo。**不主动去下载盗版/破解件之外**——现有 mod 已足够 P0/部分 P1。

## 六、对 rev-agent 的改进方向（本分析导出的 backlog）

1. **主动"栈探测"前置**（最高价值）：开局自动 grep/看 APK 结构判断栈(io/flutter、libapp.so、com/unity3d+global-metadata、com/facebook/react+index.android.bundle、assets/www、libjiagu/libshell 等壳签名),输出"栈=X、逻辑在 Y、jadx 覆盖 Z%、建议工具 W"。把现在被动的 native-boundary 诚实性升级为**主动栈识别**,从源头防止对非 dex 栈幻觉。
2. **preflight 扩展**：不只判"有无源码树",还判"这是什么栈、jadx 覆盖了多少业务逻辑、非 dex 部分在哪"——对 Flutter/加固样本直接给"jadx 看不到核心逻辑,需 blutter/脱壳"的秒级提示,而非让 agent 在空 dex 里瞎转+幻觉。
3. **反幻觉铁律**(已加)在非 dex 栈上尤其关键——对 Flutter/Unity,正确答案往往是"逻辑不在 dex,需 X 工具",而非编造一个 dex 里的假机制。
4. **工具路由知识**：agent 应知道每种栈对应的正确工具(blutter/reFlutter/Il2CppDumper/hermes-dec/脱壳)——可作为 §-prompt 或 docs-resources/tool-help 的知识补充。

## 七、结论
用户"太单一"的判断**成立**,且实测已见端倪(Duolingo=Unity/Clone=JS)。但正确的扩法不是"每个栈塞一个样本求深度分析"(对非 dex 栈物理不可行),而是:**P0 在 native 核心栈做深(多混淆多手段) + P1 在多栈做"识别+诚实+路由"元能力 + P2 做保护机制枚举**,用代表性矩阵而非穷举组合。对 rev-agent 最高价值的改进是**主动栈探测前置 + 工具路由知识**,让它面对 Flutter/Unity/加固时能"认出栈、说清边界、路由对工具、绝不幻觉"——这才是专业安全审计 agent 该有的样子。
