# 动态/运行时"去签名校验" · 机制保姆级详解

> 回答一个问题:总报告里那句"**动态去签名校验:机制有等价,小 footprint + 隐蔽的组合不可**"到底在说什么?这里把**运行时绕过签名校验**的全部机制从零讲透——ART 怎么被 hook、五大流派各自怎么权衡、为什么没有开源工具能"既一键又小 footprint 又隐蔽又覆盖广"。
>
> **读者**:懂编程、懂 hook/PLT/LD_PRELOAD、但不熟安卓底层的工程师。**合规**:只讲机制、权衡、检测、加固,**不含针对具体 APK 的操作步骤/命令**。深度背景见同目录《签名校验绕过-开源工具全景》《MT一键过签名校验-机制逆向》与教程系列 `安卓逆向保姆级教程/08、11`。

## ① 一句话本质
**运行时去签名校验 = 在 App 自己问"我这份包是不是原厂签的?"那一刻,动手脚让它听到一个满意的谎。** 各手段的差别只在:这个谎在**哪一层**说、用**多大代价**说、留**多少痕迹**。

App 查自己签名有 4 条取数路径,由浅入深:
1. 走系统 API `PackageManager.getPackageInfo(...).signatures / signingInfo`、`checkSignatures()`(Java/Binder 层,最常见);
2. 不信系统,自己在 native 层 `open`/`mmap` 打开安装后的 `base.apk`,手动解析 ZIP 里的 v1/v2/v3 签名块重算摘要;
3. 把校验搬进系统进程 `PackageManagerService`;
4. 把最终裁决交给**服务端 + Google 硬件远程认证(Play Integrity)**。

**所有本地绕过的天花板都在第 4 条**:只要判定用的密钥链和账本在 Google 服务器与硬件 TEE 里,本机再深的 hook 也伪造不出"只有真验证通过才发放的东西"(如服务端才能算出的解密密钥)。这也是为什么《加固清单》反复强调"校验结果参与解密 + 服务端 nonce"是治本。

## ② ART 运行时 hook 的底层原理(讲给不懂安卓的人)

### 2.1 心智模型:安卓 App 不是"启动"的,是"孵化"的
- 开机时系统拉起一个常驻进程 **Zygote(受精卵)**,预热好常用类库待命。
- 你每点开一个 App,系统让 Zygote **`fork()`** 一份改个名就成了这个 App 的进程。
- **推论**:只要能在 Zygote 里塞一段代码,它会被复制进"之后每一个"App 进程——这是 Xposed 全家(流派③)的地基。

### 2.2 一个 Java 方法在虚拟机里长什么样
ART(安卓的 Java 运行时,类比 JVM)里,每个 Java 方法对应一个 C++ 结构体 **`ArtMethod`**(分配在**不被 GC 移动的 LinearAlloc** 内存里,地址终生不变)。卡片上最关键的字段是 **`entry_point_from_quick_compiled_code_`**——一个**函数指针**,指向"调用这个方法时真正该跳去执行的机器码地址"。

调用任意 Java 方法,机器码层面最终都退化成:**拿到 ArtMethod 指针 → 读 entry_point 字段 → 跳过去执行。**

> **类比**:ArtMethod 是"外卖订单卡",`entry_point` 是卡上写的"送到哪个厨房"。你不用改菜谱(方法体字节码),只要把卡上厨房地址涂成"我家厨房",之后所有点这道菜的人(不管哪个类/线程调用)都先被送到你这。

### 2.3 hook 的核心动作:"偷梁换柱"在哪一跳
1. **备份**:先把原方法卡片整体复制到一张 backup 卡(同在 LinearAlloc),backup 的 entry_point 硬编码指向原始机器码——以后"调用原方法"就是反射调这张 backup。
2. **改写**:把目标方法的 entry_point 改成指向自己的一小段手写汇编 **trampoline(蹦床)**。trampoline 只干一件事:把寄存器里的"目标 ArtMethod 指针"换成"hook 方法的 ArtMethod 指针"(arm64 是 x0 寄存器),再跳过去——执行流就被引到你的 hook 代码。
3. 全程**不碰 APK 文件一个字节、纯内存生效、进程一重启就清零**——这是运行时 hook 相对静态改文件的**核心优势(隐蔽、可逆)**,也是**核心弱点(每次进程启动都要重新注入,依赖一个持续运行的注入通道)**。

> 类比你熟的:这跟改 **PLT/GOT** 表项、`LD_PRELOAD` 顶替符号、或 detour/inline-hook 是同一类"运行时改函数行为",只不过对象是 ART 的方法调度卡而非 ELF 的重定位表。

### 2.4 光改指针不够:ART 的两处"反扑"和两个"坑"
- **反扑 1 · JIT 复编译覆盖**:ART 后台持续重编译热点方法,一重编就用新地址覆盖你刚改的 entry_point。→ 对策:给方法打 `kAccCompileDontBother`(值 `0x02000000`),让 JIT/AOT 都跳过它。
- **反扑 2 · 解释器旁路**:老版本解释器执行时不老实读 entry_point。→ 对策:把方法伪装成 `kAccNative`(值 `0x0100`,"假装我是 native 方法、没有字节码可解释"),逼 ART 只剩"读 entry_point 跳转"这一条路。
- **坑 1 · 版本脆断**:Android 11(R) 之后不能再随便对已 AOT 的方法设 `kAccNative`,否则 ART 会去读**真正的 native 函数指针**→读到野指针崩溃。这是各引擎"版本适配代码量最大、最容易因没跟进新版本而报废"的一环。
- **坑 2 · 内联(inline)**:若目标方法 B 很短、被调用方 A **内联**进了自己的机器码,A 调 B 时根本不走"读卡片"这条路,改 B 的 entry_point 无效。→ 对策:对 A 做 `deoptimize`(强制打回未优化状态)。这是静态改 smali 根本不存在、运行时 hook 才遇到的坑。

### 2.5 关键代差:改"指针" vs 改"字节"
- **纯 entry_point 替换派**(YAHFA / Epic / LSPlant 8.0+):只改 ArtMethod 的指针字段,**不改任何函数体机器码字节** → 对 `.text` 段做 CRC/哈希校验**抓不到**。
- **inline hook 派**(Dobby、pine/SandHook 老版本分支):直接改写目标函数机器码开头几字节为跳转指令 → 内存字节与磁盘 so/oat 不一致,`.text` 完整性校验**能直接抓包**。

> 一句话记:**改"指针"隐蔽,改"字节"露馅。** 这条代差在下面所有流派里反复计价。

### 2.6 六大 hook 引擎(四维互斥,无一全占)
| 引擎 | 手法 | 版本/兼容 | 隐蔽 | 短板 |
|---|---|---|---|---|
| **LSPlant**(LSPosed/LSPatch 底座) | entry_point 替换 + 运行时**动态适配**字段偏移 + DexBuilder 动态生成辅助 dex + Deoptimize 解内联 | API 21–37,最广 | 静态零特征,内存有 liblsplant.so/辅助 dex | 带 Dobby 依赖;已知"无法处理嵌套 hook"(SIGILL) |
| **YAHFA** | entry_point 替换 + **硬编码**按版本偏移表 | 依赖维护者补表,~2020 后停滞 | footprint 最小 | 魔改 ROM 上野指针直接崩 |
| **pine**(canyie,**NP 用**) | entry_point 为主 + 老版本退化 inline hook;**运行时动态探测**偏移 | 4.4–15,对国产定制 ROM 兼容最好 | inline 分支改字节→易被 .text 校验抓 | 复杂度高 |
| **SandHook** | 8.0+ 替换 / 7.x 两级 trampoline inline;可操作 dex2oat 反内联 | 4.4–11,对老版本 sharpening 最全 | 同 pine | 攻击面大 |
| **Epic**(tiann) | 纯 entry_point + AOP 抽象 | 止步 Android 11 | 较好 | 新系统未适配 |
| **Dobby**(通用 native inline hook) | 改机器码字节 + 指令重定位 | 跨平台任意 native 函数 | **最易被查**(字节不一致) | 不区分 ART 方法 |

## ③ 五大绕过流派(原理 + footprint + 隐蔽 + 覆盖)
先约定三维的通俗含义(贯穿全文):
- **Footprint(脚印/注入量)= 为作案往现场搬了多少额外家伙、体积多大。** 分**两本账**:**APK 级脚印**(塞进包里的类/dex/so/资源)和**设备级脚印**(为了让它 work,设备上要长期存在的:root、常驻框架、daemon、PC)。**很多"零改动"方案只是把脚印从 APK 账本挪到了设备账本,总量没消失。**
- **隐蔽性 = 事后拿两份包对比、或运行时扫内存,能不能一眼看出被动过。**
- **覆盖面 = 你的谎能骗过多深的校验**(PM 查询 → App 重算 Java 摘要 → native 自读 → v2/v3 块 → 服务端)。

### 流派① 静态 patch(对照基线,非运行时)
- **原理**:反编译成 smali,人工定位 `checkSignatures`/`MessageDigest.isEqual` 结果分支,改条件跳转/NOP 强制 return 常量,回编重签。
- **footprint 近零**(只改几条指令);**隐蔽**:单点高,但重签必换证书→比 CERT.RSA 秒穿;**覆盖最窄**(只挡改的那一个 Java 点,混淆/内联/反射/native/服务端全穿);**一键化最差**(逐点人工手术)。

### 流派② 静态注入 + 运行时反射(MT `KillerApplication` / NP 系)
- **原理**:釜底抽薪。塞一个额外 dex,注入类在 `Application.attachBaseContext()` 先于业务跑起来(靠改 `MultiDexApplication` 的 `.super` 做"移花接木",**manifest diff 可为 0**)。运行后反射替换 `PackageInfo.CREATOR`(Parcel 反序列化入口),在 `createFromParcel` 里把真签名换成内嵌假证书,再清 `sPackageInfoCache`/`mCreators`/`sPairedCreators` 缓存;或用动态 Proxy 整体包一层 `IPackageManager`。
- **为什么"一网打尽 PM 层"**:hook 点选在**统一入口 API / 反序列化瓶颈**而非某个调用现场。业务代码不管调几次、逻辑多绕,只要走"向 system_server 要 PackageInfo → Binder 传回 → 反序列化"这条路,**一次替换全覆盖**。
- **footprint 小-中**(一个模板类几 KB~几十 KB + HiddenApiBypass,manifest diff=0,免 root 免框架);**隐蔽较好但非零**(类名 `bin.mt.signature.*`、清那三个缓存是可模板化命中的特征);**覆盖中**(挡所有 PM 查询,**挡不住 native 自读**,需配④);**脆点**:依赖特定版本内部字段布局(P 引入 signingInfo 曾让老模板失效),大版本升级需**人工跟版重写**。

### 流派③ 运行时 hook 框架(Xposed→EdXposed→LSPosed→LSPatch / Frida)
同源于②(都拦 API 返回值),区别在**"怎么把 hook 代码塞进进程"**——这是一条**"脚印从设备级搬到 APK 级"的迁移链**:
| 形态 | 注入手法 | 脚印落点 |
|---|---|---|
| Xposed 原版 | 替换 `/system/bin/app_process` | 设备级:root+写 /system+重启;APK 零改动 |
| EdXposed | Riru 顶替 `libmemtrack.so` + hook fork | 设备级:root+Magisk+Riru |
| LSPosed | Riru 版 / **Zygisk 版**(Magisk v24+ 内置);引擎=LSPlant;按作用域挂载 | 设备级:root+Magisk/KernelSU;**APK 零改动** |
| **LSPatch** | 放弃改设备,把 Xposed 缝进 APK:改 `appComponentFactory` 指向桩类,先于原 App 加载打包版 LSPlant | **APK 级**:重签+`assets/lspatch/`+dex/so |
| **Frida** | server(root daemon+PC 下发 JS)/ gadget(`libfrida-gadget.so` 塞进 lib) | server:设备级(daemon+PC);gadget:APK 级(单 arch so 可达 20MB+) |

- **LSPatch 的 `sigBypassLevel`——不是加分项,是给"重签名"擦屁股**:免 root 的代价是必须用自己证书重签,会让 App 自校验失败。于是内置三档:**Lv0(关)**;**Lv1(pm)**=反射顶替 `PackageInfo.CREATOR`(与 MT KillerApplication 同路数,只挡 Java API);**Lv2(pm+openat)**=再 hook libc `__openat` 把读 APK 的 native 调用重定向到缓存的原始 APK——**这就是把流派②和④焊死进同一个免 root 自动产物**。
- **权衡**:纯 Xposed/LSPosed **对 APK 文件零 diff(隐蔽满分)但设备级脚印巨大**(root/框架痕迹极易测);**LSPatch 隐蔽性最差**(`assets/lspatch/`+改过的 `appComponentFactory`+新证书都是稳定可 grep 特征,银行类会被拒);**Frida server 最易检**(端口 27042/进程名/`gum-js-loop` 线程名/`/proc/maps`)。框架本身只覆盖 Java 层(native 自读需另配 hook=流派④)。

### 流派④ native killOpen(hook `open`/`openat` 重定向到内嵌原版)
- **原理**:专堵②③的共同短板——App 在 native 层直接读安装后 APK 字节验签。打包时把**一份完整原始 APK** 内嵌进 assets,运行时用 inline hook(Dobby/xHook)劫持 libc `open`/`openat`/`mmap`,命中"读被改过的自身 APK 路径"时透明重定向到释放出的原版。**数据源头级伪装**,不关心上层是 Java 还是 native。
- **footprint 四类最重**(内嵌整份原 APK,几十~上百 MB,随目标线性增长);**隐蔽最差**(assets 里一份和自身体量相当的完整 APK,`unzip -l` 看大小分布就露;inline hook 留 PLT/GOT 痕迹;`origin.apk` 是现成锚点);**覆盖**:挡住 native 自读 + v2/v3 块(唯一专覆盖这档),配②③把"设备本地能查到的签名源"堵全;对服务端 attestation 无效。

### 流派⑤ 系统级(CorePatch / microG)
- **原理**:战场挪到系统进程。CorePatch 本质是跑在 `system_server` 里的 LSPosed 模块,直接 hook `PackageManagerService` 比较签名/校验 v2v3/降级校验的方法,让它对**全系统所有 App** 统一返回"通过";或对 `services.jar` 做 smali 静态 patch。microG signature spoofing 是 ROM 层新增 `FAKE_PACKAGE_SIGNATURE` 权限、白名单式对授权者返回伪 Google 签名。
- **footprint**:LSPosed 模块形式文件改动小,但要 root+框架驻留;**隐蔽**:对被改 App **最隐蔽**(APK/dex/内存零改动),但暴露面转移到设备层(root/Magisk/bootloader);**覆盖最广**(一次改动全机生效),但管不到 App 私有 native 校验(仍需④),对服务端无效。

## ④ 四维对比矩阵(★越多=该维度越"好")
| 机制/工具 | 一键化 | APK级脚印小 | 设备级脚印小 | 隐蔽(对APK) | 覆盖面 |
|---|---|---|---|---|---|
| 静态 patch | ★☆☆(逐点手工) | ★★★ | ★★★ | ★★☆(但换证书) | ★☆☆(仅一点) |
| **MT/NP 反射注入②** | ★★★(手机端一键) | ★★★(diff≈0) | ★★★(免root) | ★★★(manifest 0 diff) | ★★☆(PM层,缺native) |
| Xposed/LSPosed③ | ★★☆(装模块) | ★★★(零改APK) | ☆☆☆(root+框架) | ★★★(对APK满分) | ★★★(Java全覆盖) |
| **LSPatch③** | ★★★(PC 一条命令) | ☆☆☆(体积翻倍+lspatch) | ★★★(免root) | ☆☆☆(assets/lspatch 明显) | ★★☆(可调Lv) |
| Frida server | ★★☆(需PC/脚本) | ★★★ | ☆☆☆(daemon+PC) | ★★★(对APK) | ★★★(Java+native) |
| native killOpen④ | ★★☆ | ☆☆☆(内嵌整包) | ★★★ | ☆☆☆(第二个APK) | ★★★(含native自读) |
| CorePatch⑤ | ★★☆(装模块) | ★★★(零改APK) | ☆☆☆(root+框架) | ★★★(对APK满分) | ★★★(全机,缺私有native) |

**读表结论**:每一行都有 ☆(短板)。**没有任何一行同时把"一键化 + 两个脚印都小 + 隐蔽 + 覆盖广"占满。**

## ⑤ 为什么"小 footprint + 隐蔽的组合"开源做不到(命题论证)
这句话的完整含义:**机制上每一档校验都有开源等价物能绕,但"一键化 × 小footprint × 隐蔽 × 高覆盖"四维,没有单一开源工具全占。** 根因两条:

1. **footprint 是"两本账",按下葫芦浮起瓢**:凡是把 APK 级脚印做到 0 的(LSPosed 纯内存 hook、Frida server),都靠把成本转嫁到**设备级**(root+框架常驻),而这本身变成新的、更大的静态/运行时特征;凡是不改设备的(LSPatch、killOpen、静态patch),就得把东西塞进 APK,**APK 级脚印和暴露面立刻涨**(LSPatch 的 `assets/lspatch/`、killOpen 的内嵌整包)。
2. **覆盖面天花板由"校验点在哪一层"决定**:PM/Java 层能被②③一网打尽;native 自读必须④;系统级要⑤;而这些"补齐覆盖"的动作**每一个都在牺牲 footprint 或隐蔽**。想覆盖广 → 要么上 root 框架(设备脚印爆炸)、要么内嵌原包(APK 脚印爆炸)。

**具体到开源工具**:LSPatch 一键✓但 footprint 大、不隐蔽(assets/lspatch 特征、体积翻倍、银行类拒);LSPosed 隐蔽(对 APK)✓但要 root(设备脚印大、非普通用户可分发);Frida 覆盖广✓但要 daemon+PC(运营脚印大、不可分发);静态 patch footprint 小✓但非一键+覆盖差。**四个角各占一个,凑不齐。**

**MT/NP 怎么在手机端补上"一键"那一角**:它们用的是流派②(反射注入)——**手机端点一下就完成"提取原厂证书→回填模板→注入 dex→改 `.super`→重签"**,同时做到 **manifest diff=0(隐蔽)+ 只加一个小 dex(APK 脚印小)+ 免 root(设备脚印小)+ 一网打尽 PM 层(覆盖中)**。它在"一键+小footprint+隐蔽"三项同时拿了高分——**这正是开源 PC 工具凑不齐的组合**;代价是覆盖面只到 PM 层(要打 native 自读得再挂 killOpen,footprint 就涨了)、且模板要人工跟版。这就是那句话的完整意思:**机制人人有,但 MT/NP 那种"小 footprint + 隐蔽 + 一键"的组合,开源侧没有单一工具能给。**

## ⑥ 检测与加固(防御方)
**检测(按流派)**:
- 反射注入②:类名 `bin.mt.signature.*`/`PmsHookApplication`、对 `sPackageInfoCache`/`mCreators`/`sPairedCreators` 的反射清缓存、某基类 `.super` 指向陌生类(manifest 却正常)、`hiddenapibypass`。
- 框架③:LSPatch 五件套(`assets/lspatch/`、改过的 `appComponentFactory`、新证书、loader so/dex);LSPosed/Xposed 的 root/Zygisk/Magisk 设备特征;Frida 的 27042 端口/`frida-agent`·`libfrida-gum.so`/`gum-js-loop` 线程/`/proc/self/maps`。
- hook 引擎:**entry_point 范围自检**(关键方法 entry 应落在 oat 映射区间内,指向匿名内存/新 so 段即报警)、**access_flags 异常位检测**(纯 Java 方法突然带 `kAccNative`=强特征)、**`.text` 段 CRC/哈希**(专抓 inline hook 派,纯 entry_point 派抓不到——见 §2.5)、非常规 ClassLoader/辅助 dex(LSPlant 运行时生成的 dex 不属原签名产物)。
- killOpen④:assets 里第二个完整 APK、`origin.apk` 字符串、libc `open/openat` 被 hook(读 `/proc/self/maps` 查 libc 首字节)。

**治本加固(呼应《加固实施清单》)**:① 签名校验**多源交叉**(native 直读 v2/v3 块字节 + PM 结果比对);② **检测 `open/openat` 是否被 hook** + 别只做"读文件比对"(本地任意执行下终可被 IO 重定向绕过——本质限制);③ **反调试/反注入/反 frida**;④ **最关键——校验结果参与业务解密 + 绑服务端 nonce + Play Integrity**:把"绕过校验"变成"解不出内容/服务端不认"。**因为流派①-⑤全是本地伪装,唯有第 4 条取数路径(服务端+硬件认证)是它们的共同天花板**——本地 hook 再深,也算不出只有真验证通过才下发的密钥。

## ⑦ 一页速记
- **本质**:App 问"我是不是原厂签的",绕过=在它取数那一刻喂谎;取数有 4 层,**天花板在服务端/Play Integrity**。
- **ART hook 内核**:改 `ArtMethod.entry_point` 指向 trampoline + backup 原方法;`kAccCompileDontBother` 防 JIT 覆盖、`kAccNative` 堵解释器旁路;内联要 deoptimize;**改指针隐蔽、改字节露馅**。
- **五流派**:①静态patch(小脚印/覆盖窄/非一键)②反射注入 MT/NP(一网打尽 PM 层/manifest diff=0/免root)③框架 Xposed·LSPatch·Frida(注入通道之争,脚印在设备 vs APK 之间搬)④killOpen(专治 native 自读/内嵌整包/脚印最大)⑤系统级 CorePatch(全机生效/要 root)。
- **那句话**:机制人人有,但"**一键 + 小 footprint + 隐蔽**"三者同时满足,开源 PC 工具凑不齐;**MT/NP 用手机端反射注入补上了这个组合**(代价是覆盖只到 PM 层 + 要人工跟版)。
- **防御根**:多源交叉 + 检测 hook + **校验结果参与解密 + 服务端裁决**。
