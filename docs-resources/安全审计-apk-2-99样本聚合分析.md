# 99 例违规 Mod APK 聚合分析：破解类型、作者指纹与加固对抗态势

> 一句话定位：对 99 份「被违规 mod 的安卓 APK」只读取证审计报告做统计聚合，给出破解类型/模组作者/工具链/签名方案/置信度五维分布，并提炼 5 条跨样本可复用洞察，供审计员与本地模型快速建立先验判断。

> **合规声明**：本文仅为防御与取证视角的统计聚合。所有数据来自 99 份独立只读审计报告的结构化字段，**不链接、不复述任何单份报告的详细复现步骤**，不提供可直接执行的绕过/patch 操作序列。目的仅为帮助审计员识别攻击手法、建立检测先验、制定加固对策。

| 置信度 | 样本数 | 占比 | 含义 |
|---|---|---|---|
| 高 | 49 | 49.5% | 具体类.方法/字节码改动被直接坐实 |
| 中 | 48 | 48.5% | 定位到入口/机制层，但精确改动点被原生化/加固/Hook 遮蔽，标注【推断】 |
| 未标注 | 2 | 2.0% | 报告中该字段缺失 |

## 七、跨样本洞察（5 条）

1. **签名完整性事实上已"整体失守"**：99 个样本中 98 个（99%）原开发者签名被替换为模组作者自签或占位证书，仅 1 例保留原厂签名。若某审计任务中发现待测 APK 签名证书 CN 不属于已知开发者组织，应默认其为重打包产物，而非把"签名验证通过"当作"内容可信"的依据。

2. **越"强"的 App 越依赖 native 化/注入而非纯静态 patch**：62.6% 的样本使用 NP管理器 Apk-Dex2C 把改动方法整体原生化，23.2% 叠加 Pine/LSPlant/Epic 等 ART Hook 引擎在内存中改行为而完全不碰 dex 字节。这类样本的置信度显著更低（高置信占比 36.8% vs 无加固样本的 57.4%）——**加固程度可作为预判"静态分析能挖多深"的前置信号**：一旦在 `assets/` 下看到 `protected_by_np`/`protected_by_yj` 类水印文件，或在 `lib/*/` 下看到非官方 so（`liblshook.so`/`libcxapkmod.so`/`libyrf.so`/`libjiagu*.so`），应立即调低"能坐实具体改动"的预期，把审计目标从"定位每一行 patch"下调为"定位入口与机制"。

3. **签名绕过与权益恒真常成对出现**：命中"签名过验证/ApkSignatureKillerEx/killPM 反射清空签名缓存"类特征的 29 个样本中，18 个（62.1%）同时命中"isVip/isPremium/恒真"类特征——说明这两种手法在实战中常被同一条流水线打包在一起：先反射伪造签名骗过 App 自身完整性自检，再在权益判定处恒真。审计中一旦发现签名自校验被绕过的痕迹，应主动扩大搜索范围去核对会员/Pro 判定是否也被改动，反之亦然。

4. **模组作者按 App 类型形成鲜明专精分工**：内容消费类 App（影视/漫画/小说）的破解几乎被鹿蜀（会员/VIP + 去广告对半）、zhou45（去广告为主，13/14）两家承包；工具效率类 App（文件管理器/阅读器/相机/计算器）的"高级版解锁"则集中在 youarefinished、NURIK、Balatan 三家（各自 75%+ 样本落在"高级/Pro"）。看到证书 CN 或作者水印即可先验判断破解类型，无需从头分析。

5. **Top 3 作者垄断近半数样本，长尾极长**：鹿蜀+zhou45+PJAPK 三家覆盖 45.5% 的样本，而 24 个作者标签中有 11 个只出现 1 次。这意味着打击/监测资源如果优先覆盖头部 3-6 家（覆盖 68.7% 样本），边际收益远高于逐一应对长尾——但同时说明入行门槛低、工具链高度同质化（同一套 apktool+MT管理器+ApkSignatureKillerEx 组合任何人都能复现），单纯打击头部作者不能根治问题，须从"客户端权益判定不可信"这一架构缺陷上根治（见下）。

## 八、审计员速查表：信号 → 假设 → 去哪核实

| 看到的信号 | 大概率含义 | 去 grep / 核实什么 |
|---|---|---|
| `AndroidManifest.xml` 里 `android:appComponentFactory` 指向非官方包名 | Application 继承链被劫持，运行时注入 | 反编译该类的 `<clinit>`/构造函数，查是否调用 `killPM`/反射改 `PackageInfo.CREATOR` |
| `assets/` 下有 `protected_by_np`、`protected_by_yj` 等水印文件 | 商业加固/Dex2C 原生化已介入 | 别再执着找 smali 层改动，转去 `lib/*/` 找可疑 so 名，定位"入口"而非"每行改动" |
| `lib/*/` 下出现 `liblshook.so`/`liblsplant*.so`/`libEpic*.so`/`libpine*.so`/`libaliuhook*.so` | ART 方法级内存 Hook 引擎 | 检索这些库的加载点（`System.loadLibrary`/JNI_OnLoad），确认 Hook 目标类；扫描 `/proc/self/maps` 特征做运行时检测（防御侧建议） |
| 证书 `CN=lushu` / `CN=zhou` / `CN=editor` / `CN=rockz5555` 等已知模组作者标识 | 命中已知作者指纹 | 参照本文第三节"手法指纹速查表"直接定位其惯用破解类型和工具链，缩小排查范围 |
| 报告/字节码里出现 `bin.mt.signature.*`、`ApkSignatureKillerEx`、`bin.ghost.yrf`、`killPM()` | 客户端签名自校验被绕过 | 按洞察 3，同时扩大排查 isVip/isPremium/isMember 等权益判定方法是否也被恒真 |
| dex 分片数异常（如 classes7/classes30 等高编号）、高熵 `.jar`/`.VData` 资源文件 | 存在整体加密壳（爱加密/360/SecShell），真实业务代码不可静态读 | 停止尝试反编译该分片；改为在 native 层/manifest/资源层找"壳载入入口"，并诚实标注"具体改动位置不可静态确证" |
| 签名方案仅 `v2+v3`、v1 校验失败或 `META-INF` 缺失 | 重打包 + 自签的强信号 | 无需进一步验证即可判定原始签名链已被破坏，转而核对新证书 CN/组织信息是否匹配已知模组作者 |
| Application 父类改为 `com.srpatchv3.Application` / `com.srp.patch.Init` / `com.cxapk.mod.*` 之类壳载入类 | 通用批量改机框架（"壳加载器"模式），非该 App 专属代码 | 该类通常是多 App 共用的通用注入器，不必深挖其内部实现，重点核实它反射篡改了哪些系统 API（签名缓存/PackageManager 等） |

## 九、静态分析边界声明（诚实标注，避免幻觉）

- 本文统计的"置信度：中"样本，绝大多数是因为 **Dex2C 原生化 / VMP / 商业加固壳 / 运行时 ART Hook** 导致具体改动指令不可静态还原，报告在"cp"字段中已明确标注【推断】——**这不是分析失败，而是静态方法论的固有边界**。
- 遇到同类信号（native 化、加固壳、Hook 引擎指纹）时，**不要因为"没搜到具体改动方法"就断言"这个版本没有被破解"或"这个模块不存在改动"**——正确做法是承认"入口/机制已定位，具体字节级改动因加固/原生化超出静态审计能力范围"。
- 加固不是不可突破的黑箱（本次 62.6% 样本仍能定位到 native 化的入口类/JNI 注册点，23.2% 能定位到 Hook 引擎特征库），但**突破加固定位到具体篡改内容通常需要动态分析/运行时 dump**，这已超出只读静态审计的范围，应如实上报为"需要动态验证"而非继续静态硬猜。

## 十、给防御方的加固优先级（跨样本共性归纳）

1. **权益判定上移服务端**：会员/订阅/Pro 与广告开关的最终裁决放服务端，客户端仅展示服务器签发的短时效令牌——针对洞察 1、3。
2. **签名完整性多源校验且参与业务解密**：不要只依赖 `PackageManager.getPackageInfo(GET_SIGNATURES)`（已被 ApkSignatureKillerEx 式反射 Hook 完全绕过，28.3% 样本命中）；应 native 多点直接解析 v2/v3 签名块字节做哈希比对，且校验结果参与关键数据解密——针对洞察 1、3。
3. **运行时反 Hook / 反注入自检**：扫描 `/proc/self/maps` 中 `liblshook`/`libpine`/`liblsplant`/`libEpic`/`libaliuhook` 等特征库；检测 `appComponentFactory` 被劫持、Application 继承链异常——针对洞察 2（23.2% 命中 ART Hook）。
4. **加固壳 ≠ 防篡改**：本批样本证明商业加固壳未能阻止"不碰加密 dex，仅靠内存级 ART Hook"的绕过；加固需与签名校验、反 Hook、服务端裁决协同——针对洞察 2。
5. **默认分支 fail-closed**：授权/校验遇网络异常、缓存缺失、未知状态时默认拒绝而非放行（本批多起破解正是利用"异常→默认放行"的收敛出口）——针对全部权益类破解（84/99 样本）。
