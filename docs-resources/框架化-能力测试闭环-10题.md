## 三、找 bug —— 逐一诊断 5 个 miss（亲自核实源码，不臆断）

### bug-A（真 bug·可修）q09-duolingo：crack-audit playbook 锚点/指纹缺口
- **GT 已核实**：`Inventory$PowerUp.isPlusSubscription()` @ `Inventory$PowerUp.java:415` 真身是 `return this.f33598e == ...PLUS ? true : true;`（两分支恒真的重言式）。
- **agent 干了啥**：追了红鲱鱼——`SharedPreferences` 的 `premium_offer_count` 计数器（`zc/c1.a()`，其实是 `void` 促销计数，与门禁无关），漏掉 `isPlusSubscription`。
- **根因**：crack-audit playbook 的 grep 锚点表只有 `vip/pro/premium/getHasBuyed…`，**缺 `subscription/isPlusSubscription/hasSubscription` 系命名**；且**缺「`? true : true` 重言式」这个篡改指纹**。弱模型不会自己想到查订阅系命名。

### bug-B（判分方法学局限·非纯 miss）q08-clone：多破解点
- **GT**：`UserCache.C()` @ `UserCache.java:150` = `return true;`（已核实存在）。
- **agent 的答案**：`com.mrlee.common.leetrue()` @ `common.java:12`——**也真实存在，也是 mod 注入的恒真 helper**（已核实）。
- 即 Clone 有 ≥2 个真破解点，agent 找到了另一个真的，但**单 GT 锚点召回判 0**。这不是纯 miss，是**单点 GT 判分对「多破解点 App」系统性低估**。

### bug-C（模型上限·非框架可修）q07-snaptube
- 短名混淆 `o/lw0.h` + `reads=1 / conclusion=1 / 113s` → 疑似**读了 1 个文件就下结论**。介于「守卫过早放行」与「模型面对混淆早早认输」之间；无精确锚点。

### 上限类（本就不指望修）q04-battery / q10-kuwo
- q04 深计费协程链（`ib1.invokeSuspend → ub1.m`）、q10 控制流平坦化——这是 35B 本地模型的能力天花板，非知识注入可救（印证 memory `arch_three_proposals_verdict`：主瓶颈是**行为**不是**知识**）。

## 四、修 —— 只改可修的 bug-A（playbook），commit `<crack-audit 锚点/指纹补全>`

`src/playbook.ts` crack-audit `steps`：
1. **锚点扩表**：`isSubscribed|isSubscription|hasSubscription|isPlusSubscription|isGoldSubscription|isPlus|isSuper|subscription|premium|donate|adFree|isAdFree|skuPremium`。
2. **新增篡改指纹**：② 三元恒真/重言式 `return cond ? true : true`（Duolingo 实见）；③ 注入恒真 helper 类 `com.<modder>.common.leetrue()`（Clone 实见）。
3. **新增一步**：可直接 grep 篡改指纹（字面 `? true : true`、`return true;` 扎堆的类、getBoolean 后孤儿行）。
4. provenance 补 Duolingo/Clone 归纳来源。

离线单测 `scripts/test-playbook.ts` **17/17**（+3 断言校验新锚点/指纹在渲染块里）；typecheck 维持基线。

## 五、再跑对比 —— q09-duolingo 复测（`_scratch/pi-bench/cap-run2/`）

| 指标 | Run-1（修前） | Run-2（修后） |
|------|--------------|--------------|
| `isPlusSubscription` 是否出现在轨迹 | ❌ 0 次 | ✅ **6 次**（+`isSubscription`/`hasSubscription`） |
| 锚点召回 | 0.00 (0/8) | **0.00 (0/8)** |
| 最终结论指向 | 红鲱鱼 `premium_offer_count` 计数器 | 改指 `y2/*` 一堆 `return true` + `yx/c SubscriptionInfo` |

**诚实结论**：修**有效但不充分**。
- **有效**：playbook 锚点补全后，agent **确实开始 grep 并提到了正确方法名** `isPlusSubscription`（修前完全没出现）——知识注入把「该查什么」推进去了。
- **不充分**：agent 仍**没 read+核实+收敛**到 `Inventory$PowerUp.java:415`，而是被 Duolingo 的**体量**（65k 文件、30+ 处散落 `return true`）带偏，改抓了 `y2/*`（核实：那些 `return true` 旁边**并无** subscription 上下文，是泛型 boolean 方法，属 grep-and-guess，**未核实的弱答案**）。
- 这正好复现 memory `completeness_audit` / `arch_three_proposals_verdict` 的判断：**知识缺口修得动，但大体量+需要"读进去确认"的行为缺口，35B 本地模型的天花板顶在那**。playbook 是边际增益，不是银弹。

## 六、闭环产出的两条真发现

1. **playbook 锚点/指纹缺口是真 bug，已修**（q09 修后能 surface 正确锚点）——但对**超大体量 App** 单靠知识注入不足以收敛，需配合更强模型或前置案卷 handoff（memory 已证 case-file 能破上限）。
2. **单点 GT 锚点召回对「多破解点 App」系统性低估**（q08-clone、q09-duolingo 都 ≥2 真破解点，agent 找到了 GT 之外的真点却判 0）。判分方法学局限，`recall=0 ≠ agent 全错`。**后续判分应允许多 GT 锚点或「命中任一真恒真门即算部分分」**——这是比 playbook 更值得做的"优化"，但避免过度工程，留作判分器 TODO。

## 七、诚实边界（勿夸大）
- 平均 0.311 是**全框架开**的单跑数（temp>0 有噪声），非多 seed 中位——绝对值仅供分层判读，别当精确基准。
- 「修有效但不充分」是本闭环最诚实的一句：**别因为 playbook surface 了锚点就宣称 q09 修好了**——召回仍 0.00。
- 5 个 miss 里只有 1 个（q09 锚点缺口）是框架可修的；其余是模型上限(q04/q07/q10)或判分局限(q08)——**如实归因，不把模型上限伪装成"待修 bug"**。
